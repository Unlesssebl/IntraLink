# Printer Worker Service

Сервис `printer-worker` является частью системы IntraLink и предназначен для автоматизации удаленной установки принтеров на целевых ПК пользователей в домене Active Directory / Windows с использованием WinRM (PowerShell) и SMB.

## Основной функционал

1. **Подписка на события:** Сервис подписан на Redis Pub/Sub канал `intraservice_events` и слушает уведомления о новых задачах и изменениях статусов.
2. **Маршрутизация (Hybrid Router):**
   - **Fast-Track:** Если параметры принтера и ПК четко переданы, они сопоставляются с Базой Знаний (`printers_knowledge_base.json`).
   - **Smart-Track (LLM-as-a-Function):** Если задача написана в свободной форме, используется локальная/облачная языковая модель для извлечения структурированных параметров.
3. **Hardware-First USB-подключение:** При наличии USB-принтера сервис запрашивает Hardware ID устройства по WinRM, сравнивает с базой знаний и автоматически подгружает точечные PnP драйвера.
4. **Управление через WinRM & SMB:**
   - Копирование необходимых драйверов на целевой ПК по SMB (только если драйвер отсутствует).
   - Выполнение команд PowerShell через WinRM для добавления порта, импорта драйвера и регистрации устройства.
5. **Стейт-машина (Orchestrator):** Управляет стадиями установки и пишет человекочитаемые отчеты на каждом шаге обратно в заявку IntraService через Core API.
6. **Целевая фильтрация:** Воркер реагирует только на те заявки, где текущий администратор указан исполнителем в IntraService, игнорируя чужие задачи. Выполняется **ранняя фильтрация** событий прямо из Redis (по ID или логину) до осуществления ресурсоемких HTTP-запросов к API.

## Конфигурация (.env)

Переменные окружения для работы сервиса:

- `REDIS_URL` — адрес сервера Redis (по умолчанию `redis://127.0.0.1:6379/0`).
- `CORE_API_URL` — адрес Core API (по умолчанию `http://127.0.0.1:8000/api/v1`).
- `BOT_API_KEY` — API-ключ для аутентификации в Core API.
- `WINRM_USERNAME` — имя учетной записи администратора в домене / на ПК для подключения WinRM.
- `WINRM_PASSWORD` — пароль администратора для WinRM.
- `WINRM_TRANSPORT` — протокол WinRM (`ntlm`, `kerberos`, `basic`, по умолчанию `ntlm`).
- `LLM_PROVIDER` — провайдер языковой модели (`ollama` или `openai`).
- `LLM_API_URL` — URL адрес API модели.
- `LLM_API_KEY` — API-ключ для внешних сервисов (не требуется для Ollama).
- `LLM_MODEL_NAME` — имя модели для парсинга текста (например, `llama3` или `gpt-4o-mini`).
- `PRINTERS_KB_PATH` — путь к локальному JSON-файлу базы знаний принтеров.
- `PRINT_OUTPUT_DIR` — путь к папке сохранения эмулируемых печатных форм (по умолчанию `./prints`).
- `MAX_CONCURRENT_JOBS` — максимальное число одновременно выполняемых задач (по умолчанию `5`).
- `PRINTER_EXECUTOR_IS_USER_ID` — (Опционально) ID аккаунта исполнителя в IntraService. Если задан, воркер обрабатывает только заявки данного пользователя.
- `PRINTER_EXECUTOR_LOGIN` — (Опционально) Логин аккаунта исполнителя в IntraService. Удобная альтернатива фильтрации по ID.


## Структура папок сервиса

- `/orchestrator` — логика маршрутизации, схемы Pydantic и стейт-машина оркестратора.
- `/strategies` — реестр стратегий и классы для сетевых и USB принтеров.
- `/executors` — низкоуровневое асинхронное выполнение команд (WinRM, SMB).
- `/llm` — абстрактный интерфейс и клиенты для Ollama/OpenAI.
- `/worker_services` — клиент Core API, подписчик Redis, модуль отправки уведомлений.
- `/knowledge_base` — статические файлы справочников и базы знаний.
- `action_config.py` — конфигурация внешних действий воркера (статусы, шаблоны комментариев, адаптивные правила ошибок).

## Конфигурация действий и адаптивные комментарии (action_config.py)

Воркер поддерживает декларативную настройку действий (изменение статусов задач и отправка комментариев в IntraService) без изменения логики оркестратора:
- **Действия (ACTIONS):** Каждое ключевое событие (`on_success`, `on_usb_disconnected`, `on_error`, `on_state_lost`, `on_orphan_recovered`) сопоставлено с целевым статусом в IntraService и шаблоном ответа пользователю. Для системных и инфраструктурных сбоев (`on_error`, `on_state_lost`, `on_orphan_recovered`) по умолчанию установлены `None` для статуса и шаблона, что позволяет обрабатывать системные ошибки в "тихом" режиме.
- **Адаптивные правила ошибок (ERROR_RULES):** Позволяют перехватывать конкретные ошибки из логов выполнения (например, проблемы WMI/RPC подключения, недоступность МФУ по сети, отсутствие обязательных параметров) и отправлять пользователю полезные инструкции по их устранению (например, просьбу проверить сетевой кабель, перезагрузить ПК или указать корректный IP-адрес). При срабатывании адаптивного правила статус заявки переводится в «Требует уточнения» (35).


## Динамическое управление WinRM (WMI Bootstrap)

Для исключения зависимости от настроек групповых политик (GPO), сервис использует механизм динамического управления службой WinRM на удаленных ПК:
1. **Подключение WMI (DCOM/RPC):** Используя библиотеку `impacket`, оркестратор асинхронно подключается к порту 135 целевого хоста.
2. **Активация WinRM:** С помощью вызова `Win32_Process.Create` на хосте запускается PowerShell-скрипт. Ход его выполнения логируется локально в `C:\Windows\Temp\wmi_bootstrap.log` через `Start-Transcript`. Скрипт опрашивает статус службы WinRM и параметры `WSMan` (Basic Auth, AllowUnencrypted). Настройки применяются идемпотентно, при этом служба WinRM запускается при необходимости, а встроенное системное правило брандмауэра `WINRM-HTTP-In-TCP*` активируется. Кастомные правила не создаются. При настройке AllowUnencrypted и Basic Auth в логи выводится явное предупреждение безопасности `[SECURITY]`. После отправки команды оркестратор динамически ожидает открытия TCP-порта `5985` с таймаутом до 120 секунд (для медленных ПК). Если порт не открылся, воркер пытается прочитать `wmi_bootstrap.log` через SMB и логирует детальные ошибки.
3. **Выполнение команд:** После успешного запуска WinRM (или подтверждения доступности порта 5985) все операции диагностики и установки принтера осуществляются через штатный `WinRMExecutor`.
4. **Деактивация WinRM:** По завершении установки (успешной или сбойной) в блоке `finally` оркестратор выполняет удаленную остановку службы WinRM (`Stop-Service WinRM`) и деактивирует встроенное правило брандмауэра `WINRM-HTTP-In-TCP*`, возвращая систему в безопасное исходное состояние. StartupType службы не изменяется.

## Отказоустойчивость и безопасность (Orphan Recovery & Блокировки ПК)

Для повышения надежности и устранения уязвимостей в многопользовательской среде внедрены следующие механизмы:
1. **Распределенная блокировка по хостам (PC Locks):** Чтобы предотвратить одновременное выполнение нескольких задач установки на одном и том же компьютере (что может привести к конфликту WinRM/WMI сессий) в условиях горизонтального масштабирования сервиса, все WMI/SMB-операции установки выполняются под распределенной блокировкой Redis (`r.lock(f"printer_pc_lock:{target_pc}", timeout=3600)`).
2. **Восстановление сиротских задач (Orphan Recovery):** При перезапуске микросервиса `printer-worker` автоматически запускается фоновое сканирование состояния в Redis:
   - Задачи в незавершенных статусах (`PROBING/ROUTING/PARSING/COPYING/INSTALLING/VERIFYING`), во время которых WinRM-порт мог остаться открытым, переводятся в статус `FAILED`, при этом для их хостов принудительно вызывается отключение WinRM (`wmi.disable_winrm()`), а в IntraService отправляется статус «Требует уточнения» (35) с комментарием о сбое.
   - Задачи в статусе `WAITING_APPROVAL` сбрасываются в `FAILED` без отключения WinRM (так как подключение еще не создавалось).

## Оптимизация производительности и стабильности

В рамках оптимизации выполнения ресурсоемких операций в сервисе реализованы следующие улучшения:
1. **Изоляция блокирующих операций (ThreadPoolExecutor):** Синхронные вызовы библиотек `impacket`, `smbclient` и `pywinrm` выполняются в выделенном пуле потоков `ThreadPoolExecutor(max_workers=100)`, назначенном исполнителем по умолчанию для asyncio event loop в `worker_main.py`. Это исключает блокирование главного потока asyncio.
2. **Создание сессий WinRM:** Объекты `winrm.Session` создаются по требованию (без кэширования), так как кэширование приводило к проблемам с залипанием сессий при сетевых сбоях (stale connections), а сам объект `winrm.Session` легковесен.
3. **Механизм повторных попыток (Retry):**
   - Для SNMP-запросов и WinRM-подключений настроен автоматический перезапуск операций при временных сетевых или транспортных сбоях (2 попытки с задержкой).
4. **Кодировка вывода PowerShell:** Перед запуском любого PowerShell скрипта через WinRM принудительно задается UTF-8 (`[Console]::OutputEncoding = [System.Text.Encoding]::UTF8;`), что решает проблемы с кодировкой кириллицы в логах.
5. **Предварительная проверка доступности источника:** Перед началом копирования по SMB выполняется асинхронный вызов `smb_executor.check_source_accessible(src)` (внутри `asyncio.to_thread`), что позволяет мгновенно завершить задачу при отсутствии доступа к сетевой папке с драйвером.
6. **Гибкая конфигурация учетных данных SMB:** В `SMBExecutor` поддержана передача опциональных `username` и `password` (по умолчанию используются учетные данные WinRM из конфигурации).
7. **Оптимизация логики стратегий:**
   - Этап опроса (`probe()`) вызывается оркестратором ровно один раз перед WMI Bootstrap. Стратегии считывают статус (`driver_installed`) и параметры драйвера из схемы `PrintJob` и не вызывают `probe()` повторно в методе `execute()`.
   - В USB-стратегии фиксированное ожидание `sleep(5)` заменено циклом динамического опроса (polling) PnP-устройств с таймаутом до 60 секунд. При необходимости инициируется принудительный рескан устройств через `pnputil /scan-devices`.
   - Общие функции (например, `escape_ps`) вынесены в базовый класс `PrinterStrategy` в `strategies/base.py`.
