# Printer Worker Service

Сервис `printer-worker` является частью системы IntraLink и предназначен для автоматизации удаленной установки принтеров на целевых ПК пользователей в домене Active Directory / Windows с использованием WinRM (PowerShell) и SMB.

## Основной функционал

1. **Подписка на события:** Сервис подписан на Redis Pub/Sub канал `intraservice_events` и слушает уведомления о новых задачах и изменениях статусов.
2. **Маршрутизация (Hybrid Router):**
   - **Fast-Track:** Если параметры принтера и ПК четко переданы, они сопоставляются с Базой Знаний (`printers_knowledge_base.json`).
   - **Smart-Track (LLM-as-a-Function):** Если задача написана в свободной форме, используется локальная/облачная языковая модель для извлечения структурированных параметров.
3. **Hardware-First USB-подключение:** При наличии USB-принтера сервис запрашивает Hardware ID устройства по WinRM, сравнивает с базой знаний и автоматически подгружает точечные PnP драйвера.
4. **Управление через WinRM & SMB:**
   - Копирование необходимых драйверов на целевой ПК по SMB (только если драйвер отсутствует).
   - Выполнение команд PowerShell через WinRM для добавления порта, импорта драйвера и регистрации устройства.
5. **Стейт-машина (Orchestrator):** Управляет стадиями установки и пишет человекочитаемые отчеты на каждом шаге обратно в заявку IntraService через Core API.
6. **Целевая фильтрация:** Воркер реагирует только на те заявки, где текущий администратор указан исполнителем в IntraService, игнорируя чужие задачи. Выполняется **ранняя фильтрация** событий прямо из Redis (по ID или логину) до осуществления ресурсоемких HTTP-запросов к API.

## Конфигурация (.env)

Переменные окружения для работы сервиса:

- `REDIS_URL` — адрес сервера Redis (по умолчанию `redis://127.0.0.1:6379/0`).
- `CORE_API_URL` — адрес Core API (по умолчанию `http://127.0.0.1:8000/api/v1`).
- `BOT_API_KEY` — API-ключ для аутентификации в Core API.
- `WINRM_USERNAME` — имя учетной записи администратора в домене / на ПК для подключения WinRM.
- `WINRM_PASSWORD` — пароль администратора для WinRM.
- `WINRM_TRANSPORT` — протокол WinRM (`ntlm`, `kerberos`, `basic`, по умолчанию `ntlm`).
- `LLM_PROVIDER` — провайдер языковой модели (`ollama` или `openai`).
- `LLM_API_URL` — URL адрес API модели.
- `LLM_API_KEY` — API-ключ для внешних сервисов (не требуется для Ollama).
- `LLM_MODEL_NAME` — имя модели для парсинга текста (например, `llama3` или `gpt-4o-mini`).
- `PRINTERS_KB_PATH` — путь к локальному JSON-файлу базы знаний принтеров.
- `PRINT_OUTPUT_DIR` — путь к папке сохранения эмулируемых печатных форм (по умолчанию `./prints`).
- `MAX_CONCURRENT_JOBS` — максимальное число одновременно выполняемых задач (по умолчанию `5`).
- `PRINTER_EXECUTOR_IS_USER_ID` — (Опционально) ID аккаунта исполнителя в IntraService. Если задан, воркер обрабатывает только заявки данного пользователя.
- `PRINTER_EXECUTOR_LOGIN` — (Опционально) Логин аккаунта исполнителя в IntraService. Удобная альтернатива фильтрации по ID.


## Структура папок сервиса

- `/orchestrator` — логика маршрутизации, схемы Pydantic и стейт-машина оркестратора.
- `/strategies` — реестр стратегий и классы для сетевых и USB принтеров.
- `/executors` — низкоуровневое асинхронное выполнение команд (WinRM, SMB).
- `/llm` — абстрактный интерфейс и клиенты для Ollama/OpenAI.
- `/worker_services` — клиент Core API и подписчик Redis.
- `/knowledge_base` — статические файлы справочников и базы знаний.

## Динамическое управление WinRM (WMI Bootstrap)

Для исключения зависимости от настроек групповых политик (GPO), сервис использует механизм динамического управления службой WinRM на удаленных ПК:
1. **Подключение WMI (DCOM/RPC):** Используя библиотеку `impacket`, оркестратор асинхронно подключается к порту 135 целевого хоста.
2. **Активация WinRM:** С помощью вызова `Win32_Process.Create` на хосте запускается PowerShell команда `Enable-PSRemoting -Force`, настраивающая Basic-авторизацию и запуск службы WinRM.
3. **Выполнение команд:** После запуска WinRM все операции диагностики и установки принтера осуществляются через штатный `WinRMExecutor`.
4. **Деактивация WinRM:** По завершении установки (успешной или сбойной) в блоке `finally` оркестратор выполняет удаленную остановку службы WinRM (`Stop-Service WinRM`), возвращая систему в безопасное исходное состояние.

## Отказоустойчивость и безопасность (Orphan Recovery & Блокировки ПК)

Для повышения надежности и устранения уязвимостей в многопользовательской среде внедрены следующие механизмы:
1. **Блокировка по хостам (PC Locks):** Чтобы предотвратить одновременное выполнение нескольких задач установки на одном и том же компьютере (что может привести к конфликту WinRM/WMI сессий), все WMI/SMB-операции установки выполняются под асинхронной блокировкой `asyncio.Lock` для конкретного `target_pc`.
2. **Восстановление сиротских задач (Orphan Recovery):** При перезапуске микросервиса `printer-worker` автоматически запускается фоновое сканирование состояния в Redis:
   - Задачи в незавершенных статусах (`PROBING/ROUTING/PARSING/COPYING/INSTALLING/VERIFYING`), во время которых WinRM-порт мог остаться открытым, переводятся в статус `FAILED`, при этом для их хостов принудительно вызывается отключение WinRM (`wmi.disable_winrm()`), а в IntraService отправляется статус «Требует уточнения» (35) с комментарием о сбое.
   - Задачи в статусе `WAITING_APPROVAL` сбрасываются в `FAILED` без отключения WinRM (так как подключение еще не создавалось).
