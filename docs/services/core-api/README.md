# Core API Service

Микросервис `core-api` является центральным звеном системы IntraLink. Он выполняет функции шлюза (Gateway), а также фонового воркера для мониторинга событий IntraService.

## Архитектура воркера и AI-классификатора

Фоновый воркер `worker.py` опрашивает API IntraService от имени сервисного аккаунта, отслеживая новые и измененные заявки.

### 1. Синхронизация каталога услуг
Для автомаршрутизации воркер ежедневно опрашивает IntraService и кэширует плоский список каталога услуг в Redis с ключом `worker:service_catalog` и TTL 24 часа. Это позволяет классификатору мгновенно получать доступ к полному списку доступных разделов без лишних API-запросов.

### 2. AI-классификатор и автоотмена заявок (`ai_classifier.py`)
При появлении новой заявки воркер пропускает ее через `AIClassifier` для валидации выбранного пользователем раздела:
* **RAG-поиск:** Классификатор ищет похожие исторические кейсы в ChromaDB (коллекция `intraservice_kb`).
* **Анализ через LLM:** Модель (по умолчанию `gemini-2.5-flash`) получает текущую заявку, похожие кейсы и полный каталог услуг.
* **Принятие решения:**
  * Если раздел выбран верно -> `action="none"`, заявка обрабатывается в обычном режиме.
  * Если раздел выбран ошибочно -> `action="redirect"`. В этом случае воркер:
    1. Добавляет в IntraService публичный комментарий с указанием верного раздела.
    2. Переводит заявку в статус «Отменена» (ID 30).

### 3. База знаний RAG
Для наполнения ChromaDB используется скрипт `core-api/scripts/build_rag_dataset.py`, который:
* Собирает закрытые (ID 28) и отмененные (ID 30) заявки.
* Извлекает из них структурированную информацию (Проблема -> Решение) через LLM.
* Сохраняет записи в ChromaDB с расширенными метаданными (`service_name`, `service_id`, `status_name`).

## Конфигурация и запуск

Все настройки хранятся в переменных окружения и файле `.env` (описаны в `core-api/app/config.py`).
Поведение воркера определяется интервалом опроса `POLLING_INTERVAL`.
