# ADR 0006: CaseFrame, прикладные процессы и технические capabilities

- **Статус:** Accepted / implementation pending
- **Дата:** 2026-09-27
- **Авторы:** IntraLink Core Architecture Team
- **Заменяет:** объект маршрутизации и ограничение роли LLM из разделов 2.1 и 2.3 ADR 0005
- **Сохраняет:** доказательную модель, DLP, immutable provenance, fail-closed policy, операторское подтверждение и безопасное исполнение ADR 0005

---

## 1. Контекст

Текущий `scenario_key` смешивает разные доменные сущности:

- прикладной процесс (`account_create`);
- запрос доступа (`grant_wlan`);
- техническую операцию (`printer_spooler_restart`, `default_printer_fix`);
- симптом и диагностическую ветку (`offline_host`);
- результат обработки (`service_redirect`);
- способ формирования ответа (`rag_consultation`).

Из-за этого маршрутизатор выбирает между несопоставимыми классами. Например, исходная фраза «принтер не печатает» доказывает наличие инцидента печати, но не доказывает необходимость перезапуска Spooler. Причиной могут быть очередь, неверный принтер по умолчанию, драйвер, сеть, приложение или физическое состояние устройства.

Плоская классификация также не описывает заявки с несколькими намерениями, не отделяет понимание обращения от технической диагностики и создаёт некорректный ground truth для обучения.

Проект ещё не находится в production. Поэтому принято исправить доменную модель до накопления зависимых данных и не сохранять ошибочные контракты ради обратной совместимости.

---

## 2. Решение

### 2.1. Разделить пять уровней

```text
TicketSnapshot
    -> CaseFrame
    -> Evidence Routing / CaseDecision
    -> WorkflowPlan
    -> Readiness + Diagnostics
    -> ActionPlan
    -> Operator Approval
    -> ActionCommand / Capability Executor
```

1. **CaseFrame** — структурированное описание того, что известно из заявки.
2. **CaseDecision** — доказательное решение о типе обращения, а не о технической команде.
3. **WorkflowPlan** — прикладной процесс обработки заявки первой линией.
4. **ActionPlan** — проверенный план из разрешённых технических действий.
5. **ActionCommand** — одна исполнимая и проверяемая capability.

Результат обработки хранится отдельно как `Disposition`: `execute`, `clarify`, `consult`, `redirect` или `manual`.

### 2.2. CaseFrame является открытой моделью ситуации

`CaseFrame` содержит:

- один или несколько доменов;
- первичное и дополнительные намерения;
- наблюдаемые симптомы;
- ожидаемый пользователем результат;
- извлечённые сущности;
- отрицания и противоречия;
- ограничения и контекст;
- ссылки каждого утверждения на исходные фрагменты текста;
- неизвестные либо конфликтующие факты.

`CaseFrame` не разрешает выполнение и не подменяет immutable `TicketSnapshot`. Он является версионированной интерпретацией снимка с полным provenance.

Множественные намерения не сворачиваются принудительно в один класс. Policy может создать составной workflow, предложить разделение заявки либо передать решение оператору.

### 2.3. Начальная таксономия типов обращений

- `printer_connection_request`;
- `printing_incident`;
- `wireless_access_request`;
- `employee_onboarding`;
- `access_revocation_request`;
- `workstation_unavailable_incident`;
- `knowledge_request`;
- `non_it_request`;
- `unknown`.

Таксономия версионируется и может расширяться. Неизвестное обращение не должно насильно преобразовываться в ближайший известный тип.

### 2.4. Workflow и capabilities

Workflow описывает бизнес-процесс первой линии: сбор фактов, уточнения, диагностику, допустимые переходы, требования к подтверждению и конечные результаты. Workflow может быть композиционным и использовать несколько capabilities.

Capability является узкой технической операцией с типизированными параметрами, preflight, политикой идемпотентности и проверяемым результатом. Capability не участвует в intake-классификации.

Текущие модули преобразуются следующим образом:

| Текущий ключ | Целевая роль |
|---|---|
| `install_printer` | capability `install_printer` внутри workflow подключения принтера |
| `printer_spooler_restart` | capability `restart_spooler` внутри workflow инцидента печати |
| `default_printer_fix` | capability `set_default_printer` внутри workflow инцидента печати |
| `grant_wlan` | workflow предоставления WLAN-доступа и capability `add_wlan_group_member` |
| `account_create` | workflow онбординга и capability `create_ad_user` |
| `account_lock` | workflow отзыва доступа и capability `disable_ad_user` |
| `offline_host` | workflow диагностики недоступного рабочего места |
| `service_redirect` | disposition `redirect` |
| `rag_consultation` | disposition `consult` и механизм подготовки ответа |

Существующие LDAP, WinRM и диагностические адаптеры сохраняются как исполнители capabilities, если они удовлетворяют контрактам безопасности.

### 2.5. Распределение роли LLM

LLM используется в четырёх ограниченных ролях:

1. **Structured extraction:** формирует черновик `CaseFrame` из санитизированного текста и обязан привязать извлечённые утверждения к исходным spans.
2. **Grey-zone verification:** проверяет не более трёх кандидатов `CaseDecision`, уже найденных доказательным каскадом.
3. **Clarification drafting:** превращает детерминированный список `missing_facts` в понятный вопрос без изменения требуемых фактов.
4. **Constrained planning and response drafting:** предлагает план только из переданного каталога workflow-шагов/capabilities и формулирует ответ только по подтверждённым результатам.

LLM не может:

- зарегистрировать новую capability;
- разрешить инфраструктурную мутацию;
- обойти policy, readiness, preflight или подтверждение оператора;
- объявить техническое действие успешным;
- закрыть заявку на основании собственного текста;
- превратить неоднозначность или деградацию в принудительный выбор.

Policy Engine остаётся владельцем допустимых переходов и разрешений. Executor остаётся владельцем факта выполнения. В режиме `ASSISTED` оператор подтверждает итоговый `ActionPlan`. Будущий `FULL_AUTO` допускается только для заранее утверждённых детерминированных ветвей workflow, а не для свободного LLM-плана.

### 2.6. Пример процесса печати

`printer_connection_request` запускает workflow подключения: сбор данных о ПК и принтере, определение типа подключения, `install_printer`, проверка результата.

`printing_incident` сначала запускает диагностику. В зависимости от подтверждённых фактов ActionPlan может включать `restart_spooler`, `clear_print_queue`, `set_default_printer`, переустановку принтера, сетевую проверку либо ручную аппаратную диагностику.

Фраза пользователя «принтер не печатает» сама по себе никогда не является достаточным основанием для `restart_spooler`.

## 3. Feedback-loop и обучение

Движок не изменяет поведение online после единичного операторского действия. Под «обучением» понимается контролируемый versioned цикл:

```text
operator feedback
    -> sanitized versioned dataset
    -> replay and error analysis
    -> profiles / extraction / policy / workflow update
    -> champion-challenger shadow
    -> explicit version promotion
```

Feedback фиксируется отдельно для:

- коррекции `CaseDecision`;
- коррекции извлечённых фактов;
- изменения `WorkflowPlan` или `ActionPlan`;
- подтверждённого результата исполнения.

До накопления достаточной разметки обучение означает калибровку профилей, примеров, правил серой зоны и workflow. В дальнейшем обученный classifier/reranker может быть добавлен только как ещё один provider доказательств. Он не становится владельцем решения.

Каждая новая версия обязана проходить закрытый replay и read-only shadow. Данные оператора дедуплицируются, проходят санитарную проверку и не применяются автоматически.

## 4. Dataset и метрики

Создаются два независимых набора:

1. **Intake Routing Dataset:** исходный доступный оператору снимок -> эталонный `CaseDecision`.
2. **Action Selection Dataset:** подтверждённый CaseFrame, результаты уточнений и диагностики -> допустимый `ActionPlan`.

Закрывающие комментарии, итоговый исполнитель и результаты поздней диагностики не включаются во вход intake-набора. Это предотвращает утечку будущего.

Качество измеряется раздельно:

- понимание обращения и полнота CaseFrame;
- precision/coverage CaseDecision;
- качество безопасного `ambiguous`/`unknown`;
- корректность `missing_facts`;
- корректность предложенного ActionPlan;
- подтверждённый результат исполнения.

---

## 5. Переход

Так как production-совместимость не требуется, используется clean break:

1. Зафиксировать CaseFrame, CaseDecision, WorkflowPlan, ActionPlan, ActionCommand и Disposition как разные контракты.
2. Заменить routing-профили технических сценариев профилями типов обращений.
3. Перенести существующие технические адаптеры в capability registry.
4. Вынести `redirect` и `consult` из scenario registry в dispositions.
5. Пересобрать ещё не развёрнутые routing-миграции вместо добавления переходных колонок и dual-write.
6. Удалить старый `ScenarioRouter`, смешанные `scenario_key` и совместимые fallback-ветви после переноса тестов.
7. Обновить UI: отдельно показывать тип обращения, workflow, недостающие факты и технические действия.
8. После стабилизации контрактов подготовить два dataset и выполнить offline replay, затем live shadow без мутаций IntraService.

Существующие evidence, DLP, feedback, approval, lease, idempotency и execution-result механизмы переиспользуются, но привязываются к правильному уровню модели.

## 6. Инварианты принятого решения

- Intake Router не выбирает техническую capability.
- Диагностическое предположение не считается доказанным результатом.
- LLM предлагает, но не разрешает и не подтверждает выполнение.
- Любая инфраструктурная мутация создаётся только из валидированного ActionPlan.
- Неизвестные и многозначные случаи сохраняются как таковые.
- Feedback не изменяет production-поведение без replay, shadow и явного продвижения версии.
- Dataset размечает только информацию, доступную на соответствующем этапе процесса.

---

## 7. Последствия

Положительные последствия:

- корректная доменная граница между обращением, процессом и технической операцией;
- поддержка нескольких намерений и композиционных workflows;
- объяснимое и безопасное использование LLM;
- возможность независимо улучшать маршрутизацию, планирование и исполнение;
- пригодный для обучения ground truth.

Стоимость решения:

- потребуется заменить текущие routing-профили и API/UI-проекции;
- старые метрики по `scenario_key` нельзя напрямую сравнивать с новой таксономией;
- до подготовки dataset качество новой модели нельзя считать доказанным;
- свободный LLM-agent намеренно не поддерживается.
