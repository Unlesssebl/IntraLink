## 1. Глоссарий сущностей Helpdesk и жизненный цикл заявок

### 1.1. Сущность «Заявка» (Task / Ticket)
Основная операционная единица IntraService. 

Каноническая матрица статусов:
| ID | Название в IntraService | Канонический статус v2 | Тип UI-токена | Описание и бизнес-смысл |
| :---: | :--- | :--- | :--- | :--- |
| **1** | Новая | `new` | `info` (синий, pulse) | Заявка зарегистрирована заявителем, ещё не взята инженером. |
| **2** | В работе | `in_progress` | `warning` (янтарный) | Инженер принял тикет в работу (`take`), назначен исполнитель. |
| **3** | Выполнена | `resolved` | `success` (изумрудный) | Работы завершены, заявителю направлен обязательный отчёт о решении. |
| **4** | Закрыта | `closed` | `neutral` (серый) | Тикет подтвержден заявителем или автоматически закрыт регламентом. |
| **5** | Отклонена | `rejected` | `danger` (розовый) | Заявка отклонена диспетчером или куратором (нецелевое обращение). |
| **6** | Приостановлена | `suspended` | `neutral` (серый) | Ожидание поставки запчастей, ответа заявителя или оборудования. |
| **7** | Переоткрыта | `reopened` | `warning` (янтарный, pulse)| Заявитель вернул тикет на доработку после решения. |
| **30** | Отменена | `cancelled` | `danger` (розовый) | Заявка отменена как дубликат или для переподачи в корректный сервис. |

### 1.2. События жизненного цикла (TaskLifetimes)
* События аудита **не содержат обязательного ID** со стороны IntraService.
* Дата передаётся в поле `Date`, автор — в поле `Editor`.
* При маппинге в DTO (`TaskLifetimeEventDTO`):
  * `created`: маппится из `Date` (ISO 8601).
  * `user_name`: маппится из `Editor`.
  * `is_private`: маппится из `IsPrivateComment` (служебная заметка, видимая только инженерам).

## 2. Операторские действия и валидации (Бизнес-правила донора v1)

При проектировании интерфейса оператора (`ActionDock`) строго действуют правила, перенесённые из проверенной реализации v1 (`intra-web` / `helpdesk-cli`):

### 2.1. Взятие в работу (`take`, Alt+1)
* **Переход:** Статус `1` ➔ `2` («В работе»).
* **Исполнитель:** В поле `ExecutorIds` передаётся `user_id` авторизованного оператора.
* **Идемпотентность:** Если тикет уже находится в статусе 2, действие визуально деактивировано (`disabled`).

### 2.2. Решение заявки (`resolve`, Alt+2)
* **Переход:** Любой активный статус ➔ `3` («Выполнена»).
* **Критический инвариант:** **Запрещено закрывать заявку со скрытым служебным комментарием (`is_private: true`)!**  
  *Заявитель обязан получить публичный ответ с описанием решения. Если выбран режим «Служебная заметка», кнопка «Решено» блокируется с подсказкой.*
* **Обязательность:** Пустой комментарий при решении недопустим.

### 2.3. Отмена как дубликат (`cancel_duplicate`, Alt+3)
* **Переход:** Статус ➔ `30` («Отменена»).
* **Связывание:** Обязательно указывается Master Ticket ID (`master_task_id`).
* **Формат ответа заявителю:**
  > *«Заявка закрыта как дубликат обращения #{master_id}. Дальнейшие работы ведутся в основной заявке #{master_id}: https://servicedesk-pub.corporate.loc/Task/View/{master_id}»*

### 2.4. Регламентное перенаправление (`redirect_cancel`, Alt+4)
* **Переход:** Статус ➔ `30` («Отменена»).
* Подробности логики описаны в Разделе 3.

## 3. Спецификация каталога услуг и инвариант перенаправления

### 3.1. Ограничение контроллера сервисов IntraService API
* Эндпоинт `/api/service` работает **строго в режиме чтения (`GET`)**.
* `PUT /api/task/{id}` **не принимает изменений `ServiceId`** (попытка передать `ServiceId` игнорируется API либо вызывает ошибку).

### 3.2. Логика перенаправления
Так как перенести тикет между сервисами программно невозможно:
1. Тикет в текущем сервисе переводится в статус **`30` («Отменена»)**.
2. В историю добавляется комментарий с системным префиксом:
   `[Перенаправлено в сервис: {Service_Name}]`
3. **Запрет на дезинформацию заявителя:**  
   Строго запрещено писать: *«Заявка перенаправлена, ожидайте ответа специалистов»*. По закрытой заявке специалисты никогда не ответят.
4. **Обязательный регламентный шаблон ответа заявителю:**
   > *«Заявка отменена, т. к. создана не в подходящем разделе каталога.\nТребуется оставить заявку в подходящем разделе: «{Service_Name}».\nЕсли у вас остались вопросы, пожалуйста, напишите в комментариях к этой заявке.»*

## 4. Инварианты сетевой диагностики (Workstations)

### 4.1. Формат и эталонные контракты
Сетевая диагностика рабочей станции выполняется по трём векторам:
1. **ICMP Ping:** таймаут 400 мс (Fail-Fast).
2. **DNS-резолвинг:** с автоматической подстановкой доменного суффикса `.corporate.loc`.
3. **TCP Port Probes:** порты `445` (SMB) и `5985` (WinRM), таймаут 300 мс.

### 4.2. Контракт DTO бэкенда (`HostDiagnosticDTO`)
```json
{
  "hostname": "WKS-1234",
  "ip_address": "192.168.10.45",
  "is_online": true,
  "avg_rtt": "14ms",
  "ports": {
    "smb_445": true,
    "winrm_5985": false
  },
  "cached": false
}
```

### 4.3. Правила обработки на фронтенде:
* **Нормализация хоста:** Имя ПК перед отправкой очищается от составных элементов: `host.split(/[,;\s/]/)[0].trim()`.
* **Пинг (RTT):** Отображается значение `data.avg_rtt`. Если `is_online: false`, выводится `Down`, а не `0ms`.
* **Порты:** Статус открытости считывается строго через `data.ports?.["smb_445"]` и `data.ports?.["winrm_5985"]`. Запрещено использовать выдуманные поля `smb_port_open`.
* **Ошибки:** При сетевом сбое поповер показывает явную плашку ошибки с кнопкой «Попробовать снова».

## 5. Инварианты Базы знаний (RAG) и AI-триажа

### 5.1. Семантический поиск (`POST /api/v2/kb/search`)
* **Вход:** `SearchQuery`: `{ "query": string (>=2 chars), "limit": int, "min_similarity": float (дефолт 0.60) }`.
* **Выход:** `SearchResponse`: `{ "query": string, "total_found": int, "items": SearchResultItemDTO[] }`.
* **Фронтенд-инвариант:** Запрещено ожидать «голый» массив. Результаты всегда извлекаются из `res.items`.

### 5.2. Генерация решения RAG (`POST /api/v2/kb/ask`)
* **Вход:** `AskQuery`: `{ "query": string (>=3 chars), "max_context_items": int }`.
* **Выход:** `SolutionResponse`: `{ "answer": string, "context_used": SearchResultItemDTO[], "cited_tasks": int[], "confidence": float, "model_used": string }`.
* **Фронтенд-инвариант:** Источники решений извлекаются из поля `context_used` (не `sources`).

### 5.3. Триаж и анализ очереди (`POST /api/v2/triage/analyze/{id}`)
* **Выход:** `TriageAnalysisResponse`: `{ "audit_id": UUID, "ticket_id": int, "decision": TriageDecisionDTO, "model_used": string }`.
* **Дубликаты:** Поле `decision.is_duplicate: bool` и `decision.master_ticket_id: Optional[int]`.
* **Пакетный анализ очереди:** `POST /api/v2/triage/batch-analyze` принимает `{ "filter_id": 984, "limit": 20 }`.

## 6. Политика честности состояний и Zero-Stub Policy

1. **Запрет маскировки аварий:**  
   Если бэкенд `/api/v2/health` возвращает ошибку или недоступен по сети, индикатор состояния обязан отображать красный статус **`Offline` (`variant="danger"`)**. Статус `Standby` допустим только при явном штатном прогреве/проверке.
2. **Запрет на фиктивные поля в UI:**  
   Любое поле данных в интерфейсе TypeScript (`web/src/shared/api.ts`) обязано иметь прямое соответствие в Pydantic v2 DTO бэкенда. Запрещено создавать заглушки-иллюзии, не имеющие реального источника данных.
3. **Запрет на блокирующие `alert()`:**  
   Все системные уведомления, ошибки и подтверждения выполняются через компонент тостов `ToastProvider` (`useToast()`).
4. **Авторизация медиа-вложений:**  
   URL картинок и вложений обязаны содержать токен аутентификации `?auth_b64=...`, предотвращая ошибку 401 при отрисовке через браузерные теги `<img>`.

## 7. Двухконтурная модель автоматизации (Полуавтомат vs Автомат)

Подробная архитектурная спецификация зафиксирована в [v2-automation-pipeline.md](file:///docs/architecture/v2-automation-pipeline.md).

1. **Шлюз релевантности сервиса (Первая линия):**  
   Любая обработка тикета начинается с проверки соответствия разделу каталога услуг. Если раздел не релевантен — немедленная отмена по регламенту (Статус `30` «Отменена») с указанием корректного сервиса. Сценарии решения не запускаются.
2. **Полуавтомат (Ко-пилот / Human-in-the-Loop):**  
   Активируется, если исполнитель — инженер или заявка не назначена. Система извлекает сущности (ПК, IP, логин), подбирает сценарий и предлагает оператору в ActionDock готовую кнопку «Выполнить». Запуск происходит строго после ручной валидации параметров инженером.
3. **Автомат (Автопилот / Autonomous Execution):**  
   Активируется при назначении **сервисной учетной записи** в поле `ExecutorIds`. Является системным мандатом на автономное исполнение сценария через Worker без участия человека.
4. **Единый движок сценариев:**  
   Код сценариев (`install_printer`, `ad_password_reset` и др.) строго един для обоих контуров. Различается лишь источник валидации параметров (оператор в UI vs строгие предикаты схемы в фоне).
