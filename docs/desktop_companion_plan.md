# IntraLink Desktop Companion — архитектурный blueprint

## Решение

`IntraLink Desktop Companion` — лёгкий Windows-клиент, который дополняет
`intra-web`, но не заменяет его. Его задача — убрать переключение между окнами
и ручные повторяющиеся действия во время работы оператора. Он запускает только
безопасные локальные интеграции рабочего места инженера: LiteManager, DameWare,
RDP, сетевые пути, уведомления и открытие вложений.

Он **не** хранит доменные секреты, не подключается к Redis и не исполняет
PowerShell произвольного содержания. Все инфраструктурные действия продолжают
проходить через Core API и `execution-worker`.

```text
intra-web ── HTTPS ──> Core API ── Redis Streams ──> execution-worker ──> AD / WinRM
     │
     └── Desktop bridge ──> разрешённые программы и возможности Windows
```

## Почему Tauri 2

Для существующего React + TypeScript интерфейса Tauri позволяет переиспользовать
компоненты и собрать небольшой нативный shell. Rust-слой должен оставаться
минимальным: проверка входных параметров, запуск разрешённых приложений,
уведомления и безопасный доступ к файлам. Доступ к системным возможностям
включается только через capability manifest с конкретными путями и аргументами.

## Ценный операторский сценарий

### "Начать работу по заявке"

Оператор нажимает одну кнопку в карточке заявки и получает рабочий контекст:

1. Результат уже существующей диагностики из Core API: DNS, Ping, SMB, WinRM.
2. Рекомендованный канал подключения: автоматизация через worker, LiteManager,
   DameWare или RDP.
3. Запуск разрешённого локального клиента для выбранного хоста.
4. Окно фокуса: номер заявки, SLA-таймер, заявитель, хост, последние комментарии
   и быстрый возврат в `intra-web`.

Это не новый механизм исполнения. Companion только сокращает путь от решения
Core API до удобного действия оператора.

## MVP: одна законченная ценность

### "Подключиться к хосту"

В карточке заявки появляются действия:

1. **LiteManager**: `romviewer.exe /connect:<host>`.
2. **DameWare**: `dwrcc.exe -c: -m:<host>`.
3. **RDP**: `mstsc.exe /v:<host>`.

Desktop bridge принимает только нормализованное имя хоста или IP. Перед запуском
он проверяет формат, наличие разрешённого исполняемого файла и показывает
понятную ошибку с вариантом fallback. В браузере те же кнопки сохраняют текущее
поведение — копирование команды в буфер.

Критерий готовности MVP: оператор открывает удалённое подключение из заявки
одним нажатием, а web-панель полностью работает без установленного Companion.

## Границы пилота

В первый релиз входят только LiteManager, DameWare, RDP, локальная настройка
путей, одноразовый deep link и audit запуска. Web-панель остаётся источником
очереди, SLA, диагностики, истории, вложений, шаблонов и handoff.

После успешного недельного пилота допускается только следующий инкремент —
нативные уведомления о HITL и результате job через одноразовое сопряжение
устройства с оператором. Dashboard, учёт времени, активные сессии, отдельный
паспорт ПК и локальная обработка вложений не входят в roadmap Companion.

## Масштабируемость без тяжёлой архитектуры

### 1. Typed bridge

UI не обращается к Tauri API напрямую. Он использует один интерфейс:

```ts
interface DesktopBridge {
  launchRemoteClient(input: { client: 'litemanager' | 'dameware' | 'rdp'; host: string }): Promise<void>;
}
```

Web-реализация выпускает одноразовый `intralink://` link и сохраняет копирование
готовой команды как fallback. Tauri-реализация принимает только этот link и
вызывает узкий Rust launcher. Новая нативная возможность добавляется отдельным
методом bridge, а не общим `runCommand`.

### 2. Реестр возможностей

В пилоте allowlist намеренно статичен в Rust-коде: `litemanager`, `dameware`,
`rdp` и фиксированные аргументы. Core API выдаёт разрешение только на один из
этих клиентов и не передаёт произвольные команды для исполнения.

### 3. Разделение контуров

| Контур | Ответственность |
| --- | --- |
| Web / Companion | Интерфейс, локальные удобства, deep links |
| Core API | Авторизация, аудит, политика, бизнес-команды |
| execution-worker | Доменные операции и подтверждённое исполнение |

Поэтому рост числа операторов не увеличивает число устройств с AD-привилегиями,
а добавление нового клиента удалённого доступа не затрагивает Command Bus.

## Границы: как избежать дублирования и конфликтов

| Функция | Источник истины | Роль Companion |
| --- | --- | --- |
| Очередь, статусы, SLA, шаблоны | Core API и intra-web | Открывает контекст и уведомляет |
| Диагностика целевого хоста | Core API / execution-worker | Запрашивает и отображает результат |
| AD, Wi-Fi, принтеры, WinRM | execution-worker | Передаёт команду через API и показывает прогресс |
| LiteManager, DameWare, RDP | Companion | Запускает локально разрешённый клиент |
| HITL | Core API / Command Bus | Показывает нативное уведомление и deep link |
| Вложения | Core API | Скачивает и открывает локальную копию |

Companion не создаёт собственных статусов заявок, не принимает решений Rule
Engine и не проводит повторную диагностику как источник истины. Например,
«умный выбор подключения» использует результат диагностики Core API, а не
самостоятельно решает, как изменять инфраструктуру.

## Безопасность и эксплуатация

* Подписанный MSI, предсказуемый канал обновлений и rollback на предыдущую версию.
* Capability allowlist; запрет shell, произвольного PowerShell и произвольного пути.
* В запросы к Core API не добавляются постоянные доменные учётные данные.
* Аудитируютcя intent запуска, id заявки, host, оператор и результат запуска;
  секреты и параметры авторизации не логируются.
* При отсутствии Companion `intra-web` остаётся полностью функциональным.

## Порядок реализации

1. Добавить `DesktopBridge` и browser fallback в `intra-web`.
2. Создать Tauri shell с одной capability `launchRemoteClient`.
3. Пилотировать LiteManager на 2–3 рабочих местах инженеров.
4. Добавить DameWare/RDP и диагностическую страницу Companion.
5. После телеметрии использования решить, нужны ли tray, вложения и deep links.
