# Настройка и запуск

Термин `assistant` означает сервисную учётную запись IntraService из админ-панели («Сервисный аккаунт IntraService»), а не обязательный логин. Сервер проверяет подключение, определяет `user_id` и сохраняет логин, зашифрованный пароль, URL и подтверждённый ID в PostgreSQL. Redis используется только как восстанавливаемый рабочий кэш.

> Неподдерживаемость не ведёт к отмене. Неверный раздел обрабатывается редиректом с комментарием и ссылкой на правильный сервис. Неоднозначный редирект и инфраструктурная ошибка приостанавливают цикл без изменения заявки.

Автопилот по умолчанию выключен. Сначала примените миграции к чистой PostgreSQL командой `alembic upgrade head` и убедитесь, что API, Poller, `command-worker`, Redis и Windows execution-worker доступны.

Текущая эксплуатационная конфигурация — только полуавтоматическая: рабочие сценарии имеют режим `ASSISTED`, а `ad_password_reset` — `DISABLED`. Механизм `FULL_AUTO` и его переключатель не удалены, но активных полностью автоматических сценариев сейчас нет. Штатный поток первой линии: оператор проверяет план и параметры → назначает сервисную учётную запись исполнителем → подтверждает команду → worker исполняет выбранный сценарий без повторной классификации.

Poller обходит активные циклы устойчивыми страницами. Размер страницы задаётся `AUTOPILOT_POLL_BATCH_SIZE` (по умолчанию `200`), число параллельных сверок — `AUTOPILOT_MAX_CONCURRENCY` (по умолчанию `5`). Увеличивать параллелизм следует только после проверки лимитов IntraService.

Настройте и проверьте сервисную учётную запись в Web UI. Проверьте ID статусов IntraService: открыта `31`, требует уточнения `35`, в работе `27`, выполнена `29`, отменена `30`, закрыта `28`. Новый цикл запускается только при назначении подтверждённой сервисной учётной записи исполнителем заявки в статусе `31`, включённом глобальном автопилоте и наличии включённого сценария для сервиса.

Перед включением настройте и активируйте в PostgreSQL шаблоны:

- `printer_ip_clarify` и `pc_offline` со статусом `35`;
- `ticket_timeout_cancel`, `ticket_not_relevant`, `autopilot_unsupported_cancel` и `autopilot_execution_failed_cancel` со статусом `30`;
- `resolved_standard` со статусом `29`.

Web UI покажет отсутствующий, пустой, некорректный по статусу или переменным шаблон и не позволит включить автопилот. Тексты отмены изменяйте через существующее административное управление шаблонами.

В политиках Command API выберите режим для `diagnose_host`, `install_printer` и `apply_triage`. Значение `confirm` оставляет изменяющую команду в ожидании инженера; `auto` разрешайте отдельно только после проверки Windows-исполнителя и шаблонов. Автоматический повтор установки принтера и обновления заявки запрещён независимо от режима policy.

После проверки откройте настройки Web UI и включите общий выключатель. Назначения, замеченные во время выключения, сохраняются и продолжатся только после повторной проверки статуса и назначения Poller-ом.

Состояние видно в очереди и карточке заявки. При `system_error` проверьте фактический результат последней команды и причину в истории, затем явно возобновите цикл либо переключите его в ручной режим. Приостановленный инженером цикл общий выключатель не возобновляет. Завершение и отмена оставляют `assistant` среди исполнителей.

## Контроль пилота

До пилота выполните [staging-приёмку](staging-acceptance.md). Во время пилота контролируйте `/metrics`:

- неопубликованный outbox старше 60 секунд требует проверки command-worker и Redis;
- outbox старше 5 минут либо рост очереди служит основанием выключить автопилот;
- цикл в `running` или `waiting_approval` без движения более 15 минут требует разбора;
- `waiting_answer` может оставаться активным до заданного срока 72 часа;
- каждый новый `system_error` разбирается до повторного включения изменяющих действий в `auto`.

Начальная политика `install_printer` и `apply_triage` для пилота — `confirm`. Один необъяснённый повтор установки, комментария, трудозатрат или смены статуса останавливает пилот.

## Новая база данных

Перенос и совместимость со старой БД не требуются. В течение пилота историю `TicketRun`, команд и событий не удалять автоматически. Хранить её не менее 365 дней; перед последующим сокращением срока сначала сделать проверяемый backup через `scripts/backup-postgres.ps1` и проверить восстановление командой `scripts/verify-postgres-restore.ps1`.

## Служебные скрытые комментарии автопилота (`IsPrivateComment`)

Для обеспечения полной прозрачности жизненного цикла автоматической обработки без визуального шума для заявителей реализован механизм автоматических служебных комментариев непосредственно внутри заявки IntraService с флагом `IsPrivateComment = true`.

### 1. События жизненного цикла (Триггеры)
Служебные комментарии отправляются точечно ровно в трех ключевых точках жизненного цикла заявки:
1. **Старт (`on_start`):** заявка принята в автономную обработку. Фиксируется целевая рабочая станция, IP-адрес и сетевой отклик (RTT).
2. **Пауза или ошибка (`on_pause_or_error`):** переход в статус 35 («Требует уточнения»), ручной пересмотр («Manual Review») или сбой воркера. Инженеру сообщается точная причина и текст системной ошибки для оперативного вмешательства.
3. **Успех (`on_complete`):** сценарий успешно завершён, верифицирован и заявка переведена в финальный статус (29/30). Фиксируется время выполнения в секундах.

### 2. Уровни глубины отчёта
* **Прикладной (`applied`, по умолчанию):** 1–2 лаконичных предложения на русском языке с понятным статусом для дежурной смены первой линии:
  - `[IntraLink Autopilot: Старт]` Заявка принята в автоматическую обработку по сценарию «Установка сетевого принтера». Целевой ПК: `NTEMW0047`, IP: 10.244.12.50.
  - `[IntraLink Autopilot: Пауза]` Сценарий «Установка сетевого принтера» приостановлен: Сетевой порт SMB 445 недоступен или ПК выключен.
  - `[IntraLink Autopilot: Успех]` Сценарий «Установка сетевого принтера» успешно завершён. Время выполнения: 4.2 сек.
* **Технический (`technical`):** структурированный JSON Trace в блоке Markdown ````json ... ```` с дампами `run_id`, `task_id`, `facts`, `target_host`, `execution_proof` и временными метками для детального аудита.

### 3. Двухуровневое управление и переопределение
* **Глобально (Web UI ➔ Настройки):**
  - Главный тумблер: `[ Включены / Выключены ]`
  - Глубина по умолчанию: `[ Прикладной / Технический ]`
* **Точечно для каждого сценария:**
  - Селектор режима в строке сценария:
    - `Отчёт: авто` (`inherit`) — наследовать глобальные настройки;
    - `Отчёт: прикладной` (`applied`) — принудительно краткий статус;
    - `Отчёт: trace` (`technical`) — принудительно технический JSON-дамп;
    - `Отчёт: выкл` (`disabled`) — отключить отправку комментариев для данного сценария.

### 4. Безопасность и Zero Trust DLP
* **Рекурсивная маскировка секретов:** любые пароли, токены, ключи сессий, заголовки `Bearer` и `Basic`, а также поля `password`, `secret`, `token`, `auth_b64` автоматически замещаются строкой `***REDACTED***` до отправки в IntraService API.
* **Защита от превышения лимитов:** размер комментария жестко ограничен 3500 символами с автоматическим закрытием блоков кода.

### 5. Поведение в режимах развёртывания (Rollout Modes)
* **`active`:** комментарии отправляются в штатном режиме.
* **`shadow`:** отправка комментариев в IntraService полностью блокируется во избежание дезинформации операторов при теневом аудите.
* **`canary`:** комментарии отправляются только для тикетов, попавших в заданный процент `canary_percent`.

### 6. Отказоустойчивость (Fault Tolerance)
Сетевые сбои, таймауты или недоступность API IntraService при отправке скрытого комментария логируются как предупреждения (`WARNING`) и **не прерывают** выполнение бизнес-логики сценария или инфраструктурных команд на рабочих станциях.
