# IntraLink: ручной режим и автопилот

Статус: концепция управления двумя режимами. Продуктовые роли Rule Engine, RAG и AI, единый путь заявки и целевой Web UI заданы в [единой концепции продукта](product-concept.md). Наличие целевых требований не означает завершённости реализации; расхождения перечислены в [карте доведения](concept-alignment.md).

## Назначение

IntraLink поддерживает два полноценных режима с общими командами, правилами доступа и историей обработки. В ручном режиме инженер изучает заявку, использует диагностику и базу знаний, выбирает действия, редактирует ответ и завершает работу. В автопилоте сервер проходит разрешённый сценарий самостоятельно и проверяет результат.

Единственный развиваемый пользовательский интерфейс этапа — Web UI. Backend и исполнители изменяются в необходимом объёме. Назначение `assistant` в IntraService остаётся внешним триггером. Работа сервера не зависит от открытой вкладки. Telegram, CLI и MCP не расширяются и не удаляются из-за смены приоритета.

## Управление

Назначение сервисной учётной записи `assistant` открытой заявке передаёт её включённому автопилоту. Одно назначение создаёт один цикл. Новые автоматические циклы запускаются только из статуса «Открыта»; продолжение цикла возможно в других незавершённых статусах.

Инженер может самостоятельно работать с заявкой, приостановить автопилот или перейти в ручной режим через Web UI. Смена режима сохраняет цикл и историю. Общий выключатель доступен только администратору и по умолчанию выключен. Согласование определяется политикой действия; назначение ассистента не заменяет подтверждения команды.

## Результаты

Успех означает проверенный результат сценария. Доступность ПК, запуск команды и ответ AI сами по себе не означают решения заявки.

На автопилот назначаются заявки из поддерживаемых сервисов. Неподдерживаемость сценария приостанавливает обработку без отмены обращения. Неверный раздел обрабатывается редиректом: отменой с шаблонным комментарием и ссылкой на правильный сервис Helpdesk. Отсутствие сценария не доказывает ошибку раздела. Исчерпание уточнений, отсутствие ответа или отказ заявителя приводят к отмене по соответствующему шаблону. Автоматической передачи оператору нет. После отмены ассистент остаётся исполнителем; конечный статус блокирует повторный запуск.

Принятое техническое правило: сбой платформы, неверная конфигурация и неизвестный результат операции останавливают цикл с видимой причиной. Они не приводят к автоматической отмене корректной заявки. Инженер сохраняет возможность добровольно продолжить работу вручную.

## Первый результат разработки

Первый сквозной сценарий — установка сетевого принтера: реквизиты, диагностика, установка, проверка и завершение либо отмена. Диагностика является шагом этого сценария. Другие сценарии добавляются после его приёмки.

Пользу оценивать по экономии времени инженера, подтверждённым решениям, причинам отмен, системным остановкам и повторным обращениям. Количество закрытых заявок само по себе не является показателем качества.

Правила и выбранные значения заданы в [спецификации поведения](lifecycle.md). Для текущего этапа они уточняют общую [дорожную карту](../roadmap.md) проекта.
