# Staging-приёмка Web UI и автопилота

Статус: обязательный внешний этап перед пилотом. Автоматические тесты не заменяют эту проверку, поскольку IntraService, WinRM, драйверы и реальные переходы статусов в них изолированы моками.

## Подготовка

Использовать отдельную тестовую заявку, тестовый Windows-компьютер и тестовый сетевой принтер. Их идентификаторы не сохранять в Git. У заявки должен быть безопасный заявитель, допускающий тестовые комментарии и смены статуса.

Перед началом:

- создать backup новой PostgreSQL и проверить его восстановление;
- проверить `/ready` и `/metrics`;
- сверить ID статусов и кастомных полей с тестовым экземпляром IntraService;
- назначить политики `install_printer` и `apply_triage` в `confirm`;
- оставить общий автопилот выключенным до проверки ручного режима.

Для обезличенного снимка состояния задайте токен сессии в `INTRALINK_STAGING_TOKEN` и выполните:

```powershell
.\scripts\check-web-autopilot-staging.ps1 -BaseUrl https://staging.example -TaskId <TEST_TASK_ID>
```

Скрипт выполняет только чтение readiness, метрик, настройки и текущего цикла. Запуск сценария и подтверждение изменяющих команд выполняются через Web UI.

## Сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Ручная установка | Одна установка, одна проверка результата и одно обновление заявки |
| Назначение `assistant` | Создаётся один цикл; повторный опрос не создаёт второй |
| Недостающие реквизиты | Отправляется настроенный запрос, ответ заявителя продолжает тот же цикл |
| Проверенный отказ установки | Используется `autopilot_execution_failed_cancel`, статус становится `30` |
| Недоступный WinRM или потерянный ответ | Цикл останавливается в `system_error`, заявка автоматически не отменяется |
| Пауза и смена режима | История сохраняется, новая команда не конкурирует с выполняющейся |
| Внешний конечный статус | Цикл завершается без нового изменения заявки |
| Удаление `assistant` | Автопилот приостанавливается; автоматической передачи оператору нет |
| Перезапуск компонента | Цикл восстанавливается, внешние изменения не повторяются |

Каждое подтверждение выполнять из Web UI под отдельной учётной записью оператора. Общий выключатель проверить под оператором и администратором: оператор видит состояние, но не может его изменить.

## Фиксация результата

Для каждого сценария записать время, ID `TicketRun`, ID команд, конечное состояние и наличие дублей. Не копировать в отчёт имя заявителя, комментарии, адреса и имена компьютеров. Допустимы только обезличенные технические идентификаторы тестового контура.

Пилот разрешён, когда все сценарии пройдены, расхождений между IntraService и историей `TicketRun` нет, а причины всех `system_error` объяснены. После приёмки автопилот включается администратором; изменяющие действия остаются в `confirm` до отдельного решения.
