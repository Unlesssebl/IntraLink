# План разработки Web UI и автопилота

Статус: реализовано в ветке разработки; автоматическая приёмка выполнена. Требования — в [спецификации поведения](lifecycle.md), назначение — в [концепции](concept.md), порядок включения — в [инструкции](operations.md).

## Рамки

Использовать существующие Command API v2, PostgreSQL, outbox, identity/RBAC, Poller и исполнителей. Развивать текущие очередь, карточку и настройки Web UI. Не создавать второй механизм команд, согласований или авторизации. Существующие точки записи, способные конфликтовать с циклом, подчинить общему серверному контролю.

Первый результат — установка сетевого принтера в обоих режимах. Рефакторинг RAG, смена моделей, новые микросервисы и расширение Telegram/CLI/MCP не входят в работу.

Сохранение старой БД и перенос Redis-циклов не требуются. Поддержать создание актуальной схемы на чистой БД; автоматическое удаление существующей БД в приложение или миграции не добавлять.

## Последовательность разработки

### 1. Устойчивый цикл и запуск

Добавить в PostgreSQL цикл, события, глобальную настройку и связь команды с циклом. Разделить режим, состояние и исход. Ограничениями БД обеспечить один активный цикл и уникальность основания запуска. Общая настройка по умолчанию выключена; изменение доступно администратору и журналируется.

Подключить Poller к регистрации назначений и продолжению сохранённых циклов. Сразу исключить параллельное исполнение прежнего автономного пути для управляемых заявок. Сохранение шага и создание команды согласовать с существующим outbox.

**Готово, когда:** чистая БД создаётся штатно; конкурентное назначение создаёт один цикл; рестарт и повторный опрос его не дублируют; переоткрытие без нового основания не запускает автопилот.

### 2. Общие команды и переключение режима

Связать ручные изменения и автопилот с общим циклом. Реализовать смену режима, паузу, возобновление и внешнее закрытие. Проверять условия перед исполнением, включая уже поставленные в очередь команды. Различать начатые и ещё не начатые операции.

В существующем policy engine обеспечить административный выбор `auto/confirm/disabled` для действий первого сценария. Сейчас AUTO allowlist включает только `diagnose_host` и `rag_sync`: точечно расширить допустимость для `install_printer` и `apply_triage`, сохранив default `confirm` и проверки полномочий. Не расширять вместе с этим разрешения на автоматические повторы.

**Готово, когда:** ручное действие не конкурирует с автопилотом; выключение блокирует новые шаги; начатый результат сохраняется; запрещённая или неактуальная команда не выполняется даже через прямой API.

### 3. Установка принтера и финализация

Подключить реквизиты, диагностику, установку, проверку и обновление IntraService. Автоматические комментарии и смены статуса проводить через `apply_triage`, без прямого обхода из lifecycle.

Реализовать ожидания и исходы из спецификации. Добавить два новых шаблона отмены в существующий каталог и административное управление, строгую проверку перед отправкой. Пока обязательные шаблоны не настроены, включение сценария запрещено.

**Готово, когда:** сценарий на тестовом исполнителе достигает подтверждённого успеха либо заданной отмены; сбой платформы останавливает цикл; повторное событие не дублирует комментарий, расходы или установку.

### 4. Web UI и API управления

Добавить API чтения цикла и истории, явного запуска, смены режима, паузы/возобновления и общей настройки. Мутации проверяют права и версию состояния; устаревший запрос возвращает конфликт. Согласование использовать из Command API.

В очереди показать режим и состояние; в карточке — шаг, ожидание, результат, причины остановки и историю. Сохранить самостоятельный ручной выбор действий и редактирование ответа. В настройках разместить административный выключатель и готовность шаблонов.

**Готово, когда:** оба режима доступны из существующей карточки; смена режима сохраняет историю; ожидания и ошибки понятны; оператор не может изменить общий выключатель.

### 5. Приёмка и переход на новый механизм

Выполнить сценарии ниже, профильные backend-тесты, проверку типов и сборку Web UI. После приёмки убрать заменённые Redis-состояния и старые автономные обходные пути. Добавить краткую инструкцию настройки сервисной учётной записи, шаблонов, политик и включения.

**Готово, когда:** циклом управляет один механизм; проверки проходят; документы соответствуют реализации; автопилот по умолчанию выключен. Реальные корпоративные изменения не использовать как автоматическую проверку разработки.

## Обязательная сквозная приёмка

- Открытое назначение, назначение при выключенном автопилоте, повторный опрос, повторное назначение и переоткрытие после отмены дают ожидаемое число циклов.
- Рестарт API, потеря Redis и закрытие вкладки не теряют цикл. Недоступность PostgreSQL блокирует изменения.
- Выключение, смена режима и закрытие заявки проверены для ожидающей команды и уже выполняющейся операции.
- Политики, отклонение согласования, изменение параметров и недостаточные права проверены через API.
- Ответ перед истечением 72 часов предотвращает отмену; собственный комментарий не продлевает ожидание; исчерпание двух уточнений использует заданный шаблон.
- Неподдерживаемый сценарий, отказ заявителя, отсутствие ответа и известный отказ исполнения отменяются с правильной причиной. Неактивный шаблон и незаполненные переменные блокируют отправку.
- Частичное обновление IntraService и потеря ответа исполнителя не вызывают слепых повторов. Диагностика сама по себе не завершает заявку.
- После завершения ассистент остаётся назначенным без нового запуска. Ручное продолжение после переоткрытия доступно.

Каждый этап сдавать отдельно: изменённое поведение, проверки и ограничения. Сборка интерфейса не заменяет проверку серверного цикла.
