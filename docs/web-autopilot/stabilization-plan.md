# План стабилизации Web UI и автопилота

Статус: локальная реализация и автоматическая приёмка завершены; внешний staging-прогон ожидает выделенные тестовые заявку, компьютер и принтер. Цель — подготовить первый сценарий к контролируемому пилоту и подтвердить поведение на реальных границах системы.

Реализованы структурированный контракт ошибок, безопасная обработка истёкшего lease, блокировка обходных путей активного цикла, пагинация и изоляция Poller, эксплуатационные метрики, права Web UI и staging-протокол. Сценарии с физическим Windows-компьютером и IntraService отмечаются выполненными только после внешней приёмки.

## Рамки

Сохраняется текущая концепция: два режима, единый `TicketRun`, Command API v2, PostgreSQL и Web UI как основной интерфейс. Первый сценарий остаётся установкой сетевого принтера.

Не добавлять новые сценарии, микросервисы, брокеры, модели AI и интерфейсы Telegram/CLI/MCP. Старую БД и прежние Redis-циклы не переносить. Масштабный рефакторинг выполнять только при доказанной невозможности исправить проблему локально.

Реальные изменения в корпоративной среде проводить только на специально выбранных тестовых заявке, компьютере и принтере. Общий автопилот до завершения приёмки оставлять выключенным.

## 1. Исправить контракт результата исполнителя

Разделить результаты установки на три категории:

- подтверждённый успех;
- известный проверенный отказ, после которого заявка отменяется по шаблону;
- инфраструктурная или неопределённая ошибка, после которой цикл переходит в `system_error`.

Execution-worker должен возвращать структурированный код причины и явный `verified_failure`. Не определять категорию по тексту сообщения. Runner обязан принимать решение только по структурированным полям.

**Готово, когда:** тесты проходят для всех трёх категорий; известный отказ использует шаблон `autopilot_execution_failed_cancel`; неизвестный результат не закрывает и не отменяет заявку.

## 2. Проверить восстановление и идемпотентность

Провести управляемые сбои в критических точках: после создания команды, во время исполнения, после внешнего действия до сохранения ответа и во время обновления IntraService. Отдельно проверить перезапуск API, Poller, command-worker и execution-worker, временную потерю Redis и PostgreSQL.

Запретить слепой повтор изменяющего действия при неизвестном фактическом результате. Возобновление должно либо продолжать с подтверждённого состояния, либо требовать решения инженера.

**Готово, когда:** установка, комментарий, статус и трудозатраты не дублируются; потерянный ответ приводит к безопасной остановке; сохранённый цикл восстанавливается после перезапуска.

## 3. Закрыть параллельные пути записи

Составить перечень всех маршрутов и клиентов, способных менять заявку или запускать инфраструктурное действие. Для Web UI изменения должны проходить через `TicketRun` и Command API. Старые маршруты допускаются только как явно документированный административный или совместимый интерфейс с теми же блокировками, правами и идемпотентностью.

Не удалять CLI, Telegram и MCP в рамках этапа. Если их поведение не соответствует новому циклу, запретить им изменять управляемую активным `TicketRun` заявку и зафиксировать дальнейшую миграцию отдельно.

**Готово, когда:** активный цикл нельзя обойти прямым вызовом `/api/v1/triage/apply` или legacy-команды; конкурентные запросы возвращают предсказуемый конфликт либо присоединяются к существующей операции.

## 4. Усилить Poller и обработку нагрузки

Заменить фиксированную выборку активных циклов на пагинацию или ограниченный цикл обработки с устойчивым курсором. Ошибка одной заявки не должна прерывать обработку остальных. Добавить ограничение параллелизма внешних запросов, не создавая несколько исполнителей одного цикла.

Проверить конкуренцию: повторное назначение, два оператора, две вкладки, смена режима одновременно с подтверждением команды, выключение автопилота во время исполнения.

**Готово, когда:** очередь больше одной пачки полностью обслуживается без голодания; сбой одной заявки изолирован; один шаг не исполняется дважды.

## 5. Провести staging E2E

На тестовой инфраструктуре пройти минимум следующие истории:

- ручная успешная установка;
- автопилот с подтверждением и успешной проверкой;
- запрос недостающих данных и продолжение после ответа;
- известный отказ с отменой по шаблону;
- недоступность инфраструктуры с переходом в `system_error`;
- пауза, смена режима, внешний конечный статус и удаление `assistant`;
- перезапуск одного из компонентов посередине сценария.

Проверить фактические ID статусов, поля IntraService, комментарии, трудозатраты и сохранение `assistant` среди исполнителей. Результаты фиксировать по идентификаторам тестовых циклов и команд без сохранения персональных данных в репозитории.

**Готово, когда:** все истории воспроизводимы через Web UI; фактическое состояние IntraService совпадает с историей `TicketRun`; нет необъяснённых изменений заявки.

## 6. Подготовить эксплуатацию пилота

Добавить наблюдаемость для зависших команд, возраста активного цикла, очереди согласований, задержки outbox и числа `system_error`. Определить краткую процедуру ручного восстановления и критерии остановки пилота.

Для новой БД определить резервное копирование, восстановление и срок хранения событий. Совместимость со старой БД не проверять. В Web UI убедиться, что оператор видит причину остановки, а административные действия доступны только обладателю соответствующих прав.

**Готово, когда:** оператор может обнаружить и безопасно разобрать зависший цикл; администратор может выключить автопилот; тест восстановления новой PostgreSQL подтверждён.

## Порядок выполнения

Этапы 1–4 выполняются на автоматических и локальных интеграционных проверках. Этап 5 начинается только после их прохождения. Этап 6 завершает подготовку пилота. Расширение на другие типы заявок начинается после успешного ограниченного пилота первого сценария.

Решение о включении принимает администратор после просмотра отчёта staging E2E. Начальная политика изменяющих действий — `confirm`; переход отдельных действий в `auto` выполняется отдельно и не считается обязательным условием запуска ручного режима.

## Критерий завершения

Этап считается завершённым, если один и тот же сценарий устойчиво проходит после перезапусков и повторной доставки событий, известные отказы отменяются по заданному шаблону, неопределённые ошибки безопасно останавливают цикл, а ни один доступный путь не может параллельно изменить управляемую заявку в обход серверного контроля.
