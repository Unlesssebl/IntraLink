# Roadmap: повышение качества RAG с минимальным объёмом изменений

Дата: 2026-09-08. Статус: Этапы A, B, C, D реализованы; верифицированы тестами.

Цель: находить применимые исторические решения, отклонять нерелевантные прецеденты и корректно сообщать об отсутствии знаний. Первую итерацию ограничиваем допуском источников в ответ, рабочим reranker и полнотекстовым поиском в существующем PostgreSQL.

## 1. Исходное состояние

Наблюдения из аудита 2026-09-08 относятся к проверенному локальному Docker-стеку и не являются оценкой всех окружений:

| Область | Подтверждённое состояние |
|---|---|
| Хранилище | PostgreSQL + pgvector 0.8.6, HNSW, BGE-M3 1024 измерения |
| Корпус | 5 записей, 2 дочерних сервиса одного направления; все с эмбеддингами |
| Качество записей | Всем присвоено 1.0 при импорте; ночной аудит этих записей не подтверждён |
| Reranker | FastEmbed добавлен в `requirements.txt`, модель `BAAI/bge-reranker-v2-m3` |
| Модель reranker | `BAAI/bge-reranker-v2-m3` — мультиязычный cross-encoder |
| Gate bypass #1 | Устранён: одиночный кандидат проходит полный reranker pipeline и пороговую проверку |
| Gate bypass #2 | Устранён: при скорах ниже порога возвращается пустой список (no-match) |
| Параллельный I/O | Устранён: dense и sparse запросы выполняются последовательно, гонка в AsyncSession исключена |
| Лексический поиск | Добавлена миграция Alembic для `search_vector (tsvector)` со `setweight` и GIN-индексом; в `rag.py` реализован `plainto_tsquery` + `ts_rank` |
| Smoke-проверка | Запрос про принтер вернул прецеденты об учётных записях, включая отменённую заявку |
| Cache stale | Устранён: в ключ кэша добавлена ревизия корпуса (`rev:{corpus_rev}`), инкрементируемая при sync и индексации |
| Eval | Поддерживает no-match кейсы (`expected_ids = []`), вычисляет истинный Recall@5 (`len/len`) и Hit@5 |
| Проверки | 41 тест пройден успешно |

Проценты «использованного потенциала», прежние ~70% точности и прогнозы улучшения не считаются измеренными метриками. Два smoke-запроса показывают дефект, но не характеризуют точность системы в целом.

## 3. Первая итерация: четыре небольших результата

Этапы выполняются последовательно. Пилотный набор из этапа A используется для проверки B–D; итоговый контрольный набор не используется для подбора порогов.

### A. Зафиксировать примеры и baseline

- [x] Собрать 30–50 размеченных запросов, включая минимум 10 случаев без подходящего ответа: чужой сервис, схожие слова с другим смыслом, отсутствие решения, отменённый прецедент.
- [x] Подготовить небольшой проверенный корпус по 3–5 частым направлениям; ориентир 10–20 решений на направление. Отбор по полезности, а не достижению квоты.
- [x] Сохранить источник каждого решения и релевантные IDs для запросов; для no-match **разрешить пустой список** `expected_ids` — исправить `validate_records` в `evals.py:L57`: убрать `raise DatasetError` при пустом `expected_ids`, добавить отдельный счётчик no-match строк.
- [x] Разделить примеры для настройки и итоговой проверки; исключить тестовую заявку и её дубли из корпуса. Эталон — применимый исторический прецедент, а не ID самой тестовой заявки.
- [x] Исправить `evaluate()` в `evals.py:L94`: `recalls` сейчас вычисляет `Hit@5` (`bool(intersection)`), а не `Recall@5` (`len(intersection) / len(expected)`). No-match кейсы считать отдельно, не включать в знаменатель Recall.
- [x] Добавить простой runner, вызывающий реальный поиск на фиксированном корпусе и сохраняющий результаты до/после. Обезличенные рабочие данные хранить вне Git; синтетические регрессии — в тестах.

Готово, когда можно повторить один и тот же прогон и увидеть релевантные выдачи, ложные рекомендации и случаи отсутствия ответа. Полный CI-eval для этого этапа не требуется.

### B. Единый допуск прецедента в рекомендацию

- [x] Разделить кандидатов поиска и источники, разрешённые для ответа. Один и тот же gate использовать в AI-синтезе, deterministic fallback и RAG Consensus.
- [x] Отбрасывать слабые или явно несовместимые с проблемой результаты. Числовой порог выбирать на настройочной выборке отдельно для фактически используемого вида score.
- [x] Отменённые заявки сохранять как исторический контекст, но не считать подтверждённым техническим решением. Проверять `resolution_type`, а не только отображаемое имя статуса.
- [x] Исторический прецедент описывать как ранее применявшееся решение со ссылкой на источник; не утверждать, что действие выполнено в текущей заявке.
- [x] При отсутствии пригодного источника возвращать no-match и существующий регламентный ответ/уточнение.
- [x] **Устранить gate bypass #1** (`rag.py:L692-694`): блок `if len(candidates) == 1: return candidates[:top_n]` обходит и reranker, и пороговую проверку. Удалить ранний возврат; одиночный кандидат должен проходить полный pipeline наравне с остальными.
- [x] **Устранить gate bypass #2** (`rag.py:L728-729`): блок `if not filtered: filtered = sorted_candidates[:top_n]` аннулирует `rerank_threshold` — при пустом отфильтрованном списке возвращаются наихудшие кандидаты. Заменить на возврат пустого списка (no-match), а вызывающий код обработать как отсутствие знаний.
- [x] Отличать деградацию (`rerank_fallback=True`, модель недоступна) от отсутствия знаний (кандидаты ниже порога). Поле `rerank_fallback` уже есть в коде — использовать как явный degraded-сигнал наверх.

Готово, когда кейс «Kyocera → учётная запись» не попадает в рекомендацию ни через AI, ни через fallback, а полезные эталонные примеры продолжают находиться.

### C. Подключить готовый локальный reranker

- [x] **Добавить `fastembed` в `core-api/requirements.txt`** с закреплённой версией (например `fastembed>=0.5.0`). Убедиться, что `from fastembed import TextCrossEncoder` успешно импортируется внутри runtime-образа `python:3.13-slim` — сейчас `get_local_reranker_model()` молча возвращает `None` и reranker не вызывается никогда.
- [x] **Сменить модель**: заменить `BAAI/bge-reranker-base` (EN-only) на `BAAI/bge-reranker-v2-m3` в `settings.RERANKER_MODEL`. Это multilingual cross-encoder с подтверждённой поддержкой русского технического текста в FastEmbed.
- [x] **Прогреть веса при сборке образа**: добавить в `core-api/Dockerfile` шаг после `pip install`: `RUN python -c "from fastembed import TextCrossEncoder; TextCrossEncoder('BAAI/bge-reranker-v2-m3')"`— без этого контейнер при первом старте пойдёт скачивать ~550 МБ с Hugging Face, что сломает закрытый контур и замедлит холодный старт.
- [x] Проверить семантику scores: `model.rerank()` возвращает логиты. `normalize_rerank_score()` уже применяет sigmoid — убедиться, что при смене модели sigmoid не применяется дважды. Отдельно хранить `ranking_score` и булево решение gate.
- [x] Добавить проверку готовности модели (`model is not None`), ограничение параллелизма и таймаут. Деградацию (модель недоступна) отражать явно через `rerank_fallback=True`, а не через тихий fallback к порядку RRF.
- [x] Прогнать реальную модель внутри runtime-образа: русский positive, negative, отказ и холодный старт. Измерить p50/p95, потребление памяти и размер кэша весов.

Готово, когда reranker реально вызывается в Docker и улучшает порядок подходящих прецедентов на фиксированной выборке без роста ложных рекомендаций. Если выигрыш не подтверждён, компонент не включать в основной поток только ради наличия функции.

### D. Настоящий гибридный поиск в PostgreSQL

- [x] **Устранить небезопасный `asyncio.gather`** (`rag.py:L811`): `dense_task` и `sparse_task` оба получают одну `db: AsyncSession` и запускаются параллельно — asyncpg не поддерживает конкурентные запросы на одном соединении. Вариант 1 (предпочтительный): объединить dense и sparse в единый SQL-запрос через CTE (один roundtrip, нет проблемы сессий). Вариант 2: выполнять последовательно — `dense_matches = await dense_vector_search(...)`, затем `sparse_matches = await sparse_text_search(...)`.
- [x] **Добавить колонку `search_vector`** через Alembic-миграцию с backfill. Использовать `setweight` для ранжирования полей: `setweight(to_tsvector('russian', coalesce(original_name, '')), 'A') || setweight(to_tsvector('russian', coalesce(problem, '')), 'B') || setweight(to_tsvector('russian', coalesce(solution, '')), 'C')`. Колонка помечается `GENERATED ALWAYS AS ... STORED` — обновляется автоматически при записи.
- [x] **Не использовать двуязычный concat** `to_tsvector('russian', ...) || to_tsvector('english', ...)`: конфигурация `pg_catalog.russian` уже направляет ASCII-слова в `english_stem`, а технические токены (`numword`, `host`, `file`) — в `simple` без искажений. Конкатенация раздувает GIN-индекс, дублирует позиции лексем и ломает скоринг `ts_rank` (подтверждено живым `ts_debug` экспериментом).
- [x] Создать GIN-индекс: `CREATE INDEX CONCURRENTLY idx_tkb_search_vector ON task_knowledge_base USING GIN (search_vector)`.
- [x] Заменить ILIKE-цикл в `sparse_text_search` на `search_vector @@ plainto_tsquery('russian', :query)` с ранжированием через `ts_rank`. PostgreSQL `ts_rank` **не называть BM25** — это разные алгоритмы.
- [x] Учесть особенность парсера: дефис перед цифрой интерпретируется как знак числа (`KB-5005565` → `{kb}` + `{-5005565}`). При формировании `plainto_tsquery` нормализовать дефисы — заменять на пробелы для числовых токенов.
- [x] **Добавить ревизию корпуса в cache key** (`rag.py:L779-782`): включить `sync_timestamp` или счётчик строк корпуса. Без этого `/sync` не инвалидирует кэш и пользователь получает устаревшие результаты до истечения TTL 10 минут.
- [x] Сохранять видимые отдельные scores (`dense_rank`, `sparse_rank`, `rrf_score`, `rerank_score`) и признаки фактически работающих стадий поиска.

Готово, когда морфологические варианты и технические токены находят эталоны, обе ветви подтверждены интеграционной проверкой, а no-match сохраняется после fusion и reranking.


## 4. Критерии завершения первой итерации

Сравнивать baseline и новую версию на одном корпусе, настройках окружения и отложенных запросах. Показывать абсолютные количества рядом с долями: маленькая выборка не даёт оснований заявлять production-точность 95%.

| Проверка | Критерий приёмки |
|---|---|
| Ложные рекомендации на negative-наборе | 0 допущенных в ответ нерелевантных источников на зафиксированном наборе; не гарантия для всех запросов |
| Positive retrieval | Recall@5 (`len(hit) / len(expected)`) и MRR@5 не хуже baseline; Precision@1 выше при наличии ошибок в baseline |
| Покрытие ответа | Доля положительных кейсов с разрешённым источником не падает относительно baseline; отказ от всех ответов не считается улучшением |
| Grounding | Нет утверждений о выполнении текущей работы на основании истории другой заявки |
| Отказ компонентов | Нет обхода gate; `rerank_fallback=True` (деградация) явно отличается от пустого списка (no-match) |
| Производительность | p50/p95 без кеша и с кешем измерены; допустимый бюджет установлен по целевому оборудованию до включения |
| Воспроизводимость | Зафиксированы SHA сборки, версии пакета/модели, корпус, split, профиль, пороги и отчёт |
| Cache integrity | Обновление корпуса (`/sync`) инвалидирует кэш поиска — проверить smoke-тестом после внедрения ревизии корпуса в cache key |

Recall@5 считать как `len(expected ∩ retrieved[:5]) / len(expected)`, а не `bool(intersection)` — текущая реализация в `evals.py:L94` соответствует Hit@5. No-match кейсы (пустой `expected_ids`) оценивать отдельно: они не участвуют в знаменателе Recall. На этапе A исправить эти определения в существующем [evaluator](../../core-api/app/services/evals.py).

## 5. Включение и откат

1. Внести изменения небольшими проверяемыми PR: A → B → C → D. Общая готовность определяется критериями выше, а не числом установленных компонентов.
2. Сравнить результаты вне операторского потока, затем включить новый профиль для пилота в карточке заявки. Batch RAG расширять после замеров нагрузки и пользы.
3. Сохранить возможность отключить reranker/новый профиль. Gate применимости остаётся активным при любом откате; безопасный результат при нехватке доказательств — отсутствие рекомендации из KB.
4. FTS-миграцию сделать добавочной; при откате приложения новую колонку/индекс можно оставить до отдельной уборки. Изменения retrieval не расширяют права AI на исполнение действий.
