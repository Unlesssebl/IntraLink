## 1. Цели и границы реализации

Основная цель — устранить ложные подтверждения выполнения, ошибки интерпретации свободного текста, синтаксически неверные параметры команд, выбор неподтверждённого устройства, потерю исправлений заявителя и небезопасные повторы. Развивать существующие FactBag, сценарии, command service и worker SDK; новый движок сценариев и расширение RAG не требуются.

### Ключевые архитектурные инварианты:
1. **Строгий verify и Fail-Closed:** Никакое инфраструктурное действие не считается подтверждённым без свежего, независимого чтения целевого состояния. Флаг `already_member` фиксирует предшествующий факт, но не освобождает от проверки фактического членства в момент `verify`.
2. **Обратная совместимость функций нормализации:** Сигнатуры `normalize_pc_name(str) -> str | None` и `normalize_printer_address(str) -> str | None` остаются неизменными. Расширенная контекстная информация передаётся через новые интерфейсы `parse_pc_name()` и `parse_printer_address()`.
3. **Детерминированный приоритет перед AI:** Детерминированные парсеры и валидаторы запускаются первыми. LLM-экстрактор вызывается строго точечно для неразрешённых и неоднозначных фактов.
4. **Проверяемый Grounding:** Для каждого значения проверяется цепочка «конкретный источник → цитата → значение → допустимая нормализация». Наличие произвольной реальной цитаты не подтверждает другое значение.
5. **Разделение повторов:** Повтор доставки комментария в IntraService изолирован от инфраструктурной команды воркера. Ошибка HTTP-запроса комментария не должна приводить к повторному запуску установки на рабочей станции.
6. **Идентификация пользователя AD (решение пользователя):** Для действий над существующей учётной записью используется точный уникальный логин. Поиск по ФИО допускается только в сценарии создания учётной записи — для предварительной проверки её наличия. Автоматический выбор первого активного совпадения запрещён.

## 2. Принятые проектные решения

> [!IMPORTANT]
> **1. Политика членства в AD (WLAN):**  
> Сценарий выдачи WLAN подтверждает прямое членство в точной целевой группе. Пользователь идентифицируется точным уникальным логином; группу однозначно разрешаем в DN и сравниваем с полными значениями `MemberOf`. Транзитивное членство не подменяет это постусловие. Текущий список `groups` содержит извлечённые CN и пригоден для отображения, но не для сравнения с DN/sAMAccountName. Пользователю DN/SID для запуска операции не нужен.

> [!NOTE]
> **2. Разметка выборки 99 заявок (Этап 4):**  
> Текущие 99 заявок уже использовались при разработке и остаются регрессионной выборкой: подтверждены 4, остальные 95 требуют экспертной оценки. Независимый holdout формируется из новых обезличенных заявок и фиксируется до настройки на нём. Дубликаты и варианты одного инцидента не распределяются между разработочной и отложенной выборками. Не задавать искусственное соотношение 60/39.

**3. Валидность и проверка цели:** `FactState.VALID` означает допустимое значение по контракту факта, но не существование устройства и не принадлежность заявителю. Сценарий отдельно требует свежую проверку цели перед мутацией. Успешный ping сам по себе не подтверждает, что выбран нужный ПК.

**4. Совместимость:** новые поля контрактов добавляются с безопасными значениями по умолчанию. При изменении сериализуемых схем обновить версии, адаптеры и ANALYSIS_REVISION; старые решения с недостаточными доказательствами требуют повторного анализа. Сохранять сигнатуры нормализаторов, но явно считать отказ от неверных/неоднозначных значений намеренным изменением поведения.

## 3. Детальный пошаговый план реализации

### Уточнение сценария создания учётной записи

Согласованная последовательность: поиск в AD по ФИО → при подтверждённом отсутствии создание → проверка созданной записи по выданному логину → предоставление логина и временного пароля в результате заявки.

- `execution-worker/executors/ad.py`: выделить точный поиск существующего пользователя по логину для WLAN и остальных операций. Один зафиксированный логин используется во всех фазах; поиск по ФИО оставить только для `create_user`.
- `execution-worker/handlers/create_user.py`: предварительный поиск по ФИО с реквизитами сотрудника должен явно различать `not_found`, `found`, `ambiguous` и `unavailable`. Только успешный поиск без совпадений допускает создание. Найденная отключённая учётная запись также считается существующей; ошибка AD не является отсутствием пользователя.
- При найденной записи не создавать дубль и не генерировать пароль для существующего пользователя. При нескольких однофамильцах/совпадениях запросить уточнение, а не выбирать первого активного.
- Перед созданием повторно проверить отсутствие записи и доступность предлагаемого логина. Сохранить выбранный логин и DC в попытке команды до мутации; исполнитель не должен молча менять логин после этой фиксации. Конкурирующие запросы одного сотрудника сериализовать блокировкой по нормализованным реквизитам в существующем механизме команд; разные сотрудники с совпадающими ФИО требуют уточнения, а не автоматического объединения. Блокировка защищает исполнителей IntraLink, а не внешних администраторов AD: непосредственно перед записью нужна повторная проверка. Занятый логин требует перепланирования, а не неявного создания под другим именем.
- После создания выполнять verify и восстановление неопределённого исхода по зафиксированному логину с проверкой ожидаемых реквизитов и связи с командой. Наличие записи под этим логином само по себе не доказывает, что именно эта попытка её создала. Для старых попыток без сохранённого логина совпадение ФИО даёт только кандидатов для ручного разбора.
- `execution-worker/worker.py`, `core-api/app/services/command_secrets.py`: использовать существующий механизм защищённого артефакта для временного пароля. Результат заявки должен предоставлять логин и доступ к паролю уполномоченному получателю; пароль не переносится в обычные журналы и payload команды.
- Создание записи и доставка реквизитов учитываются отдельно. Зафиксировать `account_verified` и `credentials_available` раздельно; завершение требует обоих условий. Проверить доступ получателя к существующему механизму выдачи в интерфейсе/через API, а не только факт сохранения артефакта. Если учётка создана, но пароль утрачен до сохранения или артефакт истёк/уже получен, не создавать запись повторно и не сбрасывать пароль автоматически: сохранить частичный результат и отдельное восстановление реквизитов. При неизвестном результате сохранения артефакта сверить его метаданные; повтор не должен заменять секрет.
- Тесты: точный логин при совпадающих ФИО; существующая активная/отключённая запись; несколько кандидатов; ошибка поиска; подтверждённое отсутствие; занятый логин; параллельное создание; verify новой записи; сбой выдачи пароля после создания; повтор команды без повторного создания учётки.

Критерий готовности: существующие пользователи обрабатываются исключительно по точному логину; новая запись создаётся только после успешной проверки отсутствия, а завершённый сценарий включает подтверждённое создание и доступность логина/временного пароля получателю.

### Этап 1. Проверяемые значения и ссылки на исходный текст

**Цель:** Гарантировать, что параметры команд синтаксически валидны и трассируются до конкретных исходных данных.

1. **`shared/normalizer.py`:**
   - Реализовать dataclass `NormalizationResult`:
     ```python
     @dataclass(frozen=True, slots=True)
     class NormalizationResult:
         raw_value: str
         normalized_value: str | None
         steps: tuple[str, ...]
         candidates: tuple[str, ...]
         is_ambiguous: bool
         error: str | None = None
     ```

### Этап 2. Намерение, связи устройств и исправления в истории

**Цель:** Различать запросы действия, сообщения о симптомах и завершённые операции; разрешать конфликты при исправлении данных заявителем.

1. **`core-api/app/services/scenarios/builtin.py`:**
   - В матчере установки принтера `_printer_install_match` и базовых правилах выделить 4 независимых класса маркеров:
     - Запрос действия (`intent_action`): «установите», «подключите», «настройте», «добавьте».
     - Завершённое действие (`intent_completed`): «уже установлен», «установили», «стоит принтер».
     - Отрицание (`intent_negation`): «не устанавливайте», «отмените установку», «не надо ставить».
     - Проблема / симптом (`intent_symptom`): «не печатает», «после установки перестал печатать», «переустановка не помогла».
   - Маркеры оценивать в пределах предложения и связанного устройства. Отрицание/прошлое состояние одного объекта не подавляет запрос для другого. «На старом ПК установлен, подключите на новом» остаётся запросом установки на новый ПК; «переустановка не помогла» ведёт к диагностике. Неразрешённое противоречие ведёт к уточнению, а не к произвольному баллу уверенности.

2. **`shared/domain/scenario.py` и `FactBag`:**
   - Расширить спецификацию целевых объектов печати: связывать в единую сущность `PrinterTargetBinding` модель принтера, IP-адрес, тип подключения, целевой ПК и контекстную роль («новый», «старый/заменяемый», «упомянутый в истории»).
   - Исключить объединение модели одного принтера с адресом другого принтера, упомянутого в том же тикете.

3. **`core-api/app/services/facts/merger.py`:**
   - **Политика конфликтов между кастомным полем и комментарием:**
     - Если в комментарии заявителя содержится явное исправление («ошибся в поле, ПК ...», «исправленный ПК: ...»), факт кастомного поля не должен подавлять комментарий исключительно из-за приоритета `STRUCTURED_FIELD`.
     - Явное исправление от идентифицированного заявителя/оператора с однозначной ссылкой на старый факт сохраняется как `supersedes`; новое значение проходит проверки и аннулирует прежнее согласование действия. При двух разных действующих значениях без такой связи — CONFLICTING, при нескольких кандидатах одного наблюдения — AMBIGUOUS. Простое упоминание другого ПК и цитата старой переписки не образуют исправление. Не требовать повторного вопроса для уже однозначно подтверждённого исправления.
   - **Привязка ответов на уточнения:**
     - Привязывать факт `clarification_answer` к ключу запрашиваемого факта, вопросу и версии сценария. Исключить повторный запрос одного и того же уточнения.

4. **`scenario_pipeline.py`, `triage_service.py`, `fact_extractor.py`, `facts/collectors.py`:**
   - Единственный coordinator: детерминированный сбор → предварительный merge/кандидаты сценариев → недостающие обязательные факты или отношения → точечный extraction → окончательные merge/routing. Не запускать модель, если детерминированного результата достаточно.
   - Удалить/перенаправить прямые ранние вызовы enrichment в `triage_service.py`. В API extraction передавать allowed requested fact keys и источники; изменения других полей отбрасывать.
   - Для MISSING разрешать заполнение; для AMBIGUOUS — только доказанное разрешение. INVALID явного поля и CONFLICTING нельзя молча исправлять AI: сохранять предложение исправления для уточнения. Ошибка AI не блокирует независимый сценарий с достаточными проверенными фактами; действуют существующие режимы shadow/enabled и timeout.

Имена свойств сверить с реальным объектом используемого cmdlet/CIM provider в тестовом Windows-контуре; не предполагать, что поле называется `HostAddress`. Для `usb` проверять USB/PnP-связь и очередь без требований IP/RAW/LPR. Если ветка не реализована, возвращать UNSUPPORTED и не предлагать её как готовую автоматизацию.

Последнее — `null` без явного подтверждения пользователя/оператора с источником и временем; успешный spooler job не заменяет его. Установка может завершаться подтверждением конфигурации, а устранение неисправности печати имеет отдельное постусловие. Печатать тестовую страницу только в рамках предусмотренного сценария.

2. **`execution-worker/sdk/base.py`, `worker.py`:**

Read-only сверка различает satisfied, not_satisfied и unavailable; неизвестность не разрешает повтор. Для изменённого контракта предусмотреть адаптер и тесты сохранения статуса до БД/финализации.

3. **`decision_application_service.py`, `scenario_orchestrator.py`, `command_service.py`, `command_outbox.py`:**
   - Проверка ticket fingerprint при применении уже есть: сохранить её и расширить защиту на все пути создания/approve/claim команды. Хранить неизменяемый снимок цели, действия, версии сценария, ревизии фактов и параметров в согласованной команде.
   - Изменение цели/намерения/обязательного факта аннулирует прежнее согласование и требует нового решения. Косметическое изменение, не влияющее на основания, не должно без необходимости запускать полный цикл согласования.
   - Перед выдачей queued-команды воркеру и перед допуском первой мутации проверить свежесть исходных данных. Внешнее чтение выполнять вне длительной DB-блокировки, затем повторно проверить версию команды транзакционно. Если свежесть проверить нельзя, действие приостанавливается. Изменившаяся заявка не переписывает параметры уже согласованной команды.
   - Документировать неизбежное окно между внешней проверкой и мутацией: атомарной транзакции AD/IntraService/БД нет. Применять ограниченный срок допуска, проверку версии/lease и неизменяемую цель. Исполнитель не должен заново исправлять или выбирать hostname по свободному тексту.
   - Повтор публикации подтверждённого результата отделить от исполнения. При HTTP timeout сначала read-only reconcile применения в IntraService, затем повтор только недоставленных частей; не дублировать комментарий/трудозатраты и не пересоздавать command. Проверить create_user с существующим секретным артефактом и ошибкой доставки результата.

4. **`core-api/app/services/decision_compiler.py`:**

### Этап 4. Доказательство качества и постепенное включение

**Цель:** Объективная оценка точности на экспертно размеченной выборке и поэтапное развёртывание.

1. **Разметка контрольной выборки:**
   - Подготовить черновую разметку оставшихся 95 случаев; статус confirmed присваивать после экспертной проверки. Размечать intent, точную цель, допустимые сценарии, обязательные уточнения и запрещённые действия. Неполные данные оставлять needs_review, не считать верными автоматически.
   - Текущий набор использовать для регрессий. Новую отложенную выборку собирать отдельно, фиксируя источник, время, версии и разбиение по группам связанных заявок. После использования holdout для исправлений он становится частью разработки, а итоговую оценку проводить на следующем срезе.
   - Добавить синтетические граничные примеры (омоглифы, отрицания, несколько устройств).

2. **Метрики и бенчмарки:**
   - `decision_quality_report.py` читает рабочие журналы БД: расширить его для наблюдаемой обратной связи. Offline replay и CI должны читать зафиксированные fixtures, не обращаться к рабочей БД/AI/сети. Существующий `ticket_quality_baseline.py report` проверяет baseline, но не заменяет прогон новой реализации.
   - Разделить источники метрик: intent/target — размеченный replay; повторные вопросы — последовательности вопросов/ответов; false success — тесты исполнителей и подтверждённые результаты пилота. Из одного снимка решения нельзя получить все метрики.
   - Метрики:
     - Точность выбора намерения и цели (Intent & Target Selection Accuracy).
     - Доля ложных допусков к мутации (False Positive Execution Rate).
     - Доля избыточных и повторных уточнений (Redundant Clarification Rate).
     - Доля ложного успеха (False Success Rate).
     - Задержки вычисления p50 / p95.
   - Для каждой доли фиксировать числитель/знаменатель, размер выборки и сценарий. Дополнительно измерять долю полезно обработанных заявок: отказ от всех действий не считается качественной автоматизацией. Нет данных для метрики — N/A, не 0%. Ограничения задержки установить после измерения baseline.

3. **CI-шлюзы и этапы выкатки:**
   - Создать `test_decision_quality_benchmark.py`: запуск текущей реализации на размеченных fixtures с запретом сети. Блокировать неверную цель, forbidden actions и ошибочные уточнения на подтверждённых кейсах. False success отдельно блокируется suite исполнителей/финализации. Не использовать заранее сохранённые predicted/retrieved результаты как результат новой реализации.
   - Поэтапный rollout:
     - Фаза A: Offline Replay (без сети, проверка на датасете).
     - Фаза B: Shadow Mode (чтение живых заявок без отправки команд).
     - Фаза C: Human-in-the-Loop (обязательное подтверждение оператора).
     - Фаза D: Ограниченный Auto-режим для проверенных низкорисковых сценариев с мгновенным kill-switch.
   - На пилоте начинать с установки принтера, диагностики печати и WLAN. Создание AD-учётки с выдачей пароля сначала оставлять с подтверждением оператора. Любой подтверждённый случай неверной цели/ложного успеха отключает auto соответствующего сценария до исправления; статистика малой выборки не доказывает production-точность.

### Порядок отдельных изменений и совместимость

1. Точный AD-контракт и WLAN verify со сквозными регрессиями.
2. Создание пользователя и выдача реквизитов на новом AD-контракте.
3. Общие текстовые источники, нормализаторы, валидаторы и grounding.
4. Intent, связи устройств, исправления и единственный coordinator extraction.
5. Неизменяемая согласованная цель, recovery, printer postconditions и финализация.
6. Новая оценочная выборка и поэтапный пилот. Разметку и regression suite развивать с первого изменения.

Каждое изменение содержит код и свои тесты и оставляет CI зелёным. При необходимости хранения новых полей подготовить Alembic-миграцию в том же изменении: старые команды не получают фиктивно заполненные доказательства. Сначала совместимый reader/API, затем writer/worker; несовместимый контракт отклоняется. Данные команд не удалять при откате; отключать сценарий существующей политикой и переводить в ручной разбор. Не менять режимы работающего окружения в рамках подготовки плана.

## 4. Обязательные граничные случаи и восстановление

Этот раздел входит в приёмку этапов 1–4, а не откладывается на отдельный будущий проект. Полнота означает наличие проверок перечисленных критических случаев; документ не заявляет покрытие всех возможных комбинаций отказов.

### 4.1. Жизненный цикл фактов и источников (этапы 1–2)

Ответственные: `facts/collectors.py`, `facts/store.py`, `facts/merger.py`, `shared/domain/scenario.py`, `scenario_pipeline.py`.

- **Отзыв операторского значения:** последнее актуальное событие оператора обрабатывается до поиска предыдущего VALID. Явное очищение или INVALID не должно возвращать старый ПК как действующий. Для очистки сохранить событие отзыва со ссылкой на наблюдение; история остаётся для аудита. Новое корректное значение после отзыва может восстановить факт.
- **Редактирование/удаление источника:** хранить ID и ревизию поля/комментария, ссылку на заменённую ревизию и признак отзыва. Удаление подтверждённого источника аннулирует основанные только на нём факты и согласования. Не считать отсутствие комментария на одной странице API доказательством удаления: сначала подтвердить полноту снимка или получить событие удаления. При неполной истории отметить неизвестную актуальность, не выбирать цель автоматически.
- **События не по порядку:** различать время изменения источника, время получения и порядок записи в БД. Повторная доставка одной ревизии идемпотентна; более старая ревизия не заменяет новую. Если API не предоставляет сравнимые ревизии, перечитать актуальный источник, а не выводить порядок из времени получения. При конкурирующих исправлениях без установленного порядка — CONFLICTING.
- **Свежесть проверки:** хранить `source_modified_at`, `collected_at` и `verified_at` с разным смыслом. Перечитывание текста не продлевает TTL диагностики/проверки принадлежности устройства. Истёкшее обязательное доказательство требует нового read-only запроса; ошибка этого запроса приостанавливает мутацию. Если старое значение уже отозвано, истечение TTL нового значения не должно возвращать его из истории.
- **Закреплённый сценарий:** pin сохраняет версию логики, но не разрешение на действие. Явная отмена намерения или исчезновение обязательного основания приостанавливает сценарий, даже если другой matcher не набрал порог. Переход к другому сценарию оформляется отдельно, с новой проверкой фактов и согласованием.
- **Вложения:** в первой итерации OCR/визуальный анализ может предлагать кандидата с ID/ревизией вложения и источником. Для цели, указанной только на изображении, требуется подтверждение заявителя/оператора и обычная проверка устройства. Недоступное/нечитаемое вложение — недостающее основание, а не отсутствие проблемы. Противоречие изображения полю требует разрешения; текст изображения не выполняется как инструкция системе.

Тесты добавить в `test_fact_merge_corrections.py`, `test_fact_grounding.py`, `test_fact_override.py`, `test_scenario_execution.py`. Минимальные последовательности: VALID → отзыв; VALID → INVALID; отзыв → новый VALID; правка → старый дубль события; удаление → повтор старого снимка; истечение TTL → недоступная проверка; pinned install → «не устанавливайте»; ПК только во вложении → подтверждение.

### 4.2. Отмена, права и неопределённый результат (этап 3)

Ответственные: `command_service.py`, `scenario_orchestrator.py`, `command_outbox.py`, `execution-worker/sdk/base.py`, `sdk/lease_renewer.py`, `worker.py`.

- Допуск к исполнению проверяет не только цель, но и текущий статус заявки, отсутствие отмены, действительность согласования и применимые полномочия инициатора/согласовавшего, режим action policy. Для системного auto проверяется его собственное полномочие, а не наличие интерактивной сессии оператора. Недоступность обязательной проверки не означает разрешение.
- Для закрытой/отменённой заявки не начинать новую мутацию. Повторное открытие требует нового анализа; старые команды не оживают автоматически. Уже выполненное действие записать в аудит, но не переоткрывать заявку и не менять её статус автоматически ради финализации старого сценария.
- Разделить «отмена до первой мутации» и «отмена после возможной мутации». `prepare` тоже может менять инфраструктуру, например включать WinRM. Сохранять фазу и факт начала мутации до внешнего вызова. После отправки команды отмена/потеря lease не доказывает отсутствие изменений: запрещается следующий изменяющий шаг, назначается read-only reconcile.
- Отмена между execute и verify не должна навсегда терять результат. Если текущий worker уже не имеет полномочий на фиксацию результата, сверку завершает действующий владелец через Core API. Старый claim token не принимается; повторная мутация не разрешается неизвестным исходом.
- Cleanup — отдельное обязательство по принадлежащим попытке ресурсам: не отменять чужие изменения WinRM и не удалять staging другой команды. Неуспех cleanup остаётся видимым даже при успешном действии. Автоматический rollback бизнес-действия после отмены не вводить.

Тесты расширить в `test_worker_sdk.py`, `test_execution_worker_v2.py`, `test_commands_v2.py`, `test_command_target_drift.py`, `test_command_delivery.py`: отмена до prepare, после prepare, во время execute, перед verify; закрытие/повторное открытие заявки; отзыв полномочий; выключение policy; две конкурирующие отмена/approve; запоздалый результат старого worker; повтор сообщения после terminal state.

### 4.3. Одноразовая выдача пароля (подзадача create_user и этап 3)

Ответственные: `command_secrets.py`, вызывающий endpoint выдачи и его клиент, `worker.py`, `decision_application_service.py`.

- Сохранить одноразовую семантику существующего артефакта. `consume()` стирает секрет до доставки HTTP-ответа, поэтому потеря ответа не доказывает получение пароля. Не обещать гарантированную однократную доставку через сеть.
- Различать готовность реквизитов к выдаче, серверный факт погашения и подтверждение получения клиентом. Артефакт в БД может удовлетворять `credentials_available`, но не даёт утверждения «пароль получен». При потере ответа показывать неопределённость выдачи и согласованный путь восстановления; не выдавать секрет повторно и не сбрасывать пароль автоматически.
- Проверять права непосредственно перед выдачей. Два параллельных получателя не должны оба получить секрет; устаревшая/чужая ссылка не даёт доступа. Успешное чтение метаданных не означает право получить содержимое.
- Проверить границы TTL, гонку consume/cleanup и сбой DB commit. Повтор после погашения или истечения срока сообщает точный исход без секрета. Восстановление реквизитов — отдельная операция, не повтор создания учётки. Содержимое не попадает в журнал выдачи.

Тесты в `test_command_secrets.py` и `test_command_delivery.py`: два одновременных consume; погашение → потеря ответа; отзыв доступа перед чтением; истечение TTL во время запроса; cleanup одновременно с выдачей; ошибка фиксации; отсутствие секрета в логах и обычном результате команды.

### 4.4. Матрица проверок

Статусы ниже описывают требуемую семантику. Сопоставить их существующим enum/полям команд и попыток; не вводить параллельную машину состояний. Сверка может подтвердить результат действия, но не восстанавливает отозванное разрешение на новую мутацию.

| Граница | Событие / отказ | Ожидаемый исход | Следующая мутация | Восстановление |
|---|---|---|---|---|
| Сбор фактов | Отзыв/удаление источника | Missing/invalid/conflicting по причине; старое основание недействительно | Нет | Актуальный источник или уточнение |
| Сбор фактов | Старый дубль события | Текущая ревизия сохранена | Только по текущим основаниям | Идемпотентный пропуск |
| Согласование/очередь | Новая цель, отмена намерения, закрытие заявки | Старое разрешение недействительно | Нет | Новый анализ, если заявка снова актуальна |
| Перед первой мутацией | Истёкшая проверка, недоступные права/DC/API | Приостановлено, результат проверки неизвестен | Нет | Read-only проверка |
| Prepare уже изменил состояние | Отмена/сбой | Подготовка могла выполниться | Только разрешённый cleanup своих ресурсов | Сверка состояния и cleanup |
| Execute отправлен | Таймаут/отмена/потеря lease | Исход неизвестен | Нет | Read-only reconcile действующим владельцем |
| Execute завершён, verify не выполнен | Отмена/остановка процесса | Успех ещё не подтверждён | Нет | Verify/reconcile без повторного execute |
| Verify успешен | Сбой cleanup | Действие подтверждено, cleanup не завершён | Бизнес-действие не повторять | Повтор безопасного cleanup с проверкой владения |
| Результат подтверждён | HTTP timeout публикации | Доставка неизвестна | Нет | Сверка публикации, доставка недостающих частей |
| Секрет погашен | Потеря ответа клиенту | Получение не подтверждено | Нет | Явное восстановление реквизитов |
| Команда завершена | Повтор сообщения / поздний результат | Terminal state не переигрывается | Нет | Дедупликация, аудит |

Для каждой строки назначить параметризованный тест с ID кейса и проверить состояние в БД, число мутирующих вызовов и содержание комментария. Дополнительно обязательны сочетания: изменение цели + повтор сообщения; отзыв права + approve; timeout execute + повторная доставка; отзыв факта + истечение TTL; consume + потеря ответа. Не ограничиваться отдельными unit-тестами happy path.

Моки не подтверждают корректность PowerShell в домене. Затем выполнить штатные проверки репозитория для затронутых компонентов. Эти команды — план проверки, а не заявление об их выполнении при редактировании документа.

### Критерии успешной приёмки:
1. Ноль случаев ложного подтверждения успеха (`false success`) в тестах воркера и AD.
2. Неверный IPv4, недопустимый hostname и неоднозначная нормализация не получают VALID. Для мутации дополнительно подтверждены существование и выбор конкретной цели; формат и доступность не подменяют это доказательство.
3. Фразы с уже завершённым действием («Принтер уже установлен») не генерируют мутирующие команды установки.
4. Исправление заявителем имени ПК в комментарии тикета не игнорируется системой.
5. Текущая реализация проходит размеченные регрессии, запрещённые действия и выбор цели. Намеренное исправление ошибочного baseline допустимо и отражено в разметке; совпадение с историческим ответом само по себе не является критерием.
6. Изменение цели до допуска мутации аннулирует согласование; недоступность проверки приостанавливает действие. Повтор доставки не создаёт вторую команду.
7. Создание AD-учётки допускается только после успешной проверки отсутствия; завершение подтверждает запись по логину и доступность реквизитов. Утраченный пароль не приводит к повторному созданию или неявному сбросу.
8. Результаты AD/принтера неизвестной достоверности и ошибки доставки отображаются раздельно; комментарий не заявляет больше, чем подтверждено postconditions.
9. Для нового holdout и пилота опубликованы абсолютные числа, покрытие и ограничения. Если экспертная разметка или стенд ещё не завершены, offline-часть может быть готова, но переход к автоматическому исполнению остаётся незавершённым.
10. Все строки матрицы раздела 4.4 и обязательные сочетания имеют тесты с ожидаемым исходом; отзыв/удаление источника и старое событие не восстанавливают прежнюю цель.
11. Отмена после возможной мутации сохраняет неизвестный исход до сверки, а не сообщает «ничего не выполнено»; изменение прав/статуса заявки блокирует новые действия.
12. Погашение секретного артефакта не выдаётся за доказанное получение пароля клиентом; конкурирующая выдача, потеря ответа и истечение TTL имеют проверенный исход и не запускают повторное создание учётки.
