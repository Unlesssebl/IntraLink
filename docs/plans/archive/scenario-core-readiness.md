# План доведения сценарного ядра IntraLink до эксплуатационной готовности

Дата: 2026-09-08.

Статус: план реализации. Пункты ниже не считаются выполненными на основании предыдущего отчёта об улучшении сценарного движка.

## 1. Цель и исходное состояние

Подготовить общий механизм, на котором новые сценарии заявок могут надёжно исполняться в полуавтоматическом и автоматическом режимах. Пилот — установка сетевого принтера. Расширение автоматического допуска создания пользователей и WLAN не входит в этот этап.

В проекте уже существуют версии сценариев, требования к фактам, политики допуска, Command Bus, outbox, журнал событий и проверки результата на worker. Реализованы загрузка сохранённых фактов в автономный анализ, однократный сбор фактов, устойчивые ссылки на комментарии и блокировка создания команды при наличии активной операции.

Повторная проверка выявила четыре оставшихся ограничения:

| Ограничение | Основание в коде | Риск |
|---|---|---|
| Раздельное сохранение команды и шага | `CommandService.create()` выполняет `commit()` до записи оркестратором шага и `scenario_advanced` | После падения команда существует, а состояние сценария не соответствует ей |
| Отложенное событие участвует в дедупликации как обработанное | `advance()` записывает `ticket_event_deferred` с исходным `event_key` | Новые сведения могут не попасть в последующее решение |
| История одного оператора схлопывается до проверки валидности | `merge_observations()` заменяет элементы с одинаковыми `(source, source_ref)` | Позднее невалидное или истёкшее значение скрывает прежнее валидное |
| Фоновое продолжение исключает ручные запуски | Фильтры в `list_resumable()`, worker и `TicketRunRunner.advance()` | Полуавтоматический цикл не имеет гарантированного общего продолжения |

Предыдущие проверки: 59 целевых тестов прошли; 489 тестов прошли при исключении двух модулей; один тест конфликта версии прошёл на PostgreSQL. Последний не проверяет одновременное создание двух команд. В полном наборе остались шесть падений в telemetry и printer handler, происхождение которых нужно окончательно установить до выпуска.

## 2. Этап 1 — атомарный переход сценария

Основные компоненты: `CommandService`, `CommandDispatcher`, `TicketRunOrchestrator`, `DecisionJournalService`.

- [ ] Выделить внутренний метод создания команды без `commit()` и полного `rollback()`. Он выполняет валидацию, добавляет команду, события команды и outbox, затем делает `flush()`.
- [ ] Сохранить публичный `create()` как транзакционную обёртку для существующих самостоятельных вызовов. Сигнатура внешнего API не меняется.
- [ ] Перевести оркестратор на внутренний метод. В одной транзакции сохранять новые факты, операционное решение, команду, outbox, текущий шаг, версии запуска и событие перехода.
- [ ] Применить такую же границу к созданию команды финализации после успешного действия.
- [ ] Сбор сетевых данных и вызовы LLM выполнять до блокировки. После получения блокировки повторно проверять версию запуска и актуальность решения.
- [ ] Привести пересекающиеся пути к порядку блокировок «запуск → команда»: создание, claim, согласование, отмена и сверка. Для определения запуска разрешено предварительно прочитать идентификатор без блокировки, затем перечитать команду под блокировкой.
- [ ] Исключить внутренние commit из всех вызываемых в этой транзакции методов. Ошибки уникальности обрабатывать на границе транзакции, затем перечитывать уже созданный результат в новой транзакции.
- [ ] Отделить внешнюю доставку от транзакции перехода. Сбой HTTP-публикации не откатывает подтверждённое исполнение; используется существующая сверка доставки.

Приёмка:

- Инъекция ошибки после добавления команды, но до события запуска, не оставляет ни команды, ни outbox, ни частично увеличенных версий.
- После успешного commit команда, решение и событие доступны вместе.
- Два параллельных `advance()` из разных PostgreSQL-сессий оставляют не более одной активной команды. Проигравший вызов возвращает контролируемый конфликт или существующий результат.
- Claim не блокирует собственную queued-команду; новый create блокируется чужой активной командой.

## 3. Этап 2 — надёжная обработка отложенных событий

Основные компоненты: `TicketRunOrchestrator`, `TicketRunEvent`, фоновый runner.

- [ ] Разделить получение события и применение его сведений. `ticket_event_deferred` не является доказательством успешной обработки.
- [ ] Для новых отложенных записей использовать ключ с отдельным префиксом; исходный ключ хранить в `details_json.source_event_key`. Для применения использовать исходный ключ и событие `scenario_advanced` либо отдельную запись о поглощении события актуальным снимком.
- [ ] Изменить дедупликацию: проверять тип события, а не только наличие любого совпавшего ключа.
- [ ] После завершения активной команды находить отложенные события, заново читать актуальную заявку и историю. При недоступности IntraService сохранять ожидание без отметки об обработке.
- [ ] Несколько изменений обрабатывать одним актуальным снимком. Связь поглощённых событий с решением сохранять в журнале в той же транзакции, что и переход.
- [ ] Перед финализацией проверять ожидающие изменения. Изменение цели или параметров уже выполненного действия переводит запуск на ручную проверку без автоматического закрытия и повторного исполнения.
- [ ] Поддержать старые `ticket_event_deferred`, где исходный ключ записан непосредственно в `event_key`: считать их ожидающими до появления отдельной записи об обработке. Для такого события использовать новый ключ применения, чтобы не нарушать существующий уникальный индекс.
- [ ] Запись отложения выполнять под блокировкой запуска с повторной проверкой статуса команды и существования события.

Приёмка:

- Ответ во время `awaiting_approval`, `queued` или `running` не создаёт вторую команду и учитывается после освобождения запуска.
- Повторный poll не дублирует ни отложенную запись, ни изменяющее действие.
- Перезапуск между отложением, сверкой команды и обработкой снимка не теряет событие.
- Изменение ПК во время установки блокирует автоматическую финализацию и оставляет объяснение инженеру.

## 4. Этап 3 — корректная история ручных фактов

Основные компоненты: `merge_observations()`, `TicketFactStore`, endpoint коррекции фактов.

- [ ] Не схлопывать operator-наблюдения по `source_ref`. Сохранять их последовательность полностью в наборе для разрешения факта.
- [ ] Выбирать последнее валидное неистёкшее ручное значение. Более позднее невалидное, missing или истёкшее наблюдение не скрывает предыдущее валидное — это сохраняет ранее принятый контракт.
- [ ] Гарантировать устойчивый порядок записи под блокировкой запуска. Для operator-наблюдений назначать серверное время, строго возрастающее относительно последнего записанного ручного наблюдения; разрешение одинаковых времён случайным UUID не использовать как порядок ввода.
- [ ] Сохранить приоритет остальных источников и конфликты разных комментариев одинакового приоритета.
- [ ] Сохранить все исходные наблюдения для объяснения решения; схлопывание снимков других источников применять только к выбору актуального значения.

Приёмка:

- Один и тот же оператор с одним `source_ref` вводит `PC-A`, затем `PC-B`: выбран `PC-B`.
- Следующее невалидное или истёкшее значение не скрывает `PC-B`.
- Результат одинаков до и после новой DB-сессии, в том числе при совпадающих исходных временных метках.
- Два разных комментария с конфликтующими ПК продолжают давать `conflicting`.

## 5. Этап 4 — единое продолжение обоих режимов

Основные компоненты: `TicketRunService.list_resumable()`, `TicketRunRunner`, lifecycle worker, регистрация сценарных запусков.

- [ ] Включить в фоновую обработку явно запущенные сценарные циклы обоих режимов.
- [ ] Для новых запусков сохранять в существующем `trigger_snapshot_json` признак `execution_requested=true` при явном старте сценария. Обычная коррекция фактов и ручное редактирование карточки этот признак не устанавливают.
- [ ] Старые manual-запуски со связанной командой допускать к сверке результата и доставки; новый сценарий автоматически для них не начинать. Старые autopilot-запуски сохраняют текущий порядок продолжения.
- [ ] Убрать безусловный выход для `manual` в runner и worker, заменив его проверкой права продолжать конкретный сценарный цикл.
- [ ] После согласования автоматически выполнять ожидание результата, верификацию и доставку. Новое инфраструктурное действие полуавтоматического цикла требует нового допуска.
- [ ] Эффективный допуск вычислять в сервисе команд: запрет политики обязателен; manual-сценарий требует согласования инфраструктурного действия даже при AUTO-политике; autopilot использует разрешённую политику AUTO/HITL. Публикация и финализация сохраняют свою отдельную политику действия.
- [ ] Отключение глобального автопилота блокирует новые автоматические инфраструктурные действия, но сохраняет сверку начатых операций и доставку результатов.
- [ ] Ручная пауза и внешнее закрытие блокируют новые действия в обоих режимах. Неопределённый исход уже начатого действия фиксируется для проверки.

Приёмка:

- Полный цикл принтера проходит в обоих режимах на одном механизме продолжения.
- Manual-сценарий ждёт согласования, после него доходит до результата без ручного продвижения по шагам.
- Редактирование фактов само по себе не инициирует инфраструктурную операцию.
- Отключение автопилота не теряет завершение уже начатой команды.

## 6. Проверки и выпуск

### Автоматические проверки

- [ ] Добавить регрессии каждого этапа до объявления его завершённым.
- [ ] На изолированном PostgreSQL проверить реальные конкурентные `advance()`, create/claim, обработку одного события двумя исполнителями и откат транзакции. Тест только оптимистического конфликта версии недостаточен.
- [ ] Добавить сценарии потери ответа worker, перезапуска Core API, частичного ответа пользователя и недоступности IntraService после успешной установки.
- [ ] Проверить сохранение старых закреплённых версий сценариев и старых отложенных событий.
- [ ] Устранить или доказательно отделить шесть известных падений полного набора. Для printer handler использовать изолированные локальные тестовые файлы вместо обращения к реальному UNC; telemetry-тесты сверить с актуальными точками подмены и отдельно проверить поведение сервиса.
- [ ] Прогнать полный набор Core API, проверку diff и необходимые проверки типов/синтаксиса. Исключённые модули и непройденные проверки явно отражать в отчёте.

### Пилот и порядок поставки

1. Реализовать атомарность переходов.
2. Реализовать обработку отложенных событий.
3. Исправить историю ручных фактов.
4. Подключить оба режима к общему продолжению.
5. Выполнить автоматические проверки на SQLite и изолированном PostgreSQL.
6. На выделенном Windows-ПК проверить установку принтера, повторный запуск при уже достигнутом состоянии и восстановление после прерывания.
7. В shadow-режиме сравнить выбор сценария с размеченными обезличенными заявками, включая неисправности и неполные запросы. Одного совпадения с прежним алгоритмом недостаточно.
8. Провести полный HITL-цикл и проверить журнал. Включать AUTO для пилота только после успешных предыдущих проверок через существующую политику `install_printer`.

### Критерий готовности ядра

Ядро готово к расширению автономного исполнения, когда подтверждены все условия:

- Нет частично сохранённого перехода и повторной изменяющей операции в конкурентных проверках.
- Отложенные сведения не теряются после сбоя и не позволяют ошибочно закрыть заявку.
- Последнее действующее ручное исправление переживает перезапуск.
- Оба режима проходят полный цикл; ручная коррекция карточки не запускает сценарий сама по себе.
- Неопределённый результат не приводит к слепому повтору операции.
- Подтверждённое исполнение и доставка результата учитываются независимо.
- Сквозной пилот прошёл на Windows; ограничения полного набора тестов устранены либо явно объяснены доказательствами.

## 7. Ограничения и совместимость

- Существующие незакоммиченные изменения принадлежат пользователю и сохраняются.
- План не требует новых таблиц: используются текущие события и JSON-контекст запуска. Внешние сигнатуры API сохраняются; внутреннее создание команды получает отдельную транзакционную границу.
- Имеющиеся политики, сценарии и правила проверки результата не заменяются новым движком.
- Настройка рабочего окружения и AUTO выполняется только после выполнения соответствующих критериев, а не автоматически вслед за изменением кода.
- Предыдущий документ `implementation_plan.md` остаётся отдельным планом запуска создания учётных записей. Его эксплуатационные настройки не являются критериями готовности общего ядра.

## 8. Отчёт по завершении

Для каждого этапа указать изменённое поведение, добавленные тесты и фактический результат проверки. Отдельно перечислить выполненные испытания на PostgreSQL и Windows, состояние shadow/HITL/AUTO и оставшиеся ограничения. Не объявлять весь план завершённым по результату только модульных тестов.
