## 1. Контекст и предпосылки

В монорепозитории IntraLink функционирует гибридный AI Hub с поддержкой двух типов инференса:
1. **Локальная модель (Ollama):** `qwen2.5:1.5b` (или 7B), запускаемая локально на клиентском/серверном GPU (NVIDIA GeForce RTX 3050 с ограниченным VRAM 4–8 ГБ). Применяется для контура **RED** (учетные данные, пароли, изолированная сеть) и как локальный fallback.
2. **Облачный шлюз (LiteLLM Proxy):** Gemini Flash (`intralink-chat`), применяемый для контуров **YELLOW** (десенсибилизированные данные через PII Vault) и **GREEN** (общие IT-вопросы).

### 1.1. Выявленные технические инсайты (Архитектурный аудит 10.09.2026)
- **Thinking Tokens и обрыв по MAX_TOKENS:** Модели Gemini (поколения 2.5 и 3.x) расходуют скрытые токены на цепочки рассуждений (`thoughtsTokenCount`). При малых лимитах (`max_tokens: 150–300`) бюджет токенов исчерпывается размышлениями, приводя к обрыву текста на полуслове (`finishReason: MAX_TOKENS`). Необходим минимальный базовый резерв `AI_CLOUD_MAX_TOKENS = 1536`.
- **Многоключевой пул Free Tier в LiteLLM:** Регистрация нескольких ключей под единым алиасом `intralink-chat` со стратегией `least-busy` и `cooldown_time: 60` удваивает пропускную способность Free Tier и гарантирует бесшовный failover без ошибок 429 для пользователя.
- **Безопасность развертывания ключей:** Использование безопасного fallback `${GEMINI_API_KEY_2:-${GEMINI_API_KEY}}` в `docker-compose.yml` исключает ошибки 400/401 на средах с единственным ключом.
- **Circuit-Aware Slicing:** При срезе RAG необходимо учитывать динамически вычисленный контур (`eval_circuit`), а не только исходный параметр запроса.
- **Аудит исторического снимка 99 заявок (`decisions.json`):**
  - *Тотальная шаблонность старого движка:* 100% ответов (99 из 99) генерировались в режиме `template`, из них 83.8% (83 заявки) получали одинаковую отписку `in_work_standard` без инженерной помощи.
  - *Ложные отмены и циклический пинг-понг:* В заявках #139762 (тормоза всей ОС, сети и ПК) и #140686 (переустановка ОС по рекомендации 1С) система ошибочно отменяла заявки со статусом `wrong_service`, цепляясь за ключевое слово «1С».
  - *Сбои типизации периферии:* Заявки на подключение колонок (#140408) и проводных наушников (#140511) классифицировались как принтеры с требованием IP-адреса `10.244.***.***`.
- **Ограничение параметров Gemini API (No Penalty Support):** Передача параметров `frequency_penalty` или `presence_penalty` в Google Gemini через LiteLLM вызывает ошибку `HTTP 400: Penalty is not enabled for this model`. Предотвращение зацикливаний токенов (патологических повторов слов при жадном семплировании) реализовано на уровне клиентской regex-санитации в `AIHub` (`re.sub(r'(\b\w+\b)(?:\s+\1){3,}', r'\1', content)`).
- **Разграничение ролевых обязанностей в `system_prompt`:** В системный промпт инженера первой линии заложено строгое правило: запрещено требовать от пользователя самостоятельной переустановки Windows или правки реестров; также запрещен запрос IP сетевого принтера для аудиопериферии и мышей.

### Выявленная проблема
Подача одинакового количества RAG-прецедентов (3–5 документов) в локальную легковесную модель и в облачную Frontier-модель нарушает фундаментальные принципы машинного обучения:
- **Эффект «Lost in the Middle» у компактных моделей:** Модели класса 1.5B/7B путают детали нескольких решений (смешивают шаги настройки разных марок принтеров, путают IP-адреса хостов и ключи реестра), галлюцинируют и нарушают Zero-Emoji политику.
- **Ограничения VRAM и пропускной способности GPU (Memory Bandwidth):** На RTX 3050 раздувание промпта длинными прецедентами увеличивает KV-кэш и приводит к неприемлемым задержкам инференса (>20-30 секунд на заявку).
- **Когнитивный шум множественных ответов:** Генерация 2–3 альтернативных вариантов ответа в Helpdesk создаёт лишний шум для инженера первой линии. По умолчанию должен генерироваться **ровно один каноничный, заземленный ответ**.

## 2. Архитектурные принципы и SSOT

### Принцип 1. Model-Adaptive Context Budgeting (Capacity-Aware Prompting)
- **Для локальной модели (`Ollama / RED`):** в промпт включается **строго 1 (максимум 2)** наиболее релевантных прецедента после Cross-Encoder реранкера (`threshold >= 0.80`). Это исключает галлюцинации и обеспечивает быстрый инференс (1.5–2.5 сек).
- **Для облачной модели (`LiteLLM / YELLOW / GREEN`):** в промпт передается **до 3–4 прецедентов**, что позволяет модели сопоставить смежные случаи и сформировать взвешенный синтез.
- Настройки выносятся в `.env` через Pydantic Settings:
  - `AI_OLLAMA_MAX_RAG_MATCHES: int = 1`
  - `AI_CLOUD_MAX_RAG_MATCHES: int = 3`

### Принцип 2. Single Grounded Answer по умолчанию
- Система **не заставляет** оператора читать несколько вариантов и делать выбор.
- На выходе формируется один структурированный, заземленный на факты комментарий заявителю от первого лица инженера Helpdesk («Я проверил...»).

### Принцип 3. On-Demand Tone Orchestration (Смена тона по требованию)
- Если инженеру требуется изменить формулировку, в панели `UnifiedActionDock` Инспектора доступно выпадающее меню кнопки **«AI Ответ»**:
  1. ⚡ **Краткий статус (`concise`):** 1–2 лаконичных предложения о статусе диагностики или принятии в работу без лишних подробностей.
  2. 📋 **Подробная инструкция (`detailed`):** Пошаговый алгоритм решения, пути реестра, команды cmd/powershell для заявителя.
  3. 🏛️ **По регламенту (`regulatory`):** Строгий корпоративный шаблон (АХО, пароли, перенаправление) без генеративных вольностей.

### 3.1. Core API Backend

#### А. Конфигурация ([`core-api/app/config.py`](file:///F:/Work/Projects/IntraLink/core-api/app/config.py))
```python
# Параметры адаптивного контекста RAG и синтеза ответов

    1, ge=1, le=5, description="Лимит прецедентов RAG, передаваемых в локальную модель Ollama"
)
AI_CLOUD_MAX_RAG_MATCHES: int = Field(
    3, ge=1, le=10, description="Лимит прецедентов RAG, передаваемых в облачный LiteLLM"
```

#### Б. Срез контекста и генерация тонов ([`core-api/app/services/ai_synthesis.py`](file:///F:/Work/Projects/IntraLink/core-api/app/services/ai_synthesis.py))
1. **Capacity-Aware Slicing:**
   ```python
   is_local_circuit = (eval_circuit == DataCircuit.RED) or (settings.LLM_PROVIDER_PREFERENCE == "ollama_only")
   max_kb = settings.AI_OLLAMA_MAX_RAG_MATCHES if is_local_circuit else settings.AI_CLOUD_MAX_RAG_MATCHES
   effective_kb_matches = (kb_matches or [])[:max_kb]
   ```
2. **Директивы тональности в системном промпте:**
   - При `tone == "concise"`:
     > «СТИЛЬ КРАТКОГО СТАТУСА: Сформируй предельно лаконичный ответ (строго 1-2 предложения). Укажи только факт взятия в работу или текущий статус проверки хоста без длинных рассуждений.»
   - При `tone == "detailed"`:
     > «СТИЛЬ ПОДРОБНОЙ ИНСТРУКЦИИ: Сформируй структурированный пошаговый план (3-5 пунктов). Детально опиши шаги самодиагностики или инструкцию для заявителя.»
   - При `tone == "regulatory"`:
     > Принудительный переход на детерминированный регламентный шаблон компании без вызова LLM.

#### В. Роутер и разделение кэша в Redis ([`core-api/app/routers/triage.py`](file:///F:/Work/Projects/IntraLink/core-api/app/routers/triage.py))
- Добавить параметр запроса `tone: str = Query("default", regex="^(default|concise|detailed|regulatory)$")` в эндпоинты `/api/v2/triage/tasks/{task_id}/analyze` и `/api/v2/triage/tasks/{task_id}/apply`.

## 5. Регрессионная верификация и приёмка

1. **Тест RAG Context Slicing:**
   - В контуре RED или с `ollama_only` в промпт попадает ровно 1 прецедент из базы знаний.
   - В контуре YELLOW/GREEN в промпт попадает до 3 прецедентов.
2. **Тест тональности ответа:**
   - `concise` возвращает лаконичный ответ длиной не более 2 предложений.
   - `detailed` возвращает пошаговый план.
   - `regulatory` мгновенно возвращает детерминированный корпоративный шаблон.
3. **Изоляция кэша Redis:**
   - Переключение между тонами не возвращает закэшированный текст другого тона.
4. **Сборка фронтенда:**
   - `npm test` проходит без ошибок.
   - `npm run build` компилирует единый бандл без TypeScript-ошибок.

## 6. Долгосрочное развитие (Best Practices & Production Evolution)

Следующие расширения зафиксированы как долгосрочные архитектурные ориентиры и реализуются планомерно без усложнения базового fast-fix:
1. **3-Уровневый каскад моделей в LiteLLM:**
   - Основной Flash (2 ключа Free Tier) ➔ Экономичный Flash-Lite (2 ключа Free Tier) ➔ Локальная аварийная Ollama (RTX 3050).
2. **Прозрачная сквозная телеметрия моделей:**
   - Фиксация фактически ответившей модели (Flash / Lite / Ollama) в метаданных `decision_envelope` и отображение соответствующего бейджа в UI Инспектора Helpdesk.
3. **Автоматический бенчмарк-раннер (`tools/benchmark_rag_capacity.py`):**
   - Автоматизированное тестирование задержек VRAM, времени инференса и связности текста при изменении количества прецедентов RAG и обновлении весов локальных/облачных моделей.
