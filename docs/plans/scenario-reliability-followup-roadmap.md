# Надёжность сценариев при свободном вводе: следующий этап

Дата: 2026-09-12. Статус: предложение по результатам проверки текущего checkout.

## Цель и границы

Уменьшить ошибочный выбор действия и устройства, повторные уточнения и ложные сообщения об успехе. Развивать существующие FactBag, ScenarioRegistry и worker SDK. Основной код в рамках этой проверки не изменялся; рабочие AD, IntraService и ПК не проверялись.

Этот документ дополняет `ticket-scenario-quality-roadmap.md`. Предыдущая приёмка подтверждает наличие архитектурных механизмов, но не полную точность на свободном тексте и не надёжность реального инфраструктурного исполнения.

## Подтверждённые наблюдения

1. **WLAN verify допускает ложное подтверждение.** В `handlers/grant_wlan.py::verify` отсутствие членства не считается ошибкой при `result.payload.already_member=true`. Изолированный вызов с `status.found=true`, пустыми `groups` и `already_member=true` вернул успех. В preflight/verify/reconcile принадлежность определяется подстрокой имени группы, что также требует замены на точную идентичность.
2. **Matcher установки не различает действие и завершённое состояние.** `_printer_install_match` вернул `(True, 0.94, 'установ')` для «Принтер уже установлен, нужна помощь». Это воспроизведение matcher, а не доказательство отправки команды: дальнейшие routing/policy/approval остаются отдельными барьерами.
3. **Grounding AI проверяется формально.** `_llm_evidence_is_valid` требует непустые span и source=llm, но не сверяет span с исходным документом. `collect_llm` связывает поле с цитатой, но также не проверяет её присутствие и переносит `ambiguities` не в состояние каждого факта. Непустая выдуманная цитата проходит проверяемую функцию. Влияние зависит от режима extraction; текущий runtime-режим не проверялся.
4. **Нормализация не равна проверке адреса.** `normalize_printer_address('999.244.1.20')` возвращает строку без ошибки. В `_observation` специальная валидация есть для `pc_name`, остальные непустые нормализованные значения по умолчанию получают VALID. Это дефект границы фактов, а не утверждение, что worker успешно подключится к такому адресу.
5. **Конфликт проверяется только внутри лучшего приоритета.** `merge_observations` сравнивает значения authoritative-источников. ПК из поля и другой ПК из комментария не становятся CONFLICTING только из-за различия значений. Для явного исправления заявителем это может сохранить старую цель. Операторская коррекция поддержана отдельно.
6. **Текстовые источники собираются неодинаково.** LLM extractor и `_text` сценариев используют разные наборы ключей комментариев и правила отбора. Детерминированные collectors отдельно читают комментарии. Нужен общий нормализованный контракт, чтобы одинаковая переписка давала одинаковые основания.
7. **Проверка принтера уже существует.** `InstallPrinterHandler.verify` сравнивает имя очереди, имя порта и имя драйвера. Она не подтверждает физическую печать; не проверяет версию драйвера, несмотря на более широкую формулировку в заголовке файла. Это нужно отразить в контракте результата.

## Выбор подхода

| Вариант | Польза | Цена и ограничения |
|---|---|---|
| Только дописывать regex и шаблоны | Быстрые исправления конкретных фраз | Не решает связи между устройствами, исправления в истории и ложное verify |
| Усилить существующие факты, intent и verification — рекомендуется | Сохраняет инфраструктуру, даёт проверяемые основания для команды | Требует разметки и нескольких последовательных изменений |
| Новый универсальный LLM-агент/отдельный workflow engine | Потенциально широкий охват формулировок | Новая миграция и поверхность отказов; текущие проблемы этого не требуют |

## Этап 0. Регрессионные случаи и строгий verify

Приоритет: первым, до расширения автоматического исполнения.

- `handlers/grant_wlan.py`, `executors/ad.py`: разрешать успех только после свежего подтверждения точной целевой группы для точного пользователя. Предпочитать DN/SID, явно определить прямое или транзитивное членство. `already_member` описывает предыдущий результат, но не заменяет verify.
- Сохранить неизвестный исход при недоступной проверке; не отправлять повторную мутацию автоматически. Повторное чтение может быть ограничено по времени с учётом задержек AD.
- `tests/test_grant_wlan_handler.py`: добавить случаи «раньше состоял, теперь не состоит», похожая группа `WLAN-WORKNET-TEST`, ошибка чтения после успешного изменения, повторная доставка команды.
- `tests/test_scenario_mapping.py`, `test_fact_extractor.py`: зафиксировать ошибочную интерпретацию завершённого действия и выдуманную цитату.

Готово: неподтверждённое членство не даёт verified success; интеграционная проверка цепочки handler → command → finalization не допускает статус 29 и успешный комментарий при неизвестном исходе.

## Этап 1. Проверяемые значения и ссылки на исходный текст

- `shared/normalizer.py`: сохранить старые строковые функции для совместимости, добавить результат разбора с `raw_value`, `normalized_value`, `normalization_steps`, списком кандидатов и неоднозначностью. При равном расстоянии до нескольких префиксов не выбирать первый по порядку.
- `facts/registry.py`: добавить валидаторы фактов. IPv4 проверять через `ipaddress`; hostname проверять отдельно. Синтаксически корректное имя не считать доказательством существования или принадлежности ПК заявителю.
- `intraservice_parser.py`: перейти от regex по XML к структурному разбору; сохранить отдельные значения по ID и не терять конфликты из-за одинаковых friendly-названий. Покрыть экранирование, дополнительные атрибуты, пустые и повторные поля.
- Общий формат текстового источника: тип, ID поля/комментария, автор, время, исходный текст. Использовать его в collectors, fact_extractor и сценариях. Оригинал сохранять отдельно от очищенного текста с явным сопоставлением фрагментов.
- `fact_extractor.py`, `collectors.py`: проверять существование цитаты в указанном источнике и связь цитаты с конкретным значением. Нормализация значения должна быть воспроизводимой; выдуманные значения/цитаты отклонять. Неоднозначность конкретного поля должна давать AMBIGUOUS, а не VALID.
- Не разрешать нормализатору worker заново исправлять уже подтверждённую цель: команда должна содержать проверенный канонический идентификатор.

Готово: каждый параметр команды трассируется до входного значения и проверки; неверный IPv4 и неоднозначное исправление не допускаются к мутации. Тесты включают русскую раскладку, омоглифы, перепутанные поля, несколько ПК и выдуманные AI-цитаты.

## Этап 2. Намерение, связи устройств и исправления в истории

- `scenarios/builtin.py`: разделить признаки запроса действия, отрицания, симптома и завершённого действия. Покрыть «установите», «уже установлен», «не устанавливайте», «после установки перестал печатать», «переустановка не помогла».
- Расширить существующие `printer_targets` и FactBag вместо второго независимого хранилища: привязывать модель, адрес, тип подключения и целевой ПК к одному объекту. Хранить роли «старый», «новый», «нужный», «упомянутый в истории».
- `facts/merger.py`: добавить политику конфликтов для фактов-целей. Явное новое исправление заявителем должно либо заменять устаревшее наблюдение с доказанной связью supersedes, либо требовать уточнения. Простое «брать самый свежий комментарий» недопустимо.
- Привязать `clarification_answer` к вопросу, факту и версии сценария; повторный анализ не должен задавать уже отвеченный вопрос.
- `scenario_pipeline.py`, `fact_extractor.py`: вызывать AI после детерминированного сбора для нерешённых фактов/отношений. Сейчас collectors запускаются совместно, а критерии пропуска AI в extractor во многом привязаны к ФИО, не к потребностям конкретного сценария.
- При нескольких независимых намерениях сначала возвращать оператору отдельные предложения; не строить автоматическую цепочку мутаций на первой итерации.

Готово: пары «запрос/отрицание/прошлое действие» дают разные решения; «не на старый ПК X, а на новый Y» не выбирает X; модель и адрес разных принтеров не объединяются; неоднозначность приводит к одному предметному уточнению.

## Этап 3. Контракт исполнения и сообщения о результате

- Уточнить контракт сценария: обязательные факты по ветке, разрешённые действия, preflight, обязательные verify и допустимые утверждения в комментарии. Использовать существующие ScenarioDefinition/PlanStep; не создавать второй движок сценариев.
- `handlers/install_printer.py`: проверять параметры фактического порта (адрес/протокол), а не только имя; версию драйвера включать только при наличии заданной ожидаемой версии. Разделить результаты «очередь настроена» и «печать подтверждена».
- `sdk/base.py`, `sdk/lease_renewer.py`, `worker.py`: fault injection для потери lease, остановки процесса после изменения, сбоя verify и cleanup. Сохранить существующий запрет автоматического повтора мутаций, добавить/подтвердить read-only reconcile каждого сценария.
- `decision_application_service.py`, `scenario_orchestrator.py`: сквозные проверки изменения цели после согласования, повторной доставки, неизвестного ответа IntraService после успешного действия. Повторять доставку подтверждённого результата отдельно от инфраструктурной команды.
- `decision_compiler.py`, шаблоны: формировать утверждения об успехе из подтверждённых postconditions. Ошибка доставки комментария не должна запускать установку повторно.

Готово: для каждой мутации есть наблюдаемый postcondition и восстановление после обрыва; повторная доставка не меняет другую цель и не дублирует действие; частичный результат не называется полным успехом.

## Этап 4. Доказательство качества и постепенное включение

- Доработать разметку текущих 99 случаев: по README подтверждены только 4, ещё 95 требуют экспертной оценки. Не использовать 4/4 как общую точность.
- Для пилота выбрать установку принтера, диагностику печати и WLAN; окончательный порядок уточнить по фактической частоте и последствиям ошибок. Добавить реальные обезличенные варианты и искусственные опасные контрпримеры.
- Разделять разработочную и отложенную выборки; близкие дубликаты и варианты одной заявки держать в одной части. Для каждой разметить intent, цели, обязательные уточнения, запрещённые действия и ожидаемый verify.
- Метрики: точность выбора цели среди допущенных действий, ложные допуски, доля полезной автоматизации, лишние/повторные вопросы, ложный успех, задержки p50/p95. Показывать абсолютные числа и результаты по сценарию, режиму AI и типу источника.
- Сначала replay без сети, затем shadow на живом чтении, затем исполнение с подтверждением оператора и только затем ограниченное auto для отдельных сценариев. Существующий killswitch и режим подтверждения использовать для отката.
- Блокирующие критерии: любой известный тест на неверную цель, запрещённую мутацию или ложный успех не проходит — выпуск остановлен. Для метрик удобства установить пороги после baseline; ноль ошибок на малой выборке не доказывает отсутствие риска.

## Проверка в этой сессии

Команда:

```powershell
uv run --no-sync pytest core-api/tests/test_fact_extractor.py core-api/tests/test_scenario_mapping.py core-api/tests/test_grant_wlan_handler.py core-api/tests/test_intraservice_parser.py -q --disable-warnings
```

Результат: **23 passed, 2 warnings in 4.36s**. Это выборочный прогон, не полный CI.

Дополнительно выполнены изолированные проверки функций из текущих исходников: matcher установки, нормализация IPv4, проверка AI evidence, WLAN verify. Matcher и verify загружались из AST с подставленными входами; сетевые запросы не выполнялись. Результаты описаны выше и должны стать постоянными регрессионными тестами при реализации.

Рекомендуемая последовательность изменений: verify WLAN → валидаторы и grounding → intent/конфликты → контракты исполнения → пилот. Разметку и replay развивать с первого этапа. RAG оставить опциональным источником консультаций; качество сценариев не должно зависеть от наличия похожего закрытия.
