## 0. Декомпозиция плана на инкременты

План декомпозирован на 5 изолированных, независимо тестируемых инкрементов в папке [`worker-platform/`](worker-platform/README.md):

1. **[Инкремент 1: Контракт и Core API Safety](worker-platform/01-contract-and-core-safety.md)** — актуализация ADR 0002, баг-фикс retry в `command_outbox.py`, блокировка AUTO для mutating-действий, эндпоинт продления lease.
2. **[Инкремент 2: Worker SDK и доверенный PowerShell Runner](worker-platform/02-worker-sdk-and-runner.md)** — интерфейс `ActionHandler` (7 фаз), реестр, запуск runner через stdin/tempfile с ACL и `-ArgumentList`, cooperative cancellation.
3. **[Инкремент 3: Durable Workflow & Approval с plan_hash](worker-platform/03-durable-workflow-and-plan-hash.md)** — привязка approval к `plan_hash` и сроку годности, durable-сохранение фаз и execution evidence в PostgreSQL.
4. **[Инкремент 4: Эталонный InstallPrinterHandler и SMB Staging](worker-platform/04-printer-pilot-and-staging.md)** — обход Kerberos Double-Hop через SMB staging с SHA-256, WMI-bootstrap в `prepare`, запрет generic fallback, точный verify и cleanup.
5. **[Инкремент 5: Worker Fleet, Routing Quarantine и Отказоустойчивость](worker-platform/05-fleet-routing-and-resilience.md)** — регистрация узлов в Redis, маршрутизация по пулам, серверный routing quarantine, комплексные стресс-тесты.

## 1. Цель

Превратить существующий `execution-worker` в безопасную модульную платформу умений, сохранив текущий фундамент: PostgreSQL как источник истины, transactional outbox, Redis Streams и Command API v2.

Ожидаемый результат:

- новое умение подключается без изменения главного цикла worker-а;
- несколько Windows worker-узлов безопасно работают параллельно;
- состояние каждого узла и каждой команды прозрачно оператору;
- изменяющие действия не повторяются автоматически при неизвестном результате;
- заявка закрывается только после проверяемого подтверждения фактического выполнения.

## 2. Рамки

### В рамках

- унификация контрактов умений;
- безопасное исполнение Windows-команд;
- корректные lease, distributed lock и retry;
- capability-based маршрутизация между worker-узлами;
- наблюдаемость и эксплуатационные статусы;
- принтер как первый эталонный end-to-end сценарий;
- постепенный вывод legacy v1 и неиспользуемых Pub/Sub-маршрутов.

### За рамками

- замена PostgreSQL или Redis;
- внедрение Kubernetes, Temporal либо нового брокера сообщений;
- переработка AI/RAG и интерфейса очереди;
- одновременная миграция всех существующих сценариев;
- включение автономного исполнения изменяющих действий до прохождения пилота.

## 3. Архитектурные инварианты

1. PostgreSQL остаётся источником истины для команд, approvals, attempts и результатов.
2. Redis Streams используется только как транспорт с доставкой at-least-once.
3. Статус заявки не переводится в финальный без проверяемого execution evidence.
4. Изменяющая команда с неизвестным исходом переходит в `needs_review`, а не запускается повторно.
5. Системный сбой не создаёт публичный комментарий заявителю.
6. До подтверждения оператора выполняются только валидация и read-only preflight; любое изменение хоста начинается после approval.
7. Невалидные или несовместимые параметры не передаются Windows worker-у.
8. Старые клиенты поддерживаются в течение ограниченного миграционного окна.
9. Недоступность worker-а отображается как operational degradation, но не блокирует просмотр и ручной триаж очереди.
10. Mutating-handler начинает новую фазу только при действующих command lease и host lock; потеря любого владения закрывает вход в следующую фазу.
11. Approval связан с неизменяемым планом исполнения: версией команды, нормализованными параметрами, preflight evidence, сроком годности и `plan_hash`.
12. Exactly-once для внешнего Windows side effect не обещается: при неопределённом исходе запрещён автоматический повтор и обязателен `reconcile` либо ручной разбор.

## 4. Этапы

### Этап 0. Зафиксировать архитектурный контракт

Подготовить ADR, определяющий:

- границы Core API, workflow и execution-worker;
- единый интерфейс `ActionHandler`;
- классы риска и правила повторов;
- версионирование входных и выходных контрактов;
- жизненный цикл команды;
- модель регистрации и выбора worker-узлов;
- durable-состояния фаз, evidence и привязку approval к `plan_hash`;
- топологию capability-specific worker pools и правила обработки ошибочной маршрутизации.

Критерий выхода: согласован единый контракт, относительно которого проверяется дальнейшая реализация.

### Этап 1. Закрыть критические риски

- исключить PowerShell-инъекции на обеих границах: фиксированный локальный runner, JSON через stdin или защищённый временный файл, фиксированный удалённый `ScriptBlock` с `-ArgumentList`; `-EncodedCommand` допускается только как транспорт фиксированного кода;
- запретить автоматический retry `install_printer`, `apply_triage` и других mutating-команд;
- перенести WinRM/WMI bootstrap после approval, сохранять исходные `State`/`StartMode` и ownership token, восстанавливать состояние только при доказанном владении и отсутствии конфигурационного дрейфа;
- добавить продление command lease и host lock с **best-effort cooperative cancellation**: потерявший владение worker прекращает запуск новых фаз, пытается остановить локальную и удалённую сессии, а результат переводит в `needs_review`;
- использовать монотонные таймеры (`time.monotonic()`) и относительный `lease_ttl_seconds` от Core API для защиты от рассинхронизации часов (Clock Skew);
- для mutating-команд сделать потерю Redis или Core API fail-closed до первого side effect;
- до завершения пилота оставить изменяющие действия в режиме `CONFIRM`.

Критерий выхода: критические риски закрыты тестами, реальное исполнение по умолчанию остаётся выключенным.

### Этап 2. Создать Worker SDK

Ввести единый интерфейс умения со следующими составляющими:

- идентификатор и версия;
- список capabilities;
- строгая входная Pydantic-модель;
- типизированный результат;
- `validate`, read-only `preflight`, `prepare`, `execute`, `verify`, `reconcile` и `cleanup`;
- retry-класс и уровень риска.

Заменить центральный `if/elif` на handler registry. Сначала адаптировать `diagnose_host` и `install_printer`, затем AD-действия.

Критерий выхода: новое умение подключается регистрацией handler-а без изменения главного цикла worker-а.

### Этап 3. Отделить workflow заявки от умения

Зафиксировать общий жизненный цикл:

```text
validate
  -> clarify при необходимости
  -> preflight (read-only)
  -> build execution plan + plan_hash
  -> approval (command_version + plan_hash + expires_at)
  -> prepare
  -> execute
  -> verify
  -> cleanup
  -> finalize
```

Workflow отвечает за статусы, approvals, комментарии и durable-переходы между фазами. В PostgreSQL сохраняются как минимум preflight evidence, `plan_hash`, approval, `execute_started`, результат verify, результат cleanup и причина неопределённого исхода. Handler отвечает только за инфраструктурное действие. На этом этапе не требуется полноценный BPMN-движок: достаточно небольшого набора типизированных шагов.

### Этап 4. Ввести модель worker fleet

Каждый worker-узел регистрирует:

- уникальный `node_id`;
- версию приложения и commit SHA;
- поддерживаемые actions и версии;
- домен и сетевые зоны;
- наличие PowerShell-модулей и драйверов;
- количество слотов и текущую нагрузку;
- heartbeat.

Маршрутизация по возможностям (Capability-based routing):

- Core API до публикации вычисляет стабильный `routing_key` и направляет команду в stream совместимого worker pool;
- consumer group объединяет только взаимозаменяемые узлы с одинаковым контрактом capability;
- worker повторно проверяет совместимость до claim;
- ошибочно доставленная команда атомарно фиксируется Core API как routing error/quarantine и подтверждается через `XACK` только после durable-фиксации; worker не выполняет самостоятельный `XADD + XACK` requeue.

Критерий выхода: добавление второго worker-а не создаёт риск исполнения команды на неподходящем узле и не приводит к зависанию несовместимых задач.

### Этап 5. Сделать исполнение наблюдаемым

Добавить метрики и эксплуатационное представление:

- список worker-узлов и capabilities;
- время последнего heartbeat;
- активные команды и занятые слоты;
- длительность `preflight`, `execute` и `verify`;
- очередь, consumer lag, PEL и DLQ;
- истечения lease и lock;
- success/failure по action и failure code;
- возраст самой старой команды;
- единый correlation ID от заявки до удалённой команды.

Разделить API readiness и operational readiness. Например: API доступен, ручной триаж доступен, Windows execution недоступен.

### Этап 6. Провести принтерный пилот

Принтер становится первым эталонным handler-ом:

- раздельные TCP/IP и USB-сценарии;
- обязательные `pc_name`, `connection_type` и подтверждённый профиль устройства;
- read-only preflight проверяет целевой ПК, профиль, для TCP/IP — адрес и порт `9100`, а также состояние `Spooler` на целевом ПК;
- после approval фаза `prepare` при необходимости выполняет контролируемый WinRM bootstrap;
- обход Kerberos Double-Hop: стейджинг драйвера из SMB-шары через узел воркера на локальный диск целевого ПК (`C:\Windows\Temp\_driver_staging\...`) с последующим локальным вызовом `pnputil.exe` и обязательной зачисткой;
- подбор драйвера строго из подтверждённого профиля KB с неизменяемыми версией и SHA-256 пакета;
- разрешены только allowlist SMB-корни; подпись и хеш драйвера проверяются до кеширования и после копирования, staging-каталог получает ограниченные ACL;
- полный запрет на generic fallback (никаких `"Generic / Text Only"`): отсутствие точного профиля переводит задачу на ручное уточнение оператору;
- verify по точному совпадению проверяет имя очереди, адрес порта, имя и версию драйвера и сохраняет эти значения как execution evidence;
- cleanup удаляет временные файлы стейджинга и восстанавливает исходное состояние WinRM только при доказанном владении; невозможность cleanup создаёт operational alert и `needs_review`;
- итоговый комментарий содержит фактически подтверждённый результат.

### Этап 7. Проверить отказоустойчивость

Обязательные сценарии:

- падение worker-а до исполнения и во время исполнения;
- потеря Redis после изменения инфраструктуры;
- истечение lease до side effect, во время локального PowerShell и после запуска удалённой команды;
- сценарий, в котором локальный PowerShell завершён, но удалённая операция продолжилась;
- дублирование сообщения;
- два worker-а на один ПК (host lock contention);
- недоступность Core API при завершении;
- повторный запуск после неизвестного результата;
- сбой cleanup WinRM и зависание spooler;
- недоступная SMB-шара или отсутствующий драйвер;
- устаревший approval или изменение `plan_hash` после подтверждения;
- передача задачи воркеру без нужной capability и durable routing quarantine без PEL-зависания.

Критерий выхода: неизвестный результат всегда приводит к `needs_review`, но не к автоматическому повтору или закрытию заявки.

### Этап 8. Canary и постепенное включение

1. Shadow mode: новый handler выполняет только preflight.
2. Один тестовый ПК и один тестовый принтер.
3. Ограниченный allowlist моделей и подсетей.
4. Один production worker с обязательным подтверждением.
5. Второй worker для проверки маршрутизации и блокировок.
6. Постепенное расширение allowlist.
7. Миграция остальных умений.
8. Удаление legacy v1 и неиспользуемых Pub/Sub-каналов.

## 5. Чувствительные решения

### 5.1. Граница PowerShell

Экранирование кавычек и строковая интерполяция пользовательских данных запрещены. `-EncodedCommand` решает только передачу фиксированного кода и не считается механизмом безопасности.

Границы транспорта разделяются явно:

1. Python запускает доверенный локальный runner. JSON-параметры передаются через stdin либо защищённый временный файл с ограниченными ACL, но не через командную строку.
2. Локальный runner вызывает WinRM с фиксированным `ScriptBlock`; нормализованные значения передаются через `-ArgumentList` в объявленные `param(...)`, а не встраиваются в текст скрипта.
3. Временный файл, если он использовался, удаляется в `finally`; секреты не включаются в payload без необходимости.

До передачи worker-у необходимо валидировать:

- host и DNS-имя;
- IPv4/IPv6;
- имя очереди;
- идентификатор профиля и драйвера;
- тип подключения;
- допустимость целевой сети и домена.

Секреты и исходные пользовательские строки не должны попадать в логи исполнения.

### 5.2. Классы повторяемости

Действия разделяются на три класса:

- `SAFE_RETRY` — диагностика и чтение;
- `RECONCILE_BEFORE_RETRY` — идемпотентное действие, перед повтором которого можно достоверно проверить фактическое состояние;
- `NEVER_AUTO_RETRY` — изменение заявки, AD и другие операции с потенциально неизвестным побочным эффектом.

Для `NEVER_AUTO_RETRY` потеря результата означает только `needs_review`.

Класс назначается каждому action в серверном registry и входит в версионируемый контракт. `install_printer` остаётся `NEVER_AUTO_RETRY` на время пилота; перевод в `RECONCILE_BEFORE_RETRY` допустим только после доказательства, что reconcile однозначно различает выполненное, невыполненное и неизвестное состояние.

### 5.3. Lease, distributed lock и Cooperative Cancellation

Command lease и host lock продлеваются активным worker-ом. `time.monotonic()` используется только для локального расписания heartbeat; источником истины остаётся Core API, возвращающий относительный `lease_ttl_seconds` и принимающий renew только с действующим claim token.

Host lock продлевается атомарной compare-and-expire операцией по owner token. Для mutating-команд ошибка Redis не допускает fail-open: без подтверждённого lock запрещено начинать `prepare`, `execute` или следующий необратимый шаг.

При потере command lease или host lock:

- worker немедленно прекращает запуск новых фаз и новых side effects;
- локальный PowerShell-процесс и известная удалённая WinRM-сессия останавливаются в best-effort режиме;
- остановка локального процесса не считается доказательством остановки удалённой операции;
- команда переходит в `needs_review`, после чего выполняется только read-only `reconcile`;
- Core API отклоняет progress и финализацию с устаревшим claim token.

Fencing token защищает серверное состояние, но не способен обеспечить exactly-once для неуправляемого Windows side effect. Безопасность достигается запретом автоматического повтора при неопределённом исходе, а не обещанием гарантированной остановки удалённой команды.

### 5.4. Подтверждение оператора

Approval запрашивается после read-only preflight и показывает:

- целевой ПК;
- устройство и тип подключения;
- выбранный драйвер;
- диагностические результаты;
- планируемое изменение, включая WinRM bootstrap и staging;
- срок годности диагностики.

Подтверждение сохраняется вместе с `command_version`, `plan_hash`, идентификатором оператора и `expires_at`. Любое изменение нормализованных параметров, профиля драйвера, плана действий или истечение preflight snapshot аннулирует approval и требует повторного подтверждения.

После действительного подтверждения отдельное согласование на закрытие не требуется, если verify успешен, cleanup завершён или явно учтён, а итоговый комментарий соответствует подтверждённому плану.

### 5.5. Capability-based routing и предотвращение зависаний в PEL

Worker не должен получать команду, которую не способен выполнить. Совместимость определяется Core API до публикации по action и версии handler-а, ОС, домену, сетевой зоне и обязательным локальным зависимостям.

В среде Redis Streams с Consumer Groups:

- используются отдельные streams/consumer groups для стабильных, взаимозаменяемых worker pools;
- Core API сохраняет выбранный `routing_key` в PostgreSQL и transactional outbox;
- самостоятельный `XADD + XACK` requeue на worker-е запрещён, поскольку не даёт атомарной передачи и создаёт риск потери либо дубликата;
- при ошибочной доставке worker вызывает идемпотентную серверную операцию routing quarantine и делает `XACK` только после её durable-подтверждения;
- зависшие сообщения поднимаются через `XAUTOCLAIM` только совместимым consumer-ом того же pool.

Один общий heartbeat для всего fleet недопустим: состояние хранится отдельно для каждого `node_id`.

### 5.6. Совместимость миграции

- входные и выходные схемы версионируются;
- Core API временно понимает старый и новый формат;
- новые worker-ы сначала работают в shadow/canary;
- переключение выполняется feature flag-ом;
- удаление legacy допускается только после подтверждения отсутствия трафика и незавершённых команд старого формата.

### 5.7. Обход проблемы Kerberos Double-Hop при установке драйверов

Удаленный сеанс WinRM не имеет права обращаться к сторонней SMB-шаре (`\\server\share\driver.inf`) от имени пользователя без CredSSP (ограничение Double-Hop в Active Directory).
Решение:
1. Профиль KB задаёт allowlist UNC-корень, точную версию, SHA-256 пакета и ожидаемого издателя подписи.
2. Воркер, обладая доменным доступом к SMB, локально кеширует пакет и проверяет его хеш и подпись.
3. Файлы копируются в каталог `C:\Windows\Temp\_driver_staging\<command_id>` с ограниченными ACL.
4. После передачи хеш повторно проверяется на целевой машине.
5. `pnputil.exe` вызывается строго по проверенному локальному пути.
6. Временный каталог стейджинга удаляется на этапе `cleanup`; сбой удаления фиксируется как operational alert и не маскируется успешной установкой.

### 5.8. Жизненный цикл службы WinRM и совместимость с GPO

1. Read-only preflight получает типизированные `State` и `StartMode` через CIM/WMI; парсинг локализованного вывода `sc qc` не используется как контракт.
2. Планируемое изменение WinRM входит в `plan_hash` и показывается оператору. Перевод `Disabled` в `Manual` и запуск службы выполняются только после approval и только на разрешённых политикой хостах.
3. В PostgreSQL вместе с attempt сохраняются исходный снимок, ownership token, ожидаемое промежуточное состояние и время изменения.
4. Cleanup восстанавливает состояние только если WinRM был изменён этим attempt, ownership token действителен, а фактическая конфигурация не расходится с ожидаемой.
5. Host lock координирует только worker-ы IntraLink и не считается доказательством отсутствия чужих WinRM-сессий или изменений GPO.
6. При дрейфе состояния либо недоступности хоста автоматическое восстановление прекращается; создаются operational alert и `needs_review` с инструкцией ручного восстановления.

## 6. Контрольные точки

### Gate A. Security

- отсутствует строковая интерполяция пользовательских данных в PowerShell;
- payload отсутствует в командной строке и передаётся безопасно на обеих PowerShell-границах;
- mutating-команды не повторяются при неизвестном исходе;
- секреты отсутствуют в логах и событиях;
- approval проверен по `command_version`, `plan_hash` и `expires_at`;
- WinRM возвращается в исходное состояние только при доказанном владении; невозможность восстановления создаёт alert и `needs_review`.

### Gate B. Contract

- handlers проходят единый contract test suite;
- вход и результат строго валидируются;
- неизвестное действие отклоняется до публикации в очередь;
- переходы фаз и execution evidence сохраняются в PostgreSQL;
- routing key и версии capability являются частью серверного контракта.

### Gate C. Resilience

- пройдены тесты падений, lease, duplicate delivery и конкуренции worker-ов;
- подтверждена корректность `needs_review`;
- потеря lock/lease запрещает запуск следующего side effect;
- неопределённый удалённый результат не приводит к автоматическому повтору или ложному успеху;
- ошибочная маршрутизация не создаёт PEL-зависание, цикл requeue или потерю команды.

### Gate D. Production pilot

- выполнен контролируемый E2E на тестовой заявке;
- подтверждены установка, verify, комментарий и финальный статус;
- подтверждены хеш, подпись и версия фактически установленного драйвера;
- оператор видит весь путь команды и состояние worker-а;
- rollback и ручное восстановление задокументированы.

## 7. Критерий завершения

Проект считается завершённым, когда:

- новое умение добавляется без изменения dispatcher-а;
- несколько worker-узлов безопасно работают параллельно;
- состояние каждого узла и каждой команды наблюдаемо;
- изменяющие команды не повторяются при неопределённом исходе;
- approval однозначно связан с исполненным планом и теряет силу при его изменении;
- потеря lease/lock не выдаётся за гарантированную остановку внешнего side effect;
- отсутствие worker-а явно видно оператору;
- принтерный сценарий прошёл контролируемый E2E и отказные тесты;
- legacy-пути больше не участвуют в production-трафике.
