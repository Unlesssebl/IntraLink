# Roadmap: повышение качества RAG с минимальным объёмом изменений

Дата: 2026-09-08. Статус: запланировано; реализация не начата.

Цель: находить применимые исторические решения, отклонять нерелевантные прецеденты и корректно сообщать об отсутствии знаний. Первую итерацию ограничиваем допуском источников в ответ, готовым reranker и полнотекстовым поиском в существующем PostgreSQL.

## 1. Исходное состояние

Наблюдения из аудита 2026-09-08 относятся к проверенному локальному Docker-стеку и не являются оценкой всех окружений:

| Область | Подтверждённое состояние |
|---|---|
| Хранилище | PostgreSQL + pgvector 0.8.6, HNSW, BGE-M3 1024 измерения |
| Корпус | 5 записей, 2 дочерних сервиса одного направления; все с эмбеддингами |
| Качество записей | Всем присвоено 1.0 при импорте; ночной аудит этих записей не подтверждён |
| Reranker | Адаптер есть, пакет FastEmbed отсутствует в runtime-контейнере |
| Лексический поиск | `ILIKE`, несмотря на упоминание `tsvector` в документации |
| Smoke-проверка | Запрос про принтер вернул прецеденты об учётных записях, включая отменённую заявку |
| Генерация | Первый match может стать «подтверждённым фактом» без проверки применимости |
| Проверки | 42 профильных теста прошли; это не измерение retrieval quality |
| Eval | Есть evaluator, но воспроизводимый прогон текущего поиска и baseline не подтверждены |

Проценты «использованного потенциала», прежние ~70% точности и прогнозы улучшения не считаются измеренными метриками. Два smoke-запроса показывают дефект, но не характеризуют точность системы в целом.

## 2. Решение по готовым компонентам

| Вариант | Объём интеграции | Решение |
|---|---|---|
| [FastEmbed](https://github.com/qdrant/fastembed) | Проверить существующий адаптер, подключить пакет и модель, проверить Docker | Первый кандидат для локального reranking |
| [FlashRank](https://github.com/PrithivirajDamodaran/FlashRank) | Заменить адаптер ранжирования; проверить multilingual-модель на русском | Резерв, если FastEmbed не подходит по совместимости или ресурсам |
| [pgvector + PostgreSQL FTS](https://github.com/pgvector/pgvector#hybrid-search) | Миграция GIN/tsvector и замена lexical query | Использовать для гибридного поиска и RRF |
| [LightRAG](https://github.com/HKUDS/LightRAG) | Интеграция отдельного RAG-пайплайна и модели связей | Отложить до появления подтверждённой потребности в поиске по связям |

Подключать закреплённую версию пакета, а не копировать репозиторий внутрь проекта. До выбора версии проверить Python 3.13, Linux runtime, документированный API, лицензии пакета и модели. Модель reranker выбрать по русскоязычной выборке: существующее имя в конфигурации само по себе не подтверждает пригодность. BGE-M3 и векторный индекс сохраняются; смена только reranker не требует переэмбеддинга корпуса.

## 3. Первая итерация: четыре небольших результата

Этапы выполняются последовательно. Пилотный набор из этапа A используется для проверки B–D; итоговый контрольный набор не используется для подбора порогов.

### A. Зафиксировать примеры и baseline

- [ ] Собрать 30–50 размеченных запросов, включая минимум 10 случаев без подходящего ответа: чужой сервис, схожие слова с другим смыслом, отсутствие решения, отменённый прецедент.
- [ ] Подготовить небольшой проверенный корпус по 3–5 частым направлениям; ориентир 10–20 решений на направление. Отбор по полезности, а не достижению квоты.
- [ ] Сохранить источник каждого решения и релевантные IDs для запросов; для no-match разрешить пустой список ожидаемых IDs.
- [ ] Разделить примеры для настройки и итоговой проверки; исключить тестовую заявку и её дубли из корпуса. Эталон — применимый исторический прецедент, а не ID самой тестовой заявки.
- [ ] Добавить простой runner, вызывающий реальный поиск на фиксированном корпусе и сохраняющий результаты до/после. Обезличенные рабочие данные хранить вне Git; синтетические регрессии — в тестах.

Готово, когда можно повторить один и тот же прогон и увидеть релевантные выдачи, ложные рекомендации и случаи отсутствия ответа. Полный CI-eval для этого этапа не требуется.

### B. Единый допуск прецедента в рекомендацию

- [ ] Разделить кандидатов поиска и источники, разрешённые для ответа. Один и тот же gate использовать в AI-синтезе, deterministic fallback и RAG Consensus.
- [ ] Отбрасывать слабые или явно несовместимые с проблемой результаты. Числовой порог выбирать на настройочной выборке отдельно для фактически используемого вида score.
- [ ] Отменённые заявки сохранять как исторический контекст, но не считать подтверждённым техническим решением. Проверять `resolution_type`, а не только отображаемое имя статуса.
- [ ] Исторический прецедент описывать как ранее применявшееся решение со ссылкой на источник; не утверждать, что действие выполнено в текущей заявке.
- [ ] При отсутствии пригодного источника возвращать no-match и существующий регламентный ответ/уточнение.
- [ ] Не обходить gate при одном кандидате, отсутствии reranker или когда все кандидаты ниже порога. Отличать отказ retrieval от отсутствия знаний.

Готово, когда кейс «Kyocera → учётная запись» не попадает в рекомендацию ни через AI, ни через fallback, а полезные эталонные примеры продолжают находиться.

Основные файлы: [rag.py](../../core-api/app/services/rag.py), [ai_synthesis.py](../../core-api/app/services/ai_synthesis.py), [rag_consensus.py](../../core-api/app/services/rules/rag_consensus.py).

### C. Подключить готовый локальный reranker

- [ ] Закрепить зависимость в production- и dev-манифестах; проверить фактический import, API и формат scores в адаптере.
- [ ] Выбрать одну multilingual-модель по результатам A; закрепить её идентификатор/ревизию и обеспечить доступный кеш весов.
- [ ] Добавить проверку готовности модели, ограничение параллелизма и времени ожидания. Отражать degraded/fallback явно.
- [ ] Проверить семантику scores модели; не применять эвристику «число 0…1 уже вероятность». Отдельно хранить ranking score и решение gate.
- [ ] Прогнать реальную модель внутри runtime-образа: русский positive, negative, отказ и холодный старт. Измерить время, память и размер весов.

Готово, когда reranker реально вызывается в Docker и улучшает порядок подходящих прецедентов на фиксированной выборке без роста ложных рекомендаций. Если выигрыш не подтверждён, компонент не включать в основной поток только ради наличия функции.

### D. Настоящий гибридный поиск в PostgreSQL

- [ ] Добавить `tsvector` и GIN через миграцию с backfill существующих записей и обновлением при индексации.
- [ ] Использовать русскую морфологию для текста; отдельно проверить сохранность кодов ошибок, моделей оборудования и идентификаторов.
- [ ] Заменить `ILIKE` на PostgreSQL FTS и объединить кандидатов с dense через существующий RRF. PostgreSQL `ts_rank` не называть BM25.
- [ ] Ранжировать lexical-кандидатов до `LIMIT`; сохранять видимые отдельные scores и признаки фактически работающих стадий.
- [ ] Проверить работу с настоящим AsyncSession/PostgreSQL: не запускать одновременные SQL-операции через одну сессию. Не скрывать ошибки ветвей как штатную пустую выдачу.
- [ ] Добавить версию retrieval-профиля и ревизию корпуса в кеш поиска и зависимый кеш синтеза, чтобы обновления источников не оставляли устаревший ответ.

Готово, когда морфологические варианты и технические токены находят эталоны, обе ветви подтверждены интеграционной проверкой, а no-match сохраняется после fusion и reranking.

## 4. Критерии завершения первой итерации

Сравнивать baseline и новую версию на одном корпусе, настройках окружения и отложенных запросах. Показывать абсолютные количества рядом с долями: маленькая выборка не даёт оснований заявлять production-точность 95%.

| Проверка | Критерий приёмки |
|---|---|
| Ложные рекомендации на negative-наборе | 0 допущенных в ответ нерелевантных источников на зафиксированном наборе; не гарантия для всех запросов |
| Positive retrieval | Recall@5 и MRR@5 не хуже baseline; Precision@1 выше при наличии ошибок в baseline |
| Покрытие ответа | Доля положительных кейсов с разрешённым источником не падает относительно baseline; отказ от всех ответов не считается улучшением |
| Grounding | Нет утверждений о выполнении текущей работы на основании истории другой заявки |
| Отказ компонентов | Нет обхода gate; degraded отличается от no-match |
| Производительность | p50/p95 без кеша и с кешем измерены; допустимый бюджет установлен по целевому оборудованию до включения |
| Воспроизводимость | Зафиксированы SHA сборки, версии пакета/модели, корпус, split, профиль, пороги и отчёт |

Recall@5 считать как долю найденных релевантных документов от всех эталонных для запроса; текущая проверка наличия хотя бы одного совпадения соответствует Hit@5. No-match оценивать отдельно. На этапе A уточнить эти определения в существующем [evaluator](../../core-api/app/services/evals.py), включая поддержку пустой выдачи.

## 5. Включение и откат

1. Внести изменения небольшими проверяемыми PR: A → B → C → D. Общая готовность определяется критериями выше, а не числом установленных компонентов.
2. Сравнить результаты вне операторского потока, затем включить новый профиль для пилота в карточке заявки. Batch RAG расширять после замеров нагрузки и пользы.
3. Сохранить возможность отключить reranker/новый профиль. Gate применимости остаётся активным при любом откате; безопасный результат при нехватке доказательств — отсутствие рекомендации из KB.
4. FTS-миграцию сделать добавочной; при откате приложения новую колонку/индекс можно оставить до отдельной уборки. Изменения retrieval не расширяют права AI на исполнение действий.

| Приоритет | Работа | Когда начинать |

| P1 | Версии embedding/canonizer, хэш источника, даты обновлений, сохранение результатов quality-аудита | Нужны регулярный sync и управляемый reindex |
| P1 | Связать operator feedback с использованными источниками; измерять принятие и исправления | Есть реальные решения и обратная связь пилота |
| P2 | Метрики latency, degraded rate, cache hit, no-match по сервисам | Требуется расширение нагрузки/охвата |
| P2 | Расширение batch RAG, автоматизация отбора и обновления корпуса | Есть измеримая польза в карточке и ресурсный бюджет |

Каждый следующий этап должен закрывать наблюдаемый недостаток пилота. Массовую индексацию, отдельный RAG-сервис, новый UI и обучение моделей в первую итерацию не включаем.
