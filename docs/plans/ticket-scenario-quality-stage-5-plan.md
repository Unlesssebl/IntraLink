## 1. Цели и границы

Обеспечить измеримый аудит анализа, реакции оператора и фактического применения решения:

1. Сохранять значимые этапы анализа и их технические основания в `decision_steps`, включая fallback, пропуски и обработанные ошибки.
2. Привязывать подтверждение, отклонение и правки к неизменяемой версии решения и выбранному варианту ответа.
3. Фиксировать намерение применения до внешнего вызова, а подтверждённые результаты — после него. Различать полное, частичное, неуспешное и неопределённое выполнение.
4. Измерять согласие с рекомендациями отдельно от ручных действий без рекомендации; формировать отчёт по причинам правок.
5. Автоматически собирать кандидатов для регрессионной выборки; включать их в эталон только после экспертной разметки.
6. После проверок повысить `ANALYSIS_REVISION` с `"4"` до `"5"` и проверить устаревание прежних решений.

### Инварианты и исключения

- Сохраняется Shadow/HITL. Глобальный автопилот и новые инфраструктурные действия не входят в этап.
- Не ослаблять `TruthfulnessGuard`, проверки актуальности решения, допуска к исполнению и подтверждения инфраструктурных действий перед статусом 29.
- Не переписывать исторические решения и вердикты. Допустимо заполнить новые технические поля существующих applications по связанным commands.
- Технический trace содержит наблюдаемые входы, результаты, правила и причины fallback, а не скрытые рассуждения модели.
- Успех HTTP-запроса, принятие оператором и подтверждённый результат исполнения — разные события.
- Не обещать распределённую атомарность PostgreSQL и IntraService или exactly-once внешних комментариев/списаний без поддержки внешнего API.

## 3. Контракты и архитектура

### 3.1. Трассировка анализа

Создать `DecisionExecutionTrace` в `core-api/app/services/decision_trace.py`. Сохранить возвращаемый тип `analyze() -> DecisionEnvelope`, добавив необязательный keyword-аргумент `trace`. Сборщик создаётся на один запуск и передаётся явно; не хранить его в глобальной переменной или переиспользуемом экземпляре сервиса.

Формат сериализованного шага совместим с существующим журналом:

```python
{
    "component": "facts",  # facts, rag, routing, policy, plan, ai, guard, compiler
    "status": "succeeded",  # succeeded, fallback, failed, skipped
    "input": {},
    "output": {},
    "metadata": {"trace_schema_version": 1},
    "error_code": None,
    "duration_ms": None,
}
```

Порядок `sequence` назначает журнал. Для длительностей использовать монотонные часы; неизвестная длительность — `null`, а не выдуманный ноль.

| Этап | Что сохранять |
| --- | --- |
| `facts` | Источники наблюдений, состояния valid/missing/invalid/ambiguous/conflicting/stale, ссылки на основания; различать сбор фактов и предоставленный снимок. |
| `rag` | Реальное состояние поиска, число кандидатов, оценки, ссылки на прецеденты и измеренную длительность из места выполнения retrieval. Пустой результат отличать от ошибки и отключённого поиска. |
| `routing` | Ключ и версия сценария, выбранная оценка, runner-up, неоднозначность, фактические причины выбора. |
| `policy` | Разрешённая политика либо ошибка разрешения; не скрывать её под общей ошибкой AI. |
| `plan` | Публичные и внутренние шаги, обязательные сведения, ручные действия. |
| `ai` | Провайдер, контур, источник ответа, фактический бюджет и использованные RAG-ссылки, попытки/fallback. Токены записывать только при наличии данных провайдера. |
| `guard` | Результаты TruthfulnessGuard и валидатора ответа, коды нарушений, факт замены текста. |
| `compiler` | Итоговые gates, readiness, причины блокировки и состояние анализа. |

Дополнительные требования:

- Передавать retrieval metadata из реального места поиска через внутренний контекст анализа. Для старого вызывающего кода с одними `kb_matches` обозначать происхождение как `provided`, задержку как неизвестную.
- AI, который не запускался, фиксировать как `skipped` с причиной. При ошибке и безопасном шаблоне отражать fallback без превращения всего анализа в system error.
- При обработанном исключении до создания envelope сохранять накопленные шаги вместе с failed decision через существующий путь фиксации ошибки либо его расширение. Остальные этапы помечать skipped. Не создавать фиктивное успешное решение ради FK.
- При недоступности БД не заявлять, что аудит сохранён; возвращать техническую ошибку. Сохранение каждого шага при аварийном завершении процесса посреди анализа не входит в гарантию этого этапа.
- Передавать trace в точки durable-записи, включая `CommandDispatcher.dispatch`. Повторное использование решения по fingerprint возвращает его исходный trace, не дописывает к нему шаги нового вычисления.
- Санитизировать данные существующим `sanitize_payload`; ограничить размеры полей/число прецедентов и отмечать truncation. Не сохранять credentials, полные промпты и неограниченные дампы RAG.
- Перегенерация тона сохраняет собственную provenance у response variant; не переписывает trace исходной версии решения.

### 3.2. Идентичность рекомендации и feedback

Для всех событий фиксировать `decision_id`, серверно проверенную `decision_version`, `task_id`, actor из аутентифицированного principal, источник события и время. Сама версия остаётся связанной с неизменяемой записью решения.

Источники:

- `recommendation_apply`: оператор применяет конкретную рекомендацию;
- `explicit_feedback`: отдельное отклонение или замечание;
- `manual_apply`: действие без рекомендации, для аудита исполнения, исключается из acceptance;
- применение команды сохраняет свой execution source; автоматически выполненная команда не означает согласия человека.

Предложенный статус брать из зафиксированного envelope/policy, предложенный текст — из выбранного response variant, если он указан, иначе из канонического ответа envelope. Не использовать operational payload в качестве рекомендации и не пересчитывать старую policy текущими правилами.

`response_variant_id` проверять на принадлежность решению, версии и заявке, допустимость состояния и актуальность для применения. Тон брать из сохранённого варианта. Перед сравнением и отправкой использовать один и тот же серверно проверенный вариант.

Вердикты:

- `accepted`: применяемый статус и текст совпадают с предложенными;
- `modified`: отличается статус и/или текст;
- `rejected`: явное отклонение рекомендации;
- `commented`: замечание без утверждения о принятии или отклонении.

Закрытие модального окна не создаёт rejected. Ручной выбор другого отдела сам по себе не доказывает ошибку сценария. Трудозатраты, приватность и исполнители сохраняются в дельте действия отдельно; acceptance в этом этапе определён только для статуса и текста.

Единый словарь причин: `wrong_scenario`, `wrong_status`, `edited_comment`, `device_not_found`, `ungrounded_rag`, `other`. Разделить автоматически вычисленный результат сравнения и замечание оператора в одной записи feedback:

- `reason_code` и `reason_source` описывают основание вердикта; для accepted — SQL NULL и `none`;
- `operator_reason_code` и `comment` независимо сохраняют явно введённые причину и замечание, включая случай accepted. Замечание не меняет вычисленный вердикт и не создаёт второй apply-feedback;
- новые поля `operator_reason_code` и `reason_source` добавить в модель/миграцию; для старых записей не восстанавливать несуществовавшее происхождение причин.

Правила заполнения основания вердикта (приоритет явной причины действует только для modified/rejected/commented):

- изменён статус → `wrong_status`, `reason_source=inferred`;
- изменён только текст → `edited_comment`, `reason_source=inferred`;
- оператор указал причину → всегда сохранить её в `operator_reason_code`; для modified/rejected/commented также использовать как `reason_code` с `reason_source=operator`, для accepted оставить основание вердикта пустым;
- rejected/commented без указанной причины → `other`.

При изменении статуса и текста сохранять оба независимых признака. Причина не заменяет `status_changed`/`comment_changed`.

В `final_action_json` сохранять предложенные и отправленные значения, `response_variant_id`, тон, признаки изменений, `comment_diff_ratio`, версию алгоритма сравнения и остальные параметры действия. Фактически подтверждённые значения исполнения находятся в application, а не выводятся из feedback.

Для текста определить воспроизводимое сравнение: нормализация CRLF в LF и удаление внешних пробелов; внутренние пробелы, пунктуацию и HTML не игнорировать. `comment_diff_ratio = levenshtein(a, b) / max(len(a), len(b), 1)` по Unicode code points, 0 — совпадение, 1 — максимальное отличие. Ограничить длину входного комментария, выбрать реализацию с ограниченной памятью; считать diff до санитизации и сохранять только санитизированные тексты. NULL/отсутствующий предложенный текст означает несопоставимость, а не пустую рекомендацию.

### 3.3. API и интерфейс оператора

`POST /api/v1/triage/tasks/{task_id}/decision-feedback` (и соответствующий v2 alias):

```json
{
  "decision_id": "uuid",
  "decision_version": 3,
  "response_variant_id": null,
  "event_id": "uuid",
  "verdict": "rejected",
  "reason_code": "wrong_scenario",
  "comment": "Требуется другой сценарий"
}
```

- Этот endpoint принимает только `rejected`/`commented`; accepted/modified вычисляет сервер по конкретному применению.
- Проверять принадлежность решения заявке и версии, variant, enum и длины. Для исторического feedback разрешена старая версия, если она указана явно; применять stale-решение по-прежнему нельзя.
- `triage:mutate`, проверка trusted origin и существующая аутентификация. Не доверять actor из тела запроса.
- `event_id` обеспечивает дедупликацию: тот же идентификатор и канонический payload возвращают прежний результат; изменённый payload → 409. Невалидный контракт → 422, отсутствующая запись → 404.
- Ответ содержит feedback ID, decision ID/version, источник и сохранённый вердикт. Endpoint не меняет IntraService и не создаёт application.

Расширить `ApplyTriageRequest` и клиентские типы: `request_id`, `feedback_reason_code`, `feedback_comment`, привязки решений по заявкам для batch. Сохранить существующие single-task `decision_id`/`decision_version`/`response_variant_id`; запретить конфликт single и batch форматов. Для batch каждая recommendation-привязка содержит собственные ID/version/variant; заявки без привязки считаются manual_apply. Перед side effects валидировать все привязки и уникальность task IDs.

Обновить Inspector/UnifiedActionDock и API-клиент: явное действие отклонения, поле причины/замечания, передача выбранного варианта и стабильного request ID при сетевом повторе. Новое осознанное применение получает новый ID. Сохранить текущие подтверждения опасных действий.

### 3.4. Применение, идемпотентность и восстановление

Разделить durable-запрос, попытку по заявке и итоговую проекцию. Использовать `decision_application_requests` и `decision_application_attempts`; не расширять смысл существующей `decision_applications` до очереди незавершённых операций. Эти таблицы обслуживают прямой ручной/HITL apply; командный маршрут сохраняет существующий command lifecycle.

Контракт request:

- `request_id` — глобально уникальный UUID/primary key, actor/владелец, `request_hash`, время создания;
- hash канонического полного запроса: отсортированный набор уникальных task IDs, параметры, привязки решений/variants, feedback и влияющие на исполнение флаги; порядок ключей JSON не влияет на hash;
- hash рассчитывать до санитизации, чтобы разные исходные payload не сливались после redaction; исходные секреты не сохранять;
- request и все его attempts создаются одной транзакцией. Уникальность request ID, а не только пары с task ID, запрещает конкурентное использование одного ID для непересекающихся batch;
- состояние и ответ batch формируются из сохранённых результатов attempts. Повтор не создаёт operational-решения заново.

Минимальный контракт attempt:

- `id`, `request_id` с FK на requests, `task_id`, `decision_id`, actor;
- `source`, санитизированные proposed/requested action snapshots;
- `state = pending | running | succeeded | partial_failure | failed | unknown`;
- результаты подопераций, timestamps, `version`, lease/claim token для исключения одновременной обработки;
- уникальность `(request_id, task_id)`; hash и владелец проверяются на родительском request.

Перед durable-потоком проверить аутентификацию, права, trusted origin и синтаксис. Если `dry_run=true`, выполнить отдельную ветку симуляции: только read-only проверки входов, привязок, gates и свежести и возврат явно помеченного simulated-результата. Не создавать requests, attempts, operational decisions, applications или feedback, не резервировать/расходовать лимит применения, не отправлять mutation-вызовы IntraService, SSE об успешном применении и не индексировать решение в RAG. Переданный request ID не регистрируется; dry_run не возвращает сохранённый результат реального применения с таким ID. Клиент создаёт новый ID для последующего реального действия.

Порядок реального исполнения (`dry_run=false`):

1. Проверить аутентификацию, права, trusted origin и синтаксис запроса. Найти request по ID, проверить владельца и hash. Чужой request не раскрывать; тот же ID с другим payload → 409. Для существующего запроса вернуть сохранённый итог либо текущее состояние (202 для незавершённого), не выполнять gates/fingerprint/rate-limit проверки нового действия и не повторять side effects. Это работает и после изменения заявки самим запросом.
2. Только для нового request проверить gates, свежесть, лимиты и все привязки. Создать request, operational-решения для manual_apply и все attempts одной транзакцией до первого внешнего изменения. При гонке уникальности откатить проигравшую транзакцию и обработать существующий request по шагу 1. Если запись не удалась, внешние вызовы не выполнять. Повтор не должен повторно расходовать бюджет применения; резервирование лимита связать с request ID.
3. В исходном обработчике захватить pending attempt условным переходом в running, записать claim token/lease и зафиксировать транзакцию до внешнего вызова. Захват выполняется только один раз. При задержке до запуска повторно проверить актуальность именно ещё не начатого действия; отрицательный результат завершает attempt без side effects. Завершённые attempts batch не перепроверять и не исполнять.
4. Выполнить подоперации существующего apply: промежуточный статус при необходимости, целевое обновление, списание минут. Если целевое обновление не подтверждено, новые минуты не списывать. Сохранять известные результаты подопераций; при неопределённости остановить зависимые изменения и перейти к сверке, не повторяя запрос на транспортном уровне.
5. В одной транзакции условно обновить attempt по текущим state/version/claim token, создать/обновить его единственную application и записать автоматически вычисленный feedback для recommendation_apply. Если владение утрачено, откатить всю транзакцию, не перезаписывая результат reconciliation. Расширить `add_feedback(commit=False)`; внутренние методы не должны фиксировать эту транзакцию самостоятельно.
6. После фиксации отправлять UI/SSE результат и выполнять необязательные последующие действия. Сбой Redis/SSE/RAG-индексации не стирает итог применения и не запускает его повторно.

Гарантия: не более одной локальной application на attempt и одного apply-feedback для recommendation attempt; у pending/running итоговой проекции ещё нет, у manual attempt apply-feedback не создаётся. У терминального результата есть application, а у сопоставимой recommendation — вычисленный feedback. Несопоставимость фиксируется отдельно без фиктивного accepted. Эта гарантия не равна exactly-once внешней операции.

Восстановление выполняет ограниченный reconciliation worker/скрипт без повторения внешних изменений:

- Истёкший pending условно переводится в failed с `not_started`: running всегда фиксируется до первого вызова, поэтому pending не мог выполнять side effects. Старый обработчик после такого перехода не сможет получить claim. Автоматически возобновлять pending по санитизированному снимку нельзя; оператор может создать новый запрос после свежих проверок.
- Истёкший running условно переводится в unknown, claim инвалидируется. Перед каждой следующей подоперацией обработчик проверяет владение; уже отправленный HTTP-запрос отозвать невозможно. Новый обработчик не повторяет его.
- Unknown сверяется со статусом/историей IntraService и переходит в succeeded/partial_failure/failed только при достаточных доказательствах; иначе остаётся unknown. Записывать основание, проверенные подоперации и время. Повторная сверка идемпотентна; поздний результат прежнего claim не перезаписывает новое состояние.
- Новое применение после unknown допустимо лишь при доказанном отсутствии соответствующих изменений и новом явном запросе оператора. Нельзя считать истечение lease доказательством отсутствия внешнего действия.

API под существующими v1/v2 triage-префиксами: `GET /application-requests/{request_id}` для результата batch, `GET /application-attempts?state=unknown` (также pending/running, с cursor/limit) для списка и `POST /application-attempts/{attempt_id}/reconcile` для сверки. Чтение требует `triage:read` и доступа владельца либо `audit:read`; mutation — `triage:mutate`, trusted origin и проверку доступа. Reconcile принимает `expected_version`, запускает только чтение IntraService и возвращает обновлённую версию либо 409. Ручное замечание хранится как audit event с actor; произвольная кнопка «считать успешным» не меняет верификацию. UI показывает подоперации, основания unknown и результат сверки.

`request_id` обязателен для нового UI. На переходный период legacy-запросам без него сервер выдаёт ID, возвращает его клиенту и помечает отсутствие клиентской защиты от сетевого повтора; универсальную гарантию дедупликации таких запросов не заявлять. Это ограничение явно отражать в отчёте покрытия.

### 3.5. Проекция результата и миграция

Миграция `20260912_0015_stage_5_audit_feedback.py`, `down_revision = 20260910_0014` (перед реализацией сверить head).

`DecisionApplication`:

- nullable `command_id`, сохранить его уникальность и FK;
- nullable уникальный `attempt_id` с FK на attempts;
- `application_type`: NOT NULL, `triage_apply` или `command_execution`; серверный default `command_execution` обеспечивает совместимость старого writer. Новый triage writer всегда явно передаёт `triage_apply`;
- `task_id`, заполнение из связанной команды/решения для истории, где возможно;
- CHECK: ровно одна связь — command или attempt; тип соответствует связи;
- сохранить существующие command states; triage использует `applied_unmodified`, `applied_modified`, `applied_manual`, `partial_failure`, `failed`, `needs_review`.

Не превращать неопределённые результаты в applied. Хранить отдельно requested action, подтверждённые поля applied action и verified result по подоперациям:

- outcome: `confirmed | failed | unknown | not_requested`;
- источник доказательства: `api_response | readback | history`;
- наблюдавшееся значение, время проверки, внешний ID, если доступен;
- технический код ошибки без секретов.

`payload.status_id` никогда не является наблюдавшимся статусом. Проверить контракт адаптера IntraService: если ответ не подтверждает отдельные поля, делать readback/проверку истории. Одного совпадения текущего статуса недостаточно для подтверждения комментария или минут; при отсутствии надёжной корреляции оставлять unknown. Незапрошенное списание — not_requested, а не успешно списанные нулевые минуты.

#### Политика HTTP-повторов и fallback

Изменить `services/intraservice.py`: текущий `_make_request` повторяет запросы при таймаутах/5xx независимо от метода, а `update_task_full` может повторить обновление без исполнителей после любого `None`. Такая вложенная повторная отправка обходит идемпотентность request/attempt.

- Ввести структурированный результат изменяющего вызова: confirmed/failed/unknown/not_sent, HTTP status/error code, безопасные сведения ответа и основание классификации. Не сводить отказ до отправки, подтверждённый отказ сервера и потерю ответа к одному `False`/`None`.
- Read-only запросам оставить ограниченные retries. Для изменения с потенциально повторяемым эффектом (комментарий, минуты) отключить автоматический повтор при таймауте, обрыве связи после возможной отправки и 5xx: результат unknown, далее только сверка. Сам по себе PUT не доказывает идемпотентность содержащего комментарий запроса.
- Повтор mutation допустим лишь при доказанном отсутствии отправки/применения либо документированной внешней идемпотентности со стабильным ключом. По умолчанию неизвестность трактуется как unknown; число скрытых mutation-retries равно нулю. Отказ circuit breaker до отправки — not_sent.
- Fallback без ExecutorIds разрешить только для конкретного подтверждённого отказа назначения исполнителя, контракт которого исключает применение исходного обновления. Произвольный 400/403 или `None` таким доказательством не считать. При отсутствии подтверждённого контракта fallback не выполнять.
- При разрешённом fallback отразить неназначенных исполнителей в результате подопераций: успешные статус/комментарий не означают полного выполнения всех запрошенных полей.
- Обновить прямой triage и command consumer на структурированный результат; проверить остальные mutation callers `intraservice.py`, включая `command_delivery.py`. Старый bool-интерфейс при необходимости оставить как совместимую обёртку, но новые audited-пути не должны терять unknown или включать скрытые retries.

Обязательный fault test: внешний сервер применил комментарий/минуты, но ответ потерян. До и после reconciliation повторная mutation не отправляется ни HTTP-helper, ни fallback, ни consumer; неподтверждённая операция остаётся unknown до получения доказательства.

Обновить writer в `command_service.py`: явно задавать `command_execution` и task ID, сохранить уникальность command projection и существующую верификацию. Не создавать вторую triage application для того же исполнения command.

Обновить `backend_command_consumer.py`, который также вызывает `apply_triage_resolution`: общий сервис возвращает фактические результаты подопераций, но не создаёт request/attempt. Их жизненным циклом владеет прямой triage-маршрут; командным — CommandService. Consumer не должен объявлять success только по `update_ok`: все запрошенные операции подтверждены → succeeded; частичное или неопределённое выполнение → существующий `needs_review` с полным результатом и признаком partial/unknown; подтверждённый полный отказ → failed. Не терять результаты успешно выполненных элементов batch из-за исключения на другом элементе. Аналитика нормализует эти command outcomes по подоперациям, не выдавая needs_review за полный успех. Существующую уникальную command projection сохранить; новый attempt для command не создавать.

`DecisionFeedback`: добавить nullable `attempt_id` (unique для apply-feedback), nullable уникальный `event_id` для explicit-feedback, source, request hash, nullable `operator_reason_code` и `reason_source` (legacy для исторических записей). Исторические строки оставить legacy, не присваивать им новые причины и признаки задним числом. CHECK/валидация новых записей фиксируют допустимые сочетания source, verdict и идентификаторов.

Миграция должна работать на заполненной PostgreSQL: создать requests/attempts, добавить новые поля, заполнить технический тип команд, установить совместимые defaults и ограничения. `task_id` application остаётся nullable для старого writer; новый writer заполняет его явно. Для feedback серверный default source=`legacy`, новые идентификаторы nullable; ограничения допускают старую запись без attempt/event ID. Проверить вставки старых command/feedback writers после миграции и после отката backend. Default `command_execution` совместим с CHECK «ровно command или attempt»; triage-вставка без явного типа должна отклоняться.

Не удалять аудит при downgrade: если requests/attempts/feedback нельзя представить старой схемой без потерь, downgrade останавливается с понятной ошибкой. Откат приложения сохраняет расширенную схему и defaults, отключает новые producers; сначала прекратить приём новых apply, дождаться либо изолировать незавершённые attempts, чтобы старый backend не повторил их. Удаление совместимых defaults/ужесточение legacy-ограничений — отдельная будущая миграция после завершения окна отката.

### 3.6. Аналитика качества

Создать `DecisionFeedbackAnalyticsService` и `GET /api/v1/triage/analytics/quality` (также v2 alias). Доступ: `triage:read` и `audit:read`. В агрегатах не возвращать тексты комментариев/фактов.

Фильтры: UTC `start_date` включительно, `end_date` исключительно; ISO datetime с timezone, `scenario_key`, `scenario_version`, `analysis_revision`. Проверять порядок дат и ограничивать размер периода. Кандидаты имеют limit/cursor; выборка детерминированна.

Единица основных apply-метрик — уникальный recommendation attempt с сопоставимыми предложенными статусом и текстом, подтверждённым обновлением статуса/комментария и feedback. Не смешивать её с количеством задач, feedback-сообщений и commands.

| Метрика | Определение |
| --- | --- |
| `total_decisions` | Уникальные решения по created_at; отдельно triage/operational и failed. |
| `total_applications` | Полностью подтверждённые применения по времени подтверждения; отдельно command/triage/manual. |
| `eligible_recommendation_applications` | Знаменатель N описанных выше сопоставимых recommendation attempts. Сбой только списания не отменяет подтверждённый выбор статуса/текста, но попадает в partial_failure исполнения. |
| `acceptance_rate` | accepted / N. Это согласие со статусом и текстом, не оценка правильности сценария. |
| `status_override_rate` | Число status_changed / N. |
| `comment_edit_rate` | Число comment_changed / N. Может пересекаться со status_override_rate. |
| `feedback_coverage` | Доля подтверждённых recommendation updates с пригодным feedback среди всех подтверждённых recommendation updates. |
| `execution_breakdown` | succeeded/partial_failure/failed/unknown, отдельно ручные и командные применения. |
| `explicit_rejections` | Количество уникальных версий решений с rejected в интервале, отдельно от apply rates. |
| `reason_distribution` | Основания вердиктов по одному feedback на attempt; explicit-feedback отдельной группой, с разделением operator/inferred. Отдельная `operator_reason_distribution` учитывает введённые причины, включая accepted, без повторного увеличения числа feedback или applications. |

Для N=0 возвращать null rate и числитель/знаменатель, а не 0% принятия. Rates — числа 0..1. Сумма двух долей изменений может превышать 1.

- Группировать по версии сценария и analysis revision из снимка решения. Не выводить scenario key из текущего состояния заявки.
- Для apply rates использовать время подтверждённого обновления, для explicit-feedback — время события. Вернуть описание временной базы в metadata ответа; totals разных когорт не делить друг на друга.
- Повторное explicit-feedback не размножает applications. Агрегировать связи отдельно до JOIN, чтобы несколько feedback и applications не создавали декартово умножение.
- Legacy без достаточной привязки/снимка и manual_apply исключать из N; показывать их количество, а также missing-feedback, несопоставимые рекомендации и legacy requests без idempotency key.
- Добавить `scenario_breakdown`, минимальный размер группы и сырые счётчики. При малой выборке отмечать недостаточность данных; не ранжировать качество по одному случаю.
- Создать воспроизводимый JSON/Markdown-отчёт на том же сервисе/правилах агрегирования, с периодом, фильтрами и ограничениями. Acceptance не заменяет экспертную оценку точности, ошибочных отмен и допуска к действиям.

### 3.7. Регрессионные кандидаты

Автоматизировать сбор и экспорт кандидатов, а не признание операторской правки эталоном:

1. Отбирать явные отклонения, изменения статуса, ungrounded_rag и большие правки текста; показывать критерий отбора и значение diff. Большая правка сама по себе не доказывает ошибку.
2. Экспортировать immutable snapshot: task ID, decision ID/version, scenario/revision, входы анализа, variant, feedback и подтверждения применения; дедуплицировать по decision и событию.
3. Санитизировать/псевдонимизировать по существующему формату ticket-quality fixtures, создать manifest/checksums. Если контекста недостаточно для replay, явно пометить кандидат, не выдумывать входы.
4. Присвоить `needs_review`. Эксперт задаёт ожидаемый сценарий, допустимые альтернативы и запрещённые действия.
5. Только явно проверенные кандидаты включать в эталон и запускать offline replay. Экспорт не переписывает исходные 99 снимков; результаты «после» хранить отдельно.

### 3.8. Ревизия и выпуск

Повысить `ANALYSIS_REVISION` до `"5"` в конце реализации; обновить явные env overrides и тестовые ожидания там, где они существуют. Проверить не только отображение stale, но и отказ применения старой версии, получение новой версии, fingerprint/cache invalidation и повторные запросы.

Порядок выпуска: совместимая миграция → backend с поддержкой новых полей и наблюдением unknown → UI с request/decision bindings → проверка сквозного потока → включение новой ревизии. Не удалять исторические записи. Rollback не должен делать старые рекомендации снова актуальными; сохранять повышенную ревизию и блокировки либо отключать применение до повторного анализа.

### Этап завершён, когда

1. Новые durable-анализы имеют достоверные шаги и причины пропусков/fallback; обработанные ошибки не теряют накопленный trace при доступной БД.
2. Каждое новое прямое triage-применение имеет durable request и attempt; командное сохраняет command lifecycle без второго attempt; recommendation-feedback привязан к точной версии и варианту, manual actions не увеличивают acceptance.
3. Подтверждённые, частичные, неуспешные и неопределённые результаты различимы; retries не дублируют локальный аудит, recovery не повторяет неопределённые внешние изменения.
4. Существующая command projection и TruthfulnessGuard сохраняют поведение; PostgreSQL ограничения и fault tests проходят.
5. UI позволяет явно отклонить рекомендацию и указать причину; API проверяет права, принадлежность и идемпотентность.
6. Аналитика и отчёт используют документированные знаменатели, версии и временные базы, показывают exclusions/coverage; кандидаты экспортируются с экспертным статусом.
7. Revision 5 действительно устаревает прежние решения; отчёты тестов, replay и ограничения разметки приложены к результатам реализации.
