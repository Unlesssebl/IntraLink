# ADR 0002: Модульная платформа умений и распределенная среда исполнения Windows

Статус: accepted — 2026-09-07  
Связанные документы: [ADR 0001](0001-transactional-command-platform.md), [`docs/plans/archive/worker-platform-evolution.md`](../plans/archive/worker-platform-evolution.md)

---

## 1. Контекст и проблематика

Исторический компонент `execution-worker` был спроектирован как монолитный скрипт `worker.py` с центральным ветвлением `if/elif` по именам действий. Это создавало ряд критических архитектурных ограничений:

1. **Высокая связность и хрупкость:** Добавление любого нового действия (например, сброс пароля AD или очистка диска) требовало модификации главного цикла воркера, управления блокировками и логики доставки.
2. **Уязвимость к PowerShell-инъекциям:** Команды WinRM и `Invoke-Command` формировались через f-строки и строковую интерполяцию пользовательских данных (`target_pc`, `printer_name`, `driver_name`).
3. **Kerberos Double-Hop:** Попытка обращения к SMB-шаре (`\\server\share\driver.inf`) из удаленной сессии WinRM приводила к отказу доступа (`Access Denied`), так как доменные учетные данные не делегируются удаленному хосту без CredSSP.
4. **Опасный fallback на Generic-драйверы:** При ошибке установки драйвера принтера происходил fallback на `"Generic / Text Only"`, вызывавший аварийную порчу бумаги на офисных МФУ (печать сотен страниц бинарного мусора).
5. **Проблема "Зомби-воркера" (Martin Kleppmann Fencing Problem):** При истечении lease в Core API или временном сетевом лаге воркер мог продолжить выполнение длительной PowerShell-команды на хосте, внося необратимые изменения после того, как задача уже перешла в `needs_review` или была отдана другому узлу.
6. **PEL-голодание при маршрутизации по возможностям:** В Redis Streams вычитка несовместимой задачи узлом без требуемых модулей (например, без AD RSAT) оставляла сообщение в Pending Entries List (PEL), блокируя его обработку другими узлами на 2 минуты.
7. **Конфликт политик повторов:** В `command_outbox.py` при истечении lease проверялся `AUTO_ELIGIBLE_ACTIONS` вместо `AUTO_RETRY_ELIGIBLE_ACTIONS`, что создавало риск автоматического перезапуска изменяющих инфраструктуру команд.

## 2. Архитектурное решение

Принята модульная архитектура платформы исполнения на базе **Worker SDK**, распределенного реестра обработчиков (**Handler Registry**) и модели флота (**Worker Fleet**).

```
 ┌─────────────────────────────────────────────────────────────┐
 │                      PostgreSQL 16                          │
 │  (SSOT: Commands, Outbox, Attempts, Approvals, Policies)    │
 └──────────────────────────────┬──────────────────────────────┘
                                │ Transactional Relay
                                ▼
 ┌─────────────────────────────────────────────────────────────┐
 │                 Redis Streams (v2 Transport)                │
 │    stream:execution_commands:v2  |  lock:host:<pc_name>     │
 └──────────────────────────────┬──────────────────────────────┘
                                │ XREADGROUP / XAUTOCLAIM
                                ▼
 ┌─────────────────────────────────────────────────────────────┐
 │                 Windows Execution Worker                    │
 │  ┌───────────────────────────────────────────────────────┐  │
 │  │ Fleet Registry (node_id, capabilities, load, status)  │  │
 │  ├───────────────────────────────────────────────────────┤  │
 │  │ LeaseRenewer (Cooperative Cancellation on loss)       │  │
 │  ├───────────────────────────────────────────────────────┤  │
 │  │ Handler Registry (OCP Dispatcher)                     │  │
 │  │   ├── DiagnoseHostHandler     (R0, SAFE_RETRY)        │  │
 │  │   ├── InstallPrinterHandler   (R1, NEVER_AUTO_RETRY)  │  │
 │  │   └── GrantWlanHandler        (R2, NEVER_AUTO_RETRY)  │  │
 │  └───────────────────────────────────────────────────────┘  │
 └──────────────────────────────┬──────────────────────────────┘
                                │ WinRM (Invoke-Command) / WMI
                                ▼
 ┌─────────────────────────────────────────────────────────────┐
 │                 Target Windows Workstation                  │
 │   - Local driver staging (C:\Windows\Temp\_staging\...)     │
 │   - Cleaned up on finally                                   │
 │   - WinRM original service state restored                   │
 └─────────────────────────────────────────────────────────────┘
```

### 2.1. Единый контракт `ActionHandler` (Worker SDK)

Каждое умение реализует строго типизированный интерфейс `ActionHandler`:
- `id: str`, `version: str`, `capabilities: list[str]`, `risk_class: RiskClass`;
- `input_model: type[BaseModel]` — жесткая схема входных параметров;
- Жизненный цикл из 7 фаз:
  1. `validate(ctx, params) -> None` — статическая валидация схемы и параметров без сетевых обращений;
  2. `preflight(ctx, params) -> (ok, evidence, msg)` — строго **read-only** проверка доступности хоста, портов, служб и зависимостей ДО получения approval оператора;
  3. `prepare(ctx, params) -> (ok, prep_data, msg)` — подготовка окружения строго **ПОСЛЕ** approval оператора (WMI bootstrap WinRM с фиксацией исходных `State` и `StartMode`, локальный staging драйверов);
  4. `execute(ctx, params, prep_data) -> ActionResult` — выполнение полезной нагрузки (передача staging-папки на хост, вызов фиксированного PowerShell-кода через `-ArgumentList`);
  5. `verify(ctx, params, exec_res) -> (verified, evidence, is_failure, code)` — независимая проверка примененного состояния (опрос CIM Spooler, проверка создания очереди печати);
  6. `reconcile(ctx, params) -> (ok, msg)` — проверка фактического состояния перед повтором при неопределенном исходе (потеря связи/таймаут);
  7. `cleanup(ctx, params, prep_data) -> None` — гарантированное удаление временных файлов/папок staging и откат временно измененных настроек служб (WinRM) при отсутствии конфигурационного дрейфа.

### 2.2. Защита от инъекций и искажения аргументов (Двухконтурная безопасность)

Строковая интерполяция пользовательских параметров в PowerShell полностью исключена на обоих контурах исполнения:
- **Контур 1 (Локальный воркер):** Локальный раннер запускается с фиксированным скриптом без динамических аргументов командной строки. Параметры передаются через `stdin` либо через защищенный ACL временный файл (`ConvertFrom-Json`). Флаг `-EncodedCommand` допускается исключительно для передачи фиксированного bootstrap-раннера в Base64 (UTF-16LE).
- **Контур 2 (Удаленная сессия WinRM):** Внутри сессии `Invoke-Command` исполняется фиксированный `ScriptBlock`. Все параметры передаются строго через параметр `-ArgumentList` с типизацией в блоке `param(...)`, либо в виде нормализованного JSON-payload.
- **Нормализация входных данных:** Предварительная фильтрация имен хостов, IP-адресов и очередей выполняется через единый пакет `shared.normalizer`.

### 2.3. Решение проблемы Kerberos Double-Hop (SMB Staging)

Вместо обращения к сетевой шаре из удаленной сессии WinRM:
1. Воркер кеширует драйвер локально с SMB-шары на диск узла-воркера.
2. Проверяется целостность пакета (SHA-256 манифеста/файлов).
3. В фазе `execute` файлы копируются через WinRM-сессию во временный каталог целевого ПК `C:\Windows\Temp\_driver_staging\<job_id>\`.
4. Команда `pnputil.exe /add-driver` запускается от локального пути.
5. В фазе `cleanup` временный каталог удаляется как при успехе, так и при аварии.

### 2.4. Защита от "Зомби-воркера" (Cooperative Cancellation) и привязка Approval

- **Привязка Approval к `plan_hash`:** В режиме Human-in-the-Loop (`CONFIRM`) подтверждение оператора связывается с версией команды (`command_version`), собранными на фазе `preflight` evidence, сроком годности (`expires_at`) и неизменяемым `plan_hash = SHA256(version + params + preflight_evidence)`. При любом изменении параметров или истечении срока approval аннулируется.
- **Динамический режим AUTO:** Администратор может переводить любые действия в режим `AUTO` через Skills Hub (`PATCH /api/v1/skills/{id}/policy`). В этом режиме команда минует фазу ожидания одобрения (`awaiting_approval`) и направляется сразу в шину исполнения (`status='queued'`), проходя все фазы статической валидации и preflight.
- **Fail-Closed до первого side effect:** Любая потеря связи с Redis или Core API до начала фазы `execute` немедленно прерывает команду без применения изменений.
- **Cooperative Cancellation:** Воркер запускает фоновую задачу продления `LeaseRenewer` с относительным TTL (`time.monotonic()` и `lease_ttl_seconds`). При получении `409 Conflict` (lease перехвачен или истек) или потере host lock Renewer активирует `cancellation_token`, локальный подпроцесс PowerShell принудительно прерывается (`process.kill()`), а статус переводится в `needs_review`.
- **Запрет автоповтора mutating-команд:** Неизвестный исход изменяющего действия всегда фиксируется как `needs_review` и запрещает автоматический retry (`AUTO_RETRY_ELIGIBLE_ACTIONS`).

### 2.5. Маршрутизация по возможностям и серверный Routing Quarantine

- Каждый воркер регистрирует узел в Redis (`worker:node:<node_id>`) со списком поддерживаемых `capabilities` и `supported_actions`.
- Задачи распределяются по специализированным пулам воркеров.
- При ошибочной доставке задачи узлу, не обладающему требуемой capability, воркер не выполняет клиентский переброс в очередь (`XADD+XACK`), создающий риск циклического PEL-голодания. Вместо этого ошибка маршрутизации регистрируется в Core API, который идемпотентно помещает команду в routing quarantine с экспоненциальной задержкой или перенаправляет в целевой пул.

## 3. Классы повторяемости (Retry Classes)

1. **`SAFE_RETRY`** (`diagnose_host`, `rag_sync`): безопасные read-only действия. Автоповтор через 5 и 30 секунд.
2. **`RECONCILE_BEFORE_RETRY`**: условно идемпотентные действия. Повтор разрешен только если фаза `reconcile` подтвердила отсутствие частичных изменений.
3. **`NEVER_AUTO_RETRY`** (`install_printer`, `grant_wlan`, `apply_triage`): изменяющие действия. Любой сбой или потеря связи переводит задачу в `needs_review` для ручного разбора инженером.

## 4. Эксплуатационные последствия

1. **Плюсы:**
   - Полная изоляция умений: новые фичи добавляются без правки ядра воркера.
   - Безопасное параллельное исполнение на множестве Windows-нод без гонок.
   - Исключены инъекции, порча бумаги и сетевые отказы Double-Hop.
   - Наблюдаемость флота: оператор видит список нод, их нагрузку и возможности.
2. **Компромиссы:**
   - Установка принтера требует дополнительного времени на SMB-стейджинг драйвера (1-3 секунды на копирование по локальной сети).
   - Требуется строгая дисциплина написания `cleanup`-фаз для каждого нового handler-а.
