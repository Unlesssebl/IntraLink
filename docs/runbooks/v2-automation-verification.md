# 🧪 Сценарии приемочного тестирования и верификации (Acceptance Test Suite)

> **Статус:** Нормативный регламент тестирования v2  
> **Связанные документы:** [v2-automation-pipeline.md](file:///docs/architecture/v2-automation-pipeline.md), [v2-automation-implementation-plan.md](file:///docs/plans/v2-automation-implementation-plan.md)

## 🎯 1. Цель приемочного тестирования

Обеспечить 100% предсказуемость работы системы перед передачей в эксплуатацию инженерам. Каждый компонент конвейера проверяется на 5 эталонных бизнес-кейсах.

---

## 📋 2. Пять эталонных сценариев приемочного тестирования

### 🧪 Тест-кейс 1: Шлюз релевантности (Регламентный авто-отказ)
* **Входные данные:** Заявка в общий раздел ИТ с темой: *«Выпустите личную ЭЦП на Иванова И.И. для Госуслуг»*.
* **Ожидаемое поведение:**
  1. Поллер фиксирует новый тикет через фильтр 984.
  2. Шлюз релевантности идентифицирует запрет регламента (`RULE_PERSONAL_EDS_REJECT`, уверенность 100%).
  3. Статус тикета в IntraService переводится в **`30` («Отменена»)**.
  4. Публикуется официальный шаблон заявителю со ссылкой на аккредитованные УЦ.
  5. Добавляется скрытый комментарий (`IsPrivateComment: true`):  
     `[🤖 IntraLink Gatekeeper] Заявка автоматически отменена. Сработало правило: Личная ЭЦП физлица.`
  6. Сценарии решения технических проблем **не запускаются**.

---

### 🧪 Тест-кейс 2: Нехватка обязательных данных (Запрос к заявителю)
* **Входные данные:** Заявка в раздел «Установка принтера» с темой: *«Установите принтер в 305 кабинете»*. В тексте нет ни имени ПК, ни IP-адреса.
* **Ожидаемое поведение:**
  1. Автопилот фиксирует нехватку сущностей `pc_name` и `printer_address`.
  2. Формируется вежливый публичный вопрос заявителю с инструкцией, где найти эти данные.
  3. Статус тикета переводится в **`6` («Приостановлена»)**.
  4. В тикете фиксируется скрытая заметка: *«[🤖 Autopilot] Запрошены уточнения: pc_name, printer_address. Раунд 1/2.»*

---

### 🧪 Тест-кейс 3: Возобновление по ответу заявителя (Resume Loop)
* **Входные данные:** Заявитель из Тест-кейса 2 оставляет комментарий: *«Мой компьютер WKS-01, а принтер Kyocera 192.168.1.50»*.
* **Ожидаемое поведение:**
  1. Поллер фиксирует событие комментария через срез `ChangedMoreThan`.
  2. Автопилот пробуждается и через локальную LLM извлекает: `pc_name="WKS-01"`, `printer_address="192.168.1.50"`.
  3. Задача автоматически передается на исполнение в воркер.
  4. По завершении статус переводится в **`3` («Выполнена»)**, заявитель получает отчет.

---

### 🧪 Тест-кейс 4: Мандат сервисной учетной записи (Полный автопилот)
* **Входные данные:** Заявка на сброс пароля в AD. Диспетчер назначает в поле `ExecutorIds` сервисную учетную запись.
* **Ожидаемое поведение:**
  1. Поллер фиксирует появление сервисного аккаунта в `ExecutorIds`.
  2. Запускается автономный сценарий `ad_password_reset` через LDAP без ожидания клика человека в веб-интерфейсе.
  3. Пароль сбрасывается, заявитель получает отчет, тикет закрывается со статусом `3`.

---

### 🧪 Тест-кейс 5: Предохранитель (Self-Healing Circuit Breaker)
* **Входные данные:** Эмуляция недоступности хостов/сети: подряд 3 задачи установки принтера завершаются ошибкой связи.
* **Ожидаемое поведение:**
  1. Счетчик `consecutive_failures` сценария `install_printer` достигает 3.
  2. Система автоматически переключает режим сценария из `FULL_AUTO` в **`ASSISTED`**.
  3. В веб-интерфейсе появляется плашка предупреждения.
  4. Последующие тикеты на принтеры не выполняются вслепую, а требуют ручного подтверждения инженером до стабилизации сети.

## 🛠️ 3. Команды для автоматизированного прогона тестов

```powershell
# Запуск сквозного набора тестов конвейера автоматизации
uv run pytest api/tests/test_automation_pipeline.py -v

# Проверка моделей и миграций
uv run alembic upgrade head

# Тест изоляции очередей Taskiq
uv run pytest worker/tests/test_broker_routing.py -v
```
