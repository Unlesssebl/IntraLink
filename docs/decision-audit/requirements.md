# Требования к журналу решений

Статус: целевое поведение; существующий код покрывает его частично. Проверка проведена чтением реализации, без утверждения о полноте данных в работающей БД.

## 1. Что уже есть и чего не хватает

| Проверенный участок | Текущее состояние | Пробел |
|---|---|---|
| `database/db.py`: TicketRun, TicketRunEvent, CommandRecord, CommandEvent | PostgreSQL хранит циклы, шаги, команды, параметры и результаты | Не хранит единую полную цепочку оснований решения |
| `ticket_runs.py`: начальный trigger_snapshot_json | ID заявки, статус, ID ассистента и исполнителей | Не восстанавливает описание и переписку на момент выбора шага |
| `triage_service.py`: карточка | Получает историю, поля заявки, диагностику и RAG; поиск в этом пути использует тему и описание | Данные загружены, но это не означает, что они дошли до модели или сохранены для аудита |
| `ai_synthesis.py`: extract_thread_context | Выбирает последние пять содержательных сообщений | Важное раннее уточнение может выпасть; нужна явная фиксация выбранного и пропущенного контекста |
| Проверенные пути triage_service / ticket_run_runner / ai_synthesis | Есть сведения о вложениях; автоматическое чтение содержимого в этих путях не обнаружено | Нельзя представлять вложения как проанализированные |
| `rules/engine.py` | Первое совпадение; исключения логируются, оценка продолжается | Нет связанного с решением протокола условий и ошибок |
| `ai_suggestions.py` | Суточный Redis-кэш, fingerprint, общая строка источника | Кэш не является долговременным аудитом и не показывает реальный вклад компонентов |
| `ai/hub.py` | Модель, контур, длительность и результат доступны в ответе и часовом кэше | Нет единой долговременной связи с решением; текстовый синтез теряет часть метаданных при возврате строки |
| `triage_service.py`: запись TriageAuditLog | generated_comment=None, confidence_score=1.0, diff_ratio=0.0 | Эти значения не измеряют качество AI и фактические правки |
| `database/db.py`: RuleAuditLog | Аудит изменения правил и шаблонов | Не является журналом срабатывания правил на заявках |

Пути относятся к `core-api/app/`. Вывод: база для разбора исполнения есть, доказательств корректности выбора пока недостаточно.

## 2. Единица аудита и связи

Сохранять запись на каждое существенное предложение или выбор следующего действия, включая отсутствие решения, ошибку анализа, отказ и паузу. Только успешные команды дают смещённую выборку и не позволяют оценить качество триажа.

Запись имеет собственный ID, task_id, время, инициатора, источник, версию схемы и версию сборки. Необязательные связи: ticket_run_id, предыдущее решение, команда и попытки AI-вызовов. Корреляция должна доходить до событий команды и итоговой оценки. Анализ до создания цикла допустим.

Завершённые основания не перезаписываются. Новый анализ создаёт новую версию решения; согласование ссылается на конкретную версию и параметры. Обычный повторный просмотр не создаёт новую одинаковую запись. Вызов, не завершившийся после рестарта, обозначается как незавершённый, а не исчезает.

## 3. Минимальный состав записи

| Группа | Что фиксировать |
|---|---|
| Контекст заявки | Использованные тема, описание, сервис, статус, исполнители, релевантные дополнительные поля; время получения, версия/хэш и происхождение |
| Переписка | ID, время, авторство и допустимый к хранению текст использованных сообщений; позиция прочитанной истории; ограничения выборки |
| Реквизиты и диагностика | Извлечённое значение, откуда получено, подтверждено ли; цель, результат и время проверки; отсутствие/ошибка/устаревание отдельно |
| Вложения | ID, тип, версия/хэш при наличии, состояние: не прочитано / прочитано / ошибка / исключено политикой; использованный текст либо ссылка на защищённый артефакт |
| Rule Engine | ID и версия набора правил, порядок фактически проверенных правил, результат условий и ссылки на факты, победившее правило, ошибка, fallback; непроверенные правила не считать отклонёнными |
| RAG | Фактический запрос, фильтры и лимиты; использованные ID и версии источников, фрагменты и оценки сходства; различать найденное и переданное в AI |
| AI | Роль вызова, фактические backend и модель, версия/хэш промпта, параметры, допустимые вход и выход, контур и редактирование данных, кэш, fallback и ошибки каждой попытки |
| Производительность | Длительность; токены, если доступны от провайдера. Неизвестное значение — null, а не 0. Стоимость не вычислять без проверенной версии тарифа |
| Предложение и допуск | Действие, параметры, черновик, основания, недостающие данные, ожидаемые последствия, актуальность; применённая политика и существенные причины допуска/запрета |
| Решение инженера | Принял / изменил / отклонил; исходный и окончательный текст, структурные изменения действия, автор и время; причина при наличии |
| Исполнение и оценка | Ссылка на команду и проверенный результат; полный/частичный/неизвестный исход; оценка корректности с автором, временем и основанием |

Нельзя сохранять только хэш вместо необходимого для разбора содержимого: хэш подтверждает равенство, но не восстанавливает вход. При ограничении хранения явно показывать, что содержимое недоступно и точное воспроизведение невозможно.

## 4. Полнота контекста

Различать данные, доступные в Helpdesk, полученные backend, использованные правилом и переданные модели. Для каждого исключения сохранять причину: не требуется сценарию, лимит, недоступность, политика, отсутствие обработчика.

Не увеличивать контекст бесконтрольно. В первой версии зафиксировать реальные выборки и ограничения, включая пять последних сообщений. Это не признание такой выборки достаточной. Дальнейшее изменение отбора проверять на сохранённых примерах: раннее уточнение, исправленные реквизиты, повторная проблема, длинная переписка.

При зависимости решения от непрочитанного вложения или отсутствующего обязательного факта показывать неполноту и не считать действие готовым. Не включать автоматический анализ всех вложений только ради заполнения журнала.

## 5. Надёжность и конфиденциальность

- PostgreSQL — долговременный источник; Redis остаётся кэшем. Сброс кэша не удаляет основания уже принятого решения.
- Для изменения заявки или инфраструктуры сохранить ссылку на зафиксированное решение до публикации команды, согласовав её с существующей транзакцией/outbox. Нельзя отправить действие и затем молча потерять его основания.
- Ошибка записи журнала блокирует новые изменяющие действия, но не просмотр доступных данных. Уже выполняемая внешняя команда не объявляется неуспешной из-за сбоя аудита; результат восстанавливается существующим механизмом команд.
- Обычные логи содержат ID и безопасные метаданные. Секреты, токены и пароли не сохраняются ни в снимках, ни в промптах аудита; очистка нужна также для произвольного текста заявки.
- Чувствительные артефакты хранятся внутри разрешённого контура с шифрованием и текущими RBAC-проверками. Не копировать исходные данные в облачный мониторинг. Детальный аудит доступен только уполномоченным пользователям, имеющим доступ к соответствующей заявке.
- Хранить в рамках уже принятого срока аудита пилота — не менее 365 дней; в этом этапе не добавлять автоматическую очистку. Нельзя обещать полное воспроизведение для запрещённых к хранению фрагментов.
- Ограничить размер артефактов и страницы чтения. При усечении фиксировать объём и причину; большие разрешённые артефакты отделять от короткой записи решения. Бинарные вложения целиком по умолчанию не дублировать.

## 6. Оценка качества

Исправить заглушки TriageAuditLog: отсутствующая генерация и неизвестная уверенность остаются неизвестными. Разницу текста считать только при наличии исходного предложения и окончательного ответа. Сохранять также изменение статуса/цели/действия: одинаковый текст не означает одинаковое решение.

Оценка инженера: корректно / частично корректно / ошибочно / недостаточно данных. Основания ошибок: неверный контекст, классификация, правило, источник знаний, AI-текст, политика, исполнение. Оценка привязана к версии решения; последующее уточнение не стирает предыдущую оценку.

Принятие без правок не доказывает корректность; успешная команда не доказывает правильность выбранного действия. Сходство RAG не является вероятностью успеха. Метрики показывают размер выборки, долю оценённых и пропущенные данные. Автоматического обучения на каждом закрытии не вводить.

Минимальный просмотр Web UI: контекст → основания → предложение → правки/подтверждение → команда → проверенный результат. Нужны фильтры по ошибке, fallback, редиректу, отмене, паузе и режиму. Полный редизайн остаётся следующим этапом.
