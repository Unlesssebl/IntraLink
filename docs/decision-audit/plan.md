# План реализации единого AI-контура и автопилота

## Результат

Расширить текущий `core-api` и PostgreSQL без нового микросервиса. Rule Engine, RAG, AI, политика и исполнение останутся отдельными этапами одного процесса, а Web UI будет показывать единое предложение с понятными основаниями и фактическим результатом.

Работы выполнять небольшими законченными этапами.

## 1. Сначала устранить опасное поведение автопилота

- Неподдерживаемый сценарий переводит цикл в `paused` с причиной `unsupported_scenario`; заявка в IntraService не изменяется.
- Ошибка инфраструктуры, неизвестный или частичный результат также останавливают цикл без отмены заявки.
- Отмена применяется только к подтверждённому неверному разделу, дубликату и исчерпанию уточнений по отдельным шаблонам.
- Перед отменой повторно загружаются статус, раздел, исполнители и новые комментарии.
- Редирект разрешается только при однозначной классификации и доступной ссылке на целевой сервис. Цикл маршрутизации останавливается.
- Разделить существующий `autopilot_unsupported_cancel` на самостоятельные причины и шаблоны.

## 2. Сделать сервисную учётную запись единым источником истины

- Администратор задаёт сервисную учётную запись IntraService через Web UI.
- После проверки сохранять в PostgreSQL логин, зашифрованный пароль, URL и подтверждённый `user_id`.
- Redis хранит только рабочий кэш авторизации и `user_id`; при запуске он восстанавливается из PostgreSQL.
- Убрать использование `INTRASERVICE_SERVICE_USER_ID` из логики триггера, poller и runner.
- Смена пароля того же пользователя разрешена. Смена или удаление учётной записи возвращает `409`, пока автопилот включён либо существуют активные циклы.
- Если PostgreSQL недоступен, настройка не считается сохранённой. Ошибка синхронизации Redis показывается как деградация, а сохранённая конфигурация остаётся в БД.
- В настройках показывать логин, проверенный ID, состояние Redis и препятствия для включения автопилота.

## 3. Ввести реестр поддерживаемых сценариев

Добавить PostgreSQL-реестр со следующими полями: сервис IntraService, ключ сценария, состояние включения, версия конфигурации и автор изменения.

- Реестр изначально пуст, автопилот выключен.
- Назначение сервисной учётной записи запускает новый цикл только для включённого сценария и статуса «Открыта» (`31`).
- Уже созданный цикл может продолжаться в разрешённых незакрытых статусах.
- Добавление нового сценария не возобновляет старые приостановленные циклы.
- Управление реестром разместить рядом с глобальным переключателем автопилота в админ-панели.

## 4. Добавить долговременный журнал решений

Создать три связанные сущности:

- `decision_records` — версия решения, снимок заявки, полнота контекста, предложение, политика и итог анализа;
- `decision_steps` — фактически выполненные проверки Rule Engine, RAG и AI, включая ошибки, кэш и fallback;
- `decision_feedback` — принятие, изменение, отклонение и последующая оценка инженером.

В `commands` добавить обязательную для новых изменяющих действий ссылку `decision_id`.

Основные правила:

- Одинаковый просмотр неизменившейся заявки возвращает существующее решение.
- Изменение заявки или принудительный переразбор создаёт новую версию.
- Фиксируются использованные и исключённые сообщения, состояние вложений, запрос и результаты RAG, версии правил и промпта, фактическая модель и backend.
- Неизвестные токены, уверенность и метрики сохраняются как `null`.
- Внутренние рассуждения модели не сохраняются.
- Перед созданием команды решение повторно проверяется по версии и fingerprint. Устаревшее решение возвращает `409`.
- Решение и команда создаются одной транзакцией до публикации outbox-события.
- Старый `TriageAuditLog` удалить после переноса рабочего кода; данные из него не переносить.

## 5. Обновить серверные контракты

- Ответ триажа получает объект `decision`: ID, версия, происхождение, готовность, полнота, предложение, последствия, политика и причины блокировки.
- `has_ai_solution` заменить структурированными признаками `sources` и `readiness`; совпадение правила больше не считается участием AI.
- Rule Engine возвращает решение вместе с трассировкой проверенных правил и ошибок.
- AI Hub возвращает результат вместе с моделью, контуром, длительностью, кэшем, fallback и доступными токенами.
- Команда принимает `decision_id` и `decision_version`.
- Добавить:
  - `GET /api/v2/tasks/{task_id}/decisions`;
  - `GET /api/v2/decisions/{decision_id}`;
  - `POST /api/v2/decisions/{decision_id}/feedback`.
- Чтение требует `triage:read` и `audit:read`, обратная связь — `triage:mutate`.

## 6. Привести Web UI к единой модели

- Объединить `AiTriageCard`, AI-сводку, RAG-совпадения и состояние цикла в одну панель решения.
- В верхней части показывать: режим, предлагаемое действие, готовность, последствия и основную кнопку.
- Ниже раскрывать основания: правила, знания, AI, диагностику, полноту контекста и ограничения.
- Историю решений и исполнения показывать пользовательскими событиями, сохраняя технические сведения в раскрываемой части.
- Редактирование ответа сохранять при фоновом обновлении. При изменении заявки показывать устаревание и требовать перерасчёт.
- В очереди добавить состояния «нужно внимание», «ждёт ответа», «ждёт подтверждения», «выполняется», «пауза» и «ошибка связи».
- При ошибке обновления сохранять последнее известное состояние с отметкой времени, а не очищать данные.
- Массовые действия проверять отдельно для каждой заявки и показывать частичный результат.

## 7. Проверка и приёмка

- Миграции проверить на чистой PostgreSQL-базе; совместимость и перенос старых данных не требуются.
- Backend-тесты покрывают правило без AI, ошибку правила с fallback, непрочитанное вложение, длинную переписку, устаревшее решение, повторную команду и конкурентное подтверждение.
- Сценарии автопилота покрывают неподдерживаемую заявку, неверный раздел, неоднозначный редирект, поздний ответ, частичный внешний успех, выключение во время команды и внешнее закрытие.
- Проверить смену сервисной учётной записи, недоступность PostgreSQL, восстановление Redis и запрет смены при активном автопилоте.
- Для Web UI выполнить типизацию, тесты компонентов, production build и визуальную проверку очереди, карточки и настроек.
- Финальная проверка проводится на выделенных тестовых заявках без массового включения автопилота.

## Принятые ограничения

- На этом этапе разрабатывается только Web UI; Telegram и CLI не расширяются.
- Автоматическое чтение всех вложений не добавляется. Интерфейс честно показывает, какие вложения не анализировались.
- Реестр сценариев не заполняется предположительными ID: поддерживаемые сервисы включаются администратором после настройки.
- Автопилот после миграции остаётся выключенным.
- Старую базу и старый формат аудита не сохранять и не переносить.
