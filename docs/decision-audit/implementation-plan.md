# План реализации и приёмка журнала решений

Статус: не начат. Требования — в [requirements.md](requirements.md). Выполнять последовательно; не считать создание таблицы завершением наблюдаемости.

## 1. Контракт и хранение

Добавить минимальные модели решения, связанных артефактов/попыток и оценки либо обоснованно расширить существующие. Сохранить связь с TicketRun и CommandRecord. Добавить Alembic-миграцию, ограничения корреляции и дедупликации, разграничение доступа. Чувствительное содержимое не помещать в общие события.

Готово: чистая БД создаётся миграциями; решение без команды сохраняется; новая версия не переписывает старую; повторное чтение не создаёт дубликат. Старые данные остаются явно неполными.

## 2. Сбор оснований в реальных путях

Подключить операторский пакетный триаж, карточку/переанализ и выбор шагов автопилота. Зафиксировать состав входа, проверки правил, выборку RAG, реальные AI-вызовы и fallback. Не восстанавливать происхождение задним числом из has_ai_solution. Каждый путь может иметь разную глубину анализа, но обязан честно её обозначать.

Готово: различимы правило без модели, AI-черновик, RAG-подсказка, отсутствие решения и ошибка компонента. В кэше сохраняется ссылка на происхождение результата; новое решение после изменения фактов имеет собственную запись.

## 3. Связь с командой и обратная связь

Связать подготовленное действие, версию политики, согласование и команду. Для ручного действия без AI фиксировать ручной источник. Исправить заглушки generated_comment/confidence/diff. Добавить оценку инженера, не превращая её в обязательную анкету при каждом действии.

Готово: по команде доступны основания на момент отправки, исходное предложение и правки. Сбой сохранения до отправки не допускает внешнего изменения. Частичный успех и неизвестный результат не превращаются в полный успех.

## 4. Минимальный просмотр и проверка набора данных

Добавить чтение истории решения в текущую карточку через существующую авторизацию и короткое представление для разбора. Обеспечить фильтры, пагинацию, показ неполноты и оценку. Оценить размер записей на репрезентативных примерах и проверить отсутствие секретов в общих логах.

Готово: инженер объясняет решение по сохранённой записи после изменения заявки и очистки Redis. Если часть данных не сохранена по политике, интерфейс прямо обозначает предел восстановления.

## Обязательные проверки

| Сценарий | Ожидаемое доказательство |
|---|---|
| Правило без AI | Нет ложного AI-источника; записаны правило и факты |
| Ошибка раннего правила, затем fallback | Ошибка и неполнота видны; fallback не выглядит доказанным решением |
| Последние пять сообщений не содержат раннего уточнения | Видно, какой контекст реально использован и что исключено |
| Вложение с единственным описанием проблемы не прочитано | Неполнота явно показана, готовность не выдумана |
| Изменены RAG-источник, промпт или правило после решения | Сохранены прежние версии/фрагменты, новые значения не подменяют историю |
| Кэш и fallback между моделями | Отражены фактический источник и попытки, неизвестные токены не равны нулю |
| Инженер изменил текст, статус или цель | Исходное предложение связано с окончательным действием; различия реальные |
| Рекомендация отклонена или ни одно правило не подошло | Запись существует без успешной команды |
| Сбой БД перед публикацией команды | Внешнее действие не отправлено; нет команды без обязательных оснований |
| Сбой после внешнего вызова, рестарт, повторное событие | Существующее действие сверяется, не повторяется ради журнала |
| Два одновременных подтверждения | Одна допустимая команда, согласованная версия, понятный конфликт |
| Пользователь без доступа к заявке | Нельзя прочитать снимок, промпт или исходный текст через API аудита |
| Секрет в описании или сообщении | Не попадает в общие логи и незашифрованные артефакты; ограничение восстановления обозначено |

Сначала изолированные тесты с подставными внешними системами, затем сквозная проверка на выделенных тестовых заявках. Повторный прогон анализа по сохранённым примерам не исполняет внешние команды. Для стохастической модели не требовать побайтного совпадения ответа: проверять основания, ограничения и корректность выбранного действия.

## Переход к следующему этапу

После приёмки журнала выполнять [согласование backend и UI](../web-autopilot/concept-alignment.md): исправление исходов автопилота, единое предложение, карточка и очередь. Устранение известной опасной отмены неподдерживаемых заявок не следует откладывать ради полного интерфейса аудита; эти работы совместимы, но не расширяют автоматически область включённого автопилота.

Результат сдачи: миграции и код, результаты перечисленных проверок, несколько обезличенных примеров решений с разными исходами и явный список ограничений. Сохранённая информация должна позволять предметный разбор, а не только подсчёт вызовов AI.
