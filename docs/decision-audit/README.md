## Результат этапа

По конкретному решению можно восстановить: что система знала, что не прочитала, какое правило применилось, какие знания и модель участвовали, что предложили, что изменил инженер, какая команда выполнена и что подтверждено результатом.

Журнал фиксирует фактические основания и артефакты, а не внутренние рассуждения модели. Это не полная запись всех данных Helpdesk и не новая система исполнения.

## Рамки для реализации

- Использовать PostgreSQL, текущую авторизацию, Command API и события циклов. Не вводить внешний сервис трассировки или вторую очередь команд.
- Один формат решения для ручного триажа и автопилота; решение может существовать без цикла и без команды.
- Сначала надёжно собирать данные и дать минимальный просмотр; затем выполнять продуктовый редизайн.
- Не менять модели, не расширять автономные сценарии и не подключать массовый OCR в рамках этого этапа.
- Старые записи не заполнять выдуманными основаниями. Показывать «основания не сохранены».
- Сохранение старой БД не требуется, но автоматическое удаление данных не добавлять. Миграции должны создавать актуальную схему на чистой БД.

Предыдущий [план автопилота](../web-autopilot/implementation-plan.md) относится к уже выполненному этапу циклов и не заменяет этот план.
