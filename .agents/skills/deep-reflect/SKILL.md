# 🏛️ Workflow: Глубокая архитектурная рефлексия и эволюция системы (`/deep-reflect`)

Системный процесс глубокого стратегического аудита архитектуры, технологического стека, межсервисных связей, внешних зависимостей и ресурсной эффективности всей экосистемы IntraLink.

В отличие от оперативного `/reflect` (который оптимизирует только сессионный контекст и память агента), `/deep-reflect` производит **фундаментальную ревизию инженерных решений** с генерацией матрицы решений (ADR / RFC) и плана безопасной эволюции.

---

## 🧭 Методологические оси анализа (5D Evaluation Framework)

При запуске `/deep-reflect` агент выполняет многомерную оценку компонентов:

```
                  [ 1. Архитектурные границы & Связность ]
                                     ▲
                                     │
   [ 5. Безопасность & Отказоустойчивость ] ◄─┼─► [ 2. Технологический стек & Зависимости ]
                                     │
                                     ▼
                  [ 4. Ресурсная эффективность & I/O ]
                                     ▲
                                     │
                                     ▼
                  [ 3. Протоколы & Паттерны коммуникации ]
```

### 1. Архитектурные границы и связность (Component Boundaries)
- Оценка разделения ответственности между `core-api`, `bot`, `ai-worker`, `printer-worker` и `helpdesk_agent`.
- Выявление скрытого дублирования логики (например, дублирование парсинга полей или авторизации).
- Проверка чистоты контрактов API и предотвращение утечек абстракций.

### 2. Стек технологий и сторонние зависимости (Dependency Ecosystem)
- Поиск устаревших, медленных или неподдерживаемых библиотек.
- Оценка перехода на высокопроизводительные альтернативы (например, `orjson` / `msgpack` вместо стандартного `json`, нативные асинхронные драйверы, легковесные векторные движки).
- Анализ целесообразности подключения проверенных внешних open-source модулей или специализированных утилит.

### 3. Протоколы и шина данных (Communication & Messaging)
- Анализ модели доставки сообщений (Redis Pub/Sub vs Redis Streams / RabbitMQ для гарантированной доставки).
- Оценка накладных расходов на сериализацию/десериализацию данных.
- Проверка эффективности долгоживущих HTTP-сессий (`aiohttp`) и пулов соединений к PostgreSQL/Redis.

### 4. Ресурсная эффективность и I/O (Resource & Concurrency Profile)
- Выявление скрытых блокировок `asyncio.loop` при вызове тяжелых синхронных библиотек (WinRM, SMB, FastEmbed).
- Аудит конфигурации пулов потоков (`ThreadPoolExecutor`), семафоров и ограничений параллелизма.
- Оптимизация профиля потребления памяти (RAM) при батчевой обработке и векторном поиске.

### 5. Отказоустойчивость и живучесть (Resilience & Fault Tolerance)
- Проверка поведения при деградации внешних систем (IntraService API down, сетевой таймаут, сбой Redis).
- Анализ механизмов Graceful Shutdown, идемпотентности повторных запросов и предотвращения каскадных сбоев.

## 🛠 Порядок выполнения workflow

### Этап 1. Сбор контекста и профилирование (Zero-Assumption Inspection)
1. Агент анализирует ключевые манифесты и точки входа:
   - Конфигурации зависимостей: `pyproject.toml`, `requirements.txt`, `Pipfile`, `docker-compose.yml`.
   - Архитектурные манифесты: [`docs/architecture.md`](docs/architecture.md).
   - Точки входа сервисов и воркеров (`main.py`, `worker.py`, `orchestrator.py`).
2. Сопоставляет текущую реализацию с целевыми метриками (Latency, Concurrency, Memory Footprint, MTBF).

### Этап 2. Сравнительный бенчмаркинг альтернатив (Trade-off Matrix)
Для каждого выявленного узкого места агент формулирует альтернативные инженерные решения:
- **Вариант А (Минимальный инкремент):** Точечная замена библиотеки / конфигурации без изменения контрактов.
- **Вариант Б (Оптимальный баланс):** Рефакторинг слоя с внедрением более производительного паттерна/модуля.
- **Вариант В (Радикальная эволюция):** Выделение нового микросервиса или переход на специализированный движок.

### Этап 3. Формирование артефакта решения (ADR / Evolution Report)
Результат формируется в виде структурированного документа:

```markdown
# 🏛️ Архитектурный отчет / ADR: [Название оптимизации]

## 1. Проблемная область и узкое место (Context & Problem)
[Четкое описание неэффективности, метрики, риски]

## 2. Матрица сравнительного анализа (Options & Trade-offs)
| Критерий | Текущее решение | Альтернатива 1 | Альтернатива 2 |
|---|---|---|---|
| Производительность | ... | ... | ... |
| Потребление памяти | ... | ... | ... |
| Сложность миграции | ... | ... | ... |
| Надежность / Зрелость | ... | ... | ... |

## 3. Рекомендуемое целевое состояние (Target Architecture)
[Архитектурное решение с обоснованием выбора]

## 4. План безопасной поэтапной миграции (Zero-Downtime Rollout)
1. Фаза 1: Подготовка контрактов и параллельных адаптеров.
2. Фаза 2: Canary/Shadow тестирование под нагрузкой.
3. Фаза 3: Переключение трафика и вывод устаревшего кода.
```

### Этап 4. Согласование с инженером (Architectural HITL)
- Агент презентует выжимку оператору, подсвечивая риски и профит (ROI).
- При согласии инженера формируется задача на реализацию или создается отдельная ветка/план изменений.

## 🔒 Принципы безопасности при эволюции

1. **No Big-Bang Refactoring:** Фундаментальные изменения разбиваются на изолированные, тестируемые шаги.
2. **Backward Compatibility:** Сохранение обратной совместимости межсервисных контрактов на период миграции.
3. **Fail-Safe Defaults:** При сбое нового компонента всегда должен сохраняться работоспособный fallback-сценарий.
