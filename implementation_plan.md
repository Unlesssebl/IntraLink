# Единый план: понятный жизненный цикл AI-анализа заявок

## 1. Цель

Устранить главную неоднозначность операторского интерфейса: оператор должен сразу понимать, анализировалась ли заявка, актуален ли результат, почему действие доступно или заблокировано и изменялась ли заявка после анализа.

Работа выполняется backend-first: одновременно с упрощением frontend приводятся в порядок модель состояния, API-контракты, конкурентное выполнение, применение решений и устаревший cache-driven код backend.

## Статус реализации на 2026-09-08

Сложные и рискованные части реализованы:

- `DecisionRecord` стал источником истины для очереди и инспектора;
- GET очереди и карточки больше не запускают Rule Engine, RAG или AI;
- добавлены явные single/batch analyze и reanalyze endpoints;
- добавлены `ANALYSIS_REVISION`, source fingerprint, повторная сверка заявки и Redis lease с fencing token и атомарным освобождением;
- последняя неудачная попытка сохраняется отдельно от последнего успешного результата;
- применение AI-решения привязано к `decision_id/version` и блокируется для stale/unknown/failed;
- состояние `applied` определяется по успешно выполненной Command API v2 команде;
- frontend использует серверный `analysis`, серверные счётчики и не выполняет скрытый GET после reanalyze;
- добавлены operator-facing статусы и отдельные действия «Проанализировать»/«Проанализировать повторно».

Оставлено для следующего, более простого прохода:

- добавить новые настройки в `.env.example` и эксплуатационную документацию;
- перевести оставшихся потребителей CLI/Telegram и затем удалить legacy DTO/cache endpoint;
- унифицировать REST/SSE mapper статусов IntraService;
- довести тексты пустых состояний, подсказки и раскрываемый debug-блок;
- добавить отображение асинхронного прогресса batch через SSE, если синхронного ответа недостаточно;
- выполнить согласованное пересоздание PostgreSQL/Redis и повторную индексацию RAG отдельной эксплуатационной операцией.

Пересоздание БД намеренно не выполнялось в рамках изменения кода: это отдельная разрушительная операция после проверки и остановки внешних workers.

Проверено: 23 целевых backend-теста, Ruff, TypeScript typecheck и production Docker build `core-api` проходят. Контейнеры приложения не перезапускались.

## 2. Зафиксированные продуктовые решения

- В очереди остаются две операторские вкладки с точными названиями:
  - «Проанализированные AI»;
  - «Не проанализированные AI».
- Вкладка определяется наличием пригодного сохранённого результата, а не названием сценария, наличием RAG, AI-текста или frontend-эвристикой.
- `consultation` — полноценный результат анализа и относится к «Проанализированные AI».
- Открытие инспектора и обычное обновление данных являются read-only и никогда не запускают анализ.
- Повторный анализ запускается только явным действием оператора.
- Быстрое применение сохраняется только для актуального результата со статусом `ready` и всегда подтверждается оператором.
- В интерфейсе используется терминология IntraService. Технические сведения доступны для отладки, но скрыты в раскрываемом блоке «Как получено решение».
- PostgreSQL и Redis разрешено пересоздать без сохранения текущего содержимого. Новая миграция только ради этого изменения не создаётся.
- Старые реализации сценариев хранить не требуется. Результат содержит только номер ревизии логики, которой он был рассчитан.

## 3. Проблемы текущей реализации

1. `GET /api/v1/triage/tasks/{id}` повторно выполняет Rule Engine, RAG и AI, сохраняет решение и тем самым изменяет состояние при простом открытии инспектора.
2. После `POST /reanalyze` frontend повторно вызывает `GET details`, поэтому только что рассчитанная заявка может ещё раз пересчитаться и выглядеть устаревшей.
3. Очередь получает вычисленный `decision_envelope`, но не опирается на единый долговечный `DecisionRecord` как источник истины.
4. `isTicketProcessed` использует косвенные признаки и исключает штатный сценарий `consultation`.
5. `ai_suggestions.snapshot_fingerprint` смешивает данные заявки с вычисленным решением и может создавать ложное устаревание.
6. Массовый запуск использует клиентский `Promise.allSettled`, скрывает часть ошибок и при пустом списке способен перейти к глобальному очищению Redis.
7. Счётчики строятся по загруженной части очереди, поэтому при лимите 200 заявок не отражают всю область фильтра.
8. Frontend перегружает строку очереди и инспектор RAG/AI/техническими признаками, которые не помогают оператору принять решение.
9. Legacy API, CLI и другие клиенты могут зависеть от старого вычисляющего поведения `GET`.

## 4. Целевая модель состояния

### 4.1. Источник истины

Единственным источником истины о результате анализа становится последний долговечный `DecisionRecord` с `analysis_kind = "triage"`. Redis используется только для блокировок, краткоживущего прогресса и доставки событий, но не определяет, анализировалась ли заявка.

Существующую таблицу `decision_records` и её `context_json` использовать без изменения схемы. В `context_json` сохранять:

- `ticket_snapshot_fingerprint` — отпечаток изменяемых данных заявки и истории IntraService;
- `analysis_revision` — единый номер текущей логики анализа;
- идентификатор сценария и краткое объяснение выбора;
- использованные источники и диагностические признаки;
- снимок результата, необходимый для воспроизводимого отображения;
- ожидаемые изменения заявки при применении решения.

`context_fingerprint` остаётся внутренним ключом идемпотентности и рассчитывается из снимка заявки и основания анализа. Он не используется как пользовательское объяснение актуальности.

### 4.2. Ревизия логики

В системе хранится только текущая реализация сценариев и один `ANALYSIS_REVISION`.

- Ревизия повышается при изменении сценариев, политик, правил, шаблонов или алгоритма, способном изменить решение.
- Сохранённый результат содержит номер применённой ревизии.
- Несовпадение сохранённой и текущей ревизии означает `stale` с причиной «Правила анализа изменились».
- Обновление RAG-индекса само по себе не инвалидирует все заявки. Оно влияет на результат только после явного повторного анализа, если отдельно не принято другое продуктовое решение.

### 4.3. Публичное состояние анализа

API возвращает отдельный объект `analysis`, не заставляя frontend восстанавливать состояние из `scenario_key`:

```json
{
  "has_result": true,
  "state": "ready",
  "freshness": "current",
  "disposition": "available",
  "decision_id": "uuid",
  "decision_version": 3,
  "scenario_key": "consultation",
  "analyzed_at": "2026-09-08T12:00:00Z",
  "stale_reason": null,
  "last_attempt": {
    "state": "succeeded",
    "error_code": null,
    "finished_at": "2026-09-08T12:00:00Z"
  },
  "can_quick_apply": true,
  "blocked_reason": null
}
```

Допустимые значения:

- `state`: `not_analyzed`, `analyzing`, `ready`, `failed`;
- `freshness`: `current`, `stale`, `unknown`;
- `disposition`: `available`, `applied`.

Правила:

- начальная ошибка без результата: `has_result=false`, `state=failed`;
- ошибка повторного анализа при наличии старого результата: `has_result=true`, `state=failed`, старый результат остаётся видимым, но `can_quick_apply=false`;
- IntraService недоступен для проверки: `freshness=unknown`, а не `current` или `stale`;
- после успешного применения: `disposition=applied`, интерфейс показывает «Решение применено» и не предлагает немедленный повторный анализ;
- ручное изменение заявки после анализа переводит результат в `stale`;
- сценарий `consultation` имеет `state=ready`, если его результат корректно сформирован.

На переходный период legacy-поля `suggested_action`, `decision_envelope` и `ai_suggestion` заполняются из последнего долговечного результата. После перевода всех клиентов они удаляются отдельной задачей.

## 5. Целевой API и backend

### 5.1. Read-only чтение

Изменить:

- `GET /api/v1/triage/batch` — получает заявки и одним пакетным запросом добавляет последнее состояние анализа, серверные счётчики и область выборки;
- `GET /api/v1/triage/tasks/{id}` — получает актуальные данные IntraService и сохранённый результат, вычисляет только его freshness, но не запускает RAG/AI и не пишет в БД;
- отдельный read-only endpoint статуса batch допустим, если это упростит polling.

Не выполнять в GET:

- создание новой версии решения;
- принудительный сброс кэша;
- RAG-поиск и LLM-вызов;
- изменение заявки или команды;
- запись «просмотра» как нового анализа.

### 5.2. Явный анализ

Добавить или нормализовать команды:

- `POST /api/v1/triage/tasks/{id}/analyze` — создаёт результат, если пригодного результата ещё нет;
- `POST /api/v1/triage/tasks/{id}/reanalyze` — создаёт новую версию только по явному запросу;
- `POST /api/v1/triage/analyze-batch` — серверная пакетная обработка ограниченного набора ID или зафиксированной области фильтра.

Batch-контракт должен включать:

- область: `filter_id`, выбранный сервис и/или явные `task_ids`;
- максимальный размер запроса и дедупликацию ID;
- ограниченный серверный concurrency;
- итоговые `processed`, `skipped`, `failed` и ошибки по заявкам;
- идентификатор запуска для polling/SSE;
- отсутствие глобального `cache/purge`.

### 5.3. Защита от гонок

Для одной заявки одновременно допускается один расчёт:

1. Получить Redis-lock с уникальным owner/fencing token.
2. Прочитать заявку и зафиксировать исходный `ticket_snapshot_fingerprint`.
3. Выполнить анализ.
4. Перед финализацией повторно прочитать заявку и сравнить fingerprint.
5. Проверить, что lock всё ещё принадлежит текущему обработчику и его token новее уже сохранённого.
6. Если заявка изменилась или lease потерян, сохранить сведения о попытке, но не публиковать результат как `current`.
7. Поздно завершившийся обработчик не может перезаписать более новую версию.

Повторный запрос во время активного анализа возвращает существующий run/status, а не запускает второй расчёт.

### 5.4. Ошибки и предыдущие результаты

Разделить:

- последнюю попытку анализа;
- последний успешно финализированный результат;
- последний результат, разрешённый к применению.

Ошибка новой попытки не удаляет предыдущий результат. При этом предыдущий результат блокируется для быстрого применения, пока backend не подтвердит его актуальность.

Таймауты, отмена и недоступность зависимостей имеют стабильные error codes. Пользовательские сообщения не содержат stack trace, секреты или персональные данные из технических payload.

### 5.5. Применение решения

Frontend передаёт в Command API v2 `decision_id` и `decision_version`. Перед постановкой команды backend повторно проверяет:

- решение существует и относится к заявке;
- это последняя применимая triage-версия;
- состояние `ready`, freshness `current`, disposition `available`;
- текущий fingerprint заявки совпадает с зафиксированным;
- обязательные поля, policy и подтверждение оператора валидны.

После успешной команды записать feedback/связь с решением и перевести его в `applied`. Изменения статуса и комментария, ожидаемые от самой команды, не должны превращать только что применённое решение в обычный `stale`. Неожиданный или ручной drift помечает его устаревшим.

Неизвестный результат внешней мутации не повторять автоматически: состояние команды переводится в `needs_review`, после чего выполняется только read-only reconciliation.

### 5.6. Безопасность и наблюдаемость

- Для `analyze`, `reanalyze` и batch требуется `triage:mutate`.
- Для mutating endpoint обязательны trusted-origin/CSRF-проверка, аудит оператора и rate limit.
- Логировать correlation/run ID, task ID, ревизию, длительность этапов, причину stale, lock contention и код ошибки без секретов и лишних данных заявки.
- Добавить метрики: latency, success/failure, доля stale/unknown, batch backlog, lock conflicts и количество применений.

## 6. UX очереди оператора

### 6.1. Классификация вкладок

- «Проанализированные AI»: `analysis.has_result=true`, включая `stale`, `unknown`, `applied` и старый результат после ошибки повторного анализа.
- «Не проанализированные AI»: пригодного результата никогда не было; сюда входят `not_analyzed`, первая `analyzing` и первая неуспешная попытка.
- Перемещение между вкладками происходит только после подтверждённого ответа backend/SSE, а не оптимистически по локальной эвристике.

Счётчики возвращает backend для всей выбранной области, а не только для текущих 200 строк. Интерфейс явно показывает область действия, например: «Фильтр 984 · Все сервисы · 37 без анализа».

### 6.2. Строка заявки

В основной строке оставить только сведения, необходимые оператору:

- ID и тема;
- заявитель/рабочая станция при наличии;
- сервис IntraService;
- точный статус IntraService;
- компактный AI-статус;
- основное действие.

AI-статусы показываются компактным pill-индикатором:

- «Анализируется»;
- «Готово»;
- «Устарело»;
- «Актуальность не проверена»;
- «Ошибка анализа»;
- «Решение применено».

Не выводить отдельными колонками признаки RAG, Rule Engine, confidence, fingerprint и источник вычисления. Они доступны в инспекторе. Таблица должна сохранять рассчитанную минимальную ширину и горизонтальный scroll вместо наложения колонок.

### 6.3. Действия в очереди

- Во вкладке «Не проанализированные AI» основное пакетное действие — «Проанализировать».
- Во вкладке «Проанализированные AI» пакетный повторный анализ не является действием по умолчанию и требует явного выбора заявок.
- Кнопка не запускает глобальный purge и не переанализирует скрытые или уже готовые заявки.
- Прогресс показывает общий объём, завершённые, ошибки и возможность повторить только неуспешные.
- Быстрое применение доступно только при `can_quick_apply=true` и после подтверждения с итоговым статусом IntraService, текстом комментария и трудозатратами.
- Для заблокированной кнопки рядом выводится доступная с клавиатуры причина; не полагаться только на tooltip у disabled-элемента.

Пустые состояния:

- «Проанализированные AI»: «Нет проанализированных заявок»;
- «Не проанализированные AI»: «Все заявки в выбранной области проанализированы AI».

## 7. UX инспектора

### 7.1. Верхний уровень

Сразу после открытия показать:

- точный статус заявки в IntraService;
- состояние анализа и время последнего успешного результата;
- краткую рекомендацию;
- основное разрешённое действие;
- понятную причину блокировки, если действие недоступно.

Не использовать формулировку «обновить информацию» для повторного анализа.

- «Обновить данные заявки» — только повторное read-only чтение IntraService;
- «Проанализировать» — первый расчёт;
- «Проанализировать повторно» — новая версия результата с подтверждением причины/намерения.

### 7.2. Доказательства и отладка

В раскрываемом блоке «Как получено решение» показывать:

- выбранный сценарий и объяснение;
- факты и недостающие данные;
- RAG-совпадения;
- результаты диагностик;
- версии решения и ревизию логики;
- причины `stale`, `unknown` или ошибки;
- технические timestamps/correlation ID.

Запуск диагностики хоста остаётся в единственном месте контекста рабочей станции. В evidence-разделе показываются только результаты.

### 7.3. Черновик оператора

Повторный анализ не перезаписывает непустой отредактированный комментарий. Новый AI-вариант отображается отдельно с действиями «Сравнить» и «Заменить черновик».

## 8. Совместимость и удаление legacy

Перед изменением поведения GET найти потребителей в:

- `intra-web`;
- `helpdesk-cli`;
- `telegram-bot`;
- тестах и скриптах автоматизации.

Для каждого потребителя заменить ожидание «GET вычисляет решение» на явный `analyze/reanalyze`. На переходный период сохранить additive DTO и legacy-поля. После перевода клиентов:

- удалить frontend-эвристики `isTicketProcessed`;
- удалить fallback к глобальному `purgeTriageCache`;
- исключить cache fingerprint из проверки применимости;
- удалить недостижимые вкладки/ветки инспектора и дублирующие действия;
- синхронизировать общий mapper статусов IntraService для REST и SSE, чтобы неизвестный status ID не ломал таблицу.

## 9. Пересоздание БД и Redis

Пересоздание выполняется после реализации и проверки кода на отдельной пустой БД.

### 9.1. Что будет удалено

- Docker volume `postgres_data`: решения, история команд, feedback, RAG/embeddings, системные настройки, principals/sessions и прочие локальные данные IntraLink;
- Docker volume `redis_data`: кэш, locks, progress и необработанные Redis-сообщения.

Данные IntraService и файлы `.secrets` не удаляются.

### 9.2. Предохранители перед удалением

1. Разрешить точные compose project/volume names; не использовать широкие маски.
2. Остановить приём новых mutating-команд.
3. Остановить/осушить Docker workers и внешний Windows execution-worker.
4. Убедиться, что нет выполняющихся удалённых операций. Неясный результат сначала перевести в `needs_review` и сверить read-only.
5. Проверить текущую цепочку Alembic на временной пустой БД до удаления рабочих volumes.
6. Подтвердить наличие корректного `ADMIN_LOGINS` и пути bootstrap первого администратора.

### 9.3. Чистый запуск

1. Остановить compose stack и внешние workers.
2. Удалить только подтверждённые volumes PostgreSQL и Redis без резервной копии — это осознанно принятое решение.
3. Запустить PostgreSQL и Redis.
4. Выполнить существующую цепочку Alembic до `head`; новую миграцию для этого плана не создавать, пока не появится реальное изменение схемы.
5. Запустить `core-api` и проверить health/readiness.
6. Войти первым администратором и восстановить обязательные системные настройки/секрет-ссылки.
7. Выполнить полную синхронизацию/переиндексацию RAG.
8. Запустить workers только после проверки настроек и очередей.
9. Выполнить smoke-analysis одной тестовой заявки, затем разрешить batch.

## 10. Этапы реализации

### Этап 1. Контракт и backend source of truth

- Ввести DTO `analysis` и правила выбора последнего triage-результата.
- Добавить `ANALYSIS_REVISION` в основание анализа.
- Сделать GET read-only и реализовать пакетную загрузку состояний/счётчиков.
- Сохранить временную обратную совместимость полей.

### Этап 2. Надёжное выполнение

- Добавить bounded concurrency, single-flight, fencing и двойную проверку fingerprint.

- Добавить ошибки, аудит, RBAC, trusted-origin и метрики.

### Этап 3. Безопасное применение

- Проверять freshness непосредственно перед постановкой команды.

### Этап 4. Frontend оператора

- Упростить строку очереди и унифицировать статусы REST/SSE.

## 11. План тестирования

### Backend

- GET details не вызывает Rule Engine/RAG/LLM и не создаёт `DecisionRecord`.
- Первый analyze создаёт одну версию; повторный параллельный запрос присоединяется к активному запуску.
- Reanalyze создаёт ровно одну новую версию.
- Поздний worker с устаревшим fencing token не может финализировать результат.
- Изменение заявки во время расчёта не публикует результат как current.
- Изменение `ANALYSIS_REVISION` делает прежний результат stale без хранения старого сценария.
- Недоступность IntraService даёт freshness unknown.
- `consultation` является готовым результатом.
- Ошибка повторного анализа сохраняет старый результат, но блокирует применение.
- Command API отвергает устаревшие ID/version/fingerprint.
- Успешное применение переводит решение в applied; неизвестный исход — в needs_review без автоматического retry.
- Batch соблюдает лимит, дедупликацию, concurrency и возвращает частичные ошибки явно.
- Серверные счётчики корректны при очереди больше frontend page limit.
- Mutating endpoints проверяют permission, origin и rate limit.

### Frontend

- Вкладки классифицируются только по `analysis.has_result`.
- `consultation`, stale, unknown, applied и failed reanalysis находятся в правильной вкладке.
- Открытие и закрытие инспектора не запускает анализ.
- После reanalyze нет скрытого второго пересчёта.
- Событие SSE со старой версией не перезаписывает новое состояние.
- Неизвестный status ID отображается безопасно и не вызывает runtime error.
- Заблокированное действие имеет видимую и доступную с клавиатуры причину.
- Непустой черновик не заменяется новым AI-текстом.
- Таблица не допускает наложения колонок на поддерживаемых ширинах.
- Unit tests и `npm --prefix intra-web run build` проходят.

### Интеграция и чистый старт

- Существующая цепочка Alembic поднимает пустую БД до `head`.
- Первый администратор успешно bootstrap-ится через `ADMIN_LOGINS`.
- После восстановления настроек выполняются login, загрузка очереди, единичный анализ, reanalyze и применение.
- После переиндексации RAG поиск возвращает результаты.
- Перезапуск `core-api`, Redis и worker не создаёт дубликатов анализа или команд.
- Production bundle собирается в `core-api/app/static/admin/index.html`.

## 12. Критерии готовности

План считается реализованным, когда:

- оператор без открытия debug понимает, анализировалась ли заявка и можно ли применить результат;
- открытие инспектора ничего не пересчитывает;
- первый и повторный анализ запускаются только явными действиями;
- frontend не определяет состояние анализа эвристиками;
- stale/unknown/failed/applied различаются и имеют понятные причины;
- никакой старый или непроверенный результат нельзя применить через обход UI;
- массовый анализ ограничен, наблюдаем и не очищает общий кэш;
- CLI и другие клиенты не зависят от side-effect GET;
- пустая PostgreSQL/Redis-инсталляция полностью поднимается существующими миграциями и bootstrap-процедурой;
- автоматические, интеграционные и операторские acceptance-сценарии пройдены.
