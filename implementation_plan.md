# План безопасного запуска автопилота для создания учетных записей

## Цель и исходное состояние

Заявка [#140628](https://servicedesk-pub.corporate.loc/Task/View/140628) назначена сервисной учетной записи `alen_assistant` (User ID `10502`), но автоматический цикл не запускается или не завершается корректно из-за нескольких независимых причин:

1. Poller передает IntraService неподдерживаемый параметр `ExecutorId` вместо `ExecutorIds`.
2. Глобальный автопилот отключен.
3. Для сервиса `53` («Создание нового пользователя сети») отсутствует активная привязка сценария `create_user`.
4. Windows `execution-worker`, необходимый для работы с Active Directory, не запущен или не готов к исполнению.
5. В заявке #140628 отсутствуют обязательные реквизиты сценария: фамилия, имя, организация, подразделение и должность.
6. Ошибки команды и ошибки разрешения сценария переводят `TicketRun` в терминальное/приостановленное состояние без гарантированной публикации понятного комментария в IntraService.
7. При неизменившейся заявке ранняя проверка дубликата события может не дать оркестратору обработать новый терминальный статус команды.

## Принятые решения

- Первый запуск выполняется с подтверждением оператора для `create_user`. Автономный режим включается отдельным шагом после успешной сквозной проверки.
- Запрос недостающих данных публикуется как публичный комментарий и переводит заявку в статус 35 («Требует уточнения»).
- Ошибка исполнения публикуется как публичный комментарий без внутренних адресов, stack trace, команд PowerShell, учетных данных и иных технических секретов. Полная диагностика остается в журнале команды и событиях `TicketRun`.
- При ошибке исполнения заявка остается в статусе 27 («В работе») и помечается для ручной обработки. Текст о передаче дежурному инженеру используется только при фактическом назначении или создании соответствующего механизма эскалации.
- Статусы `needs_review` и неопределенный результат после потери lease не запускают автоматический повтор `create_user`: сначала инженер сверяет фактическое состояние учетной записи в AD.
- Изменения конфигурации выполняются через сервисный слой/API с аудитом и проверками готовности. Прямой SQL допускается только как заранее подготовленная аварийная процедура с эквивалентными проверками и записью аудита.

## Этап 1. Исправление получения и обработки заявок

### `core-api/app/services/worker.py`

В `process_autonomous_lifecycle` заменить параметр фильтра:

```diff
- "ExecutorId": assistant_user_id,
+ "ExecutorIds": str(assistant_user_id),
```

Добавить корректную пагинацию ответа IntraService. `pagesize=100` не гарантирует получение всех назначенных заявок. Poller должен пройти все страницы либо использовать общий клиентский helper пагинации и объединить результаты до `register_observed_assignments`.

### `core-api/app/services/scenario_orchestrator.py`

Изменить порядок обработки в `advance`:

1. Загрузить `TicketRun`.
2. Сначала вызвать `_reconcile_command`, поскольку статус команды может измениться при неизменном снимке заявки.
3. Только если команда не требует сверки, применять дедупликацию входного события заявки по `ticket_event_key`.

Для событий сверки команды продолжать использовать отдельный ключ вида `command:{command.id}:{command.version}:{command.status}`. Это позволяет независимо дедуплицировать входное событие заявки и переход состояния команды.

## Этап 2. Надежная доставка ошибок в IntraService

### `core-api/app/services/command_delivery.py`

Добавить два явных пути доставки:

1. `deliver_command_failure(command_id, actor, service_auth_b64=None)` для терминальных состояний команды `failed`, `rejected`, `cancelled` и `needs_review`.
2. `deliver_run_failure(run_id, error_code, error_message, actor, service_auth_b64=None)` для ошибок, возникших до создания команды, включая `resolution_error`.

Оба пути должны:

- определить `task_id` из команды или `TicketRun`;
- сформировать безопасный публичный текст по коду ошибки;
- записать полные технические сведения только в БД и серверный лог;
- оставить заявку в статусе 27 для ручной обработки;
- записать событие `command_failure_delivery_succeeded` либо `run_failure_delivery_succeeded`;
- при сбое внешнего вызова записать `*_delivery_failed`, сохранить причину и оставить доставку доступной для повторной попытки.

Рекомендуемый публичный шаблон:

> При автоматической обработке заявки произошла ошибка. Автоматическое выполнение остановлено, заявка ожидает ручной проверки инженером. Код ошибки: `{safe_error_code}`.

Для `needs_review` использовать отдельный текст, прямо запрещающий повторное создание до проверки AD:

> Результат автоматического выполнения не удалось подтвердить. Перед повторным запуском требуется проверить наличие учетной записи в Active Directory. Код проверки: `{safe_error_code}`.

### Идемпотентность доставки

Одной записи события после HTTP-вызова недостаточно: процесс может завершиться после успешной публикации комментария, но до фиксации события в PostgreSQL.

Реализация должна использовать стабильный маркер доставки, например `[AUTOPILOT:{run_id}:{failure_revision}]`, включенный в комментарий. Перед повторной публикацией сервис проверяет собственные события и, если состояние доставки неопределенно, историю комментариев IntraService на наличие маркера. Конкурирующие попытки сериализуются блокировкой строки `TicketRun`/`CommandRecord`.

Повтор доставки выполняется отдельным reconciliation-проходом для недоставленных ошибок; состояние `paused` или `system_error` не должно навсегда исключать такую попытку.

### `core-api/app/services/scenario_orchestrator.py`

В `_reconcile_command`:

- для `failed`, `rejected` и `cancelled` вызвать `deliver_command_failure`, затем перевести run в `paused`;
- для `needs_review` вызвать тот же путь со специальным шаблоном и причиной `command_result_requires_review`;
- не выполнять автоматический retry мутационного действия `create_user`;
- сохранить исходный `command.error_message` в `TicketRun.error_message`, но не публиковать его напрямую.

В ветке `envelope.policy["resolution_error"]`:

- сохранить run в `system_error` с технической причиной;
- вызвать `deliver_run_failure` без требования `command_id`;
- обеспечить повтор доставки при временной недоступности IntraService.

Если сама публикация комментария завершилась ошибкой, состояние основной команды не откатывается. Ошибка доставки учитывается отдельно и повторяется безопасно.

## Этап 3. Автоматические тесты

Добавить тесты до изменения рабочей конфигурации:

1. Poller передает `ExecutorIds="10502"` и обходит несколько страниц ответа.
2. Неизменная заявка не блокирует сверку новой версии/статуса команды.
3. `failed`, `rejected`, `cancelled` и `needs_review` приводят к одной безопасной публикации и корректному состоянию `TicketRun`.
4. `resolution_error` публикуется без `command_id`.
5. Повторный reconciliation не создает второй комментарий.
6. Сбой после успешного внешнего вызова, но до commit, распознается по стабильному маркеру в истории заявки.
7. Недоступность IntraService записывает ошибку доставки и допускает последующую повторную попытку.
8. Публичный комментарий не содержит `command.error_message`, stack trace, пароли или параметры подключения.
9. `needs_review` не создает повторную команду `create_user`.
10. Нехватка каждого обязательного факта приводит к `request_clarification`, публичному комментарию и статусу 35.

## Этап 4. Подготовка Windows execution-worker

Перед запуском определить фактический опубликованный Redis-порт из `REDIS_PORT`/Docker Compose. Значение по умолчанию в репозитории — `6379`; использовать `6380` только если оно действительно задано в окружении.

Для локального Windows-процесса задать:

```powershell
$env:REDIS_URL="redis://127.0.0.1:<published-port>/0"
$env:CORE_API_URL="http://127.0.0.1:8000"
$env:WINDOWS_WORKER_SERVICE_KEY_ID="<service-key-id>"
$env:WINDOWS_WORKER_SERVICE_SECRET="<service-secret>"
$env:PYTHONPATH="."
uv run python execution-worker/worker.py
```

Секреты не сохранять в плане, командной истории или логах. Перед сквозным тестом проверить:

- соединение с Redis;
- доступность Core API и успешную сервисную аутентификацию;
- heartbeat воркера;
- наличие capability `ad`;
- регистрацию `CreateUserHandler`, `InstallPrinterHandler` и `GrantWlanHandler`;
- успешный read-only preflight DC/OU/групп;
- получение воркером тестовой команды без выполнения изменений в AD.

## Этап 5. Настройка сценария и политик

Создать или обновить запись `autopilot_scenarios` через управляющий API/сервис:

- `service_id = 53`;
- `scenario_key = "create_user"`;
- `enabled = true`;
- `rollout_mode = "active"`;
- `config_json = {}` либо только реально читаемые кодом параметры.

Не использовать `require_approval` и `auto_deliver` в `config_json`: текущий путь исполнения их не читает.

Режим подтверждения задается в `action_policies`, а не в конфигурации сценария:

- `create_user = confirm` для первого запуска;
- `apply_triage = auto`, если автоматическая публикация запроса данных и финализация уже разрешены эксплуатационной политикой; иначе `confirm` до отдельной проверки.

После настройки сценария включить глобальный автопилот через `TicketRunService.set_global_enabled(...)` или соответствующий API с `updated_by="belikov.a"`, `reason` и актуальной `expected_version`. Этот путь должен подтвердить готовность шаблонов, сервисной учетной записи и хотя бы одного сценария и записать событие аудита.

## Этап 6. Сквозная проверка на #140628

### Ветка запроса данных

1. Зафиксировать исходный статус, исполнителей и историю комментариев заявки.
2. Запустить poller и убедиться, что #140628 найден через `ExecutorIds` и зарегистрирован ровно один `TicketRun`.
3. Проверить, что система запросила все отсутствующие обязательные данные и перевела заявку в статус 35.
4. Повторный poll без изменений не должен добавлять второй комментарий.

### Ветка подтвержденного исполнения

1. Заполнить фамилию, имя, организацию, подразделение и должность; отчество остается необязательным, если это допускает доменная модель.
2. Убедиться, что сформирована одна команда `create_user` в статусе `awaiting_approval`.
3. Проверить preflight и содержимое команды без временного пароля в логах/UI.
4. После явного подтверждения оператора выполнить команду один раз.
5. Проверить подтвержденный результат в AD, доставку результата в IntraService, целевой статус, трудозатраты и удаление временного секретного артефакта после успешной доставки.

### Ветка ошибки и неопределенного результата

Проверять ее на безопасном тестовом стенде или инъекцией ошибки в тестах, не отключая рабочий контроллер домена:

1. Смоделировать подтвержденный отказ preflight/исполнения и проверить один безопасный публичный комментарий и статус 27.
2. Смоделировать потерю lease/ответа после запуска и проверить переход в `needs_review` без автоматического retry.
3. Смоделировать временную недоступность IntraService, затем восстановление и проверить ровно одну публикацию после reconciliation.

## Этап 7. Переход к автономному режиму

Переводить `create_user` из `confirm` в `auto` только после успешного завершения всех предыдущих проверок и просмотра журнала первой реальной команды. Изменение выполнять через API политик с указанием автора и причины.

После переключения проверить новую тестовую заявку с уникальными реквизитами. Критерии готовности автономного режима:

- команда создается и исполняется один раз;
- повторные poll/reconciliation не дублируют пользователя или комментарии;
- неподтвержденный результат блокирует повтор и требует ручной проверки;
- заявитель получает понятные сообщения без технических секретов;
- все изменения политики и состояния отражены в журнале аудита.

## План отката

При любом неконтролируемом поведении сначала отключить глобальный автопилот через управляющий API, затем остановить Windows worker. Не удалять `TicketRun`, команды и события: они нужны для reconciliation и расследования. Политику `create_user` вернуть в `confirm` или `disabled`; уже начатые команды сверить по фактическому состоянию AD перед любым повтором.
