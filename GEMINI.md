### Правила для `GEMINI.md` (этот файл)

- **Только правила и принципы.** Если хочется добавить описание эндпоинтов, полей БД, команды запуска — это идёт в `docs/` или `README.md`, а не сюда.
- **Нет абсолютных путей.** Все ссылки — относительные (`docs/architecture.md`, не `file:///...`).
- **Нет дублирования.** Если информация уже есть в `docs/` — добавь только ссылку.
- **Архитектурные решения с обоснованием.** Раздел «Принципы (ПОЧЕМУ)» обновляется при добавлении новых архитектурных инвариантов.

### Структура `docs/` (инвариант — не нарушать)

```
docs/
├── architecture.md          ← единственный источник правды об архитектуре системы
├── services/                ← документация по нашим сервисам
```

> [!NOTE]
> При создании нового сервиса сразу добавить заглушку `docs/services/<name>/README.md`.
> При обнаружении абсолютной ссылки `file:///...` — заменить на относительную.
> Эти два действия выполняются **в момент изменения кода**, а не отдельно.

### Правила для `README.md`

- Описание структуры `docs/` в разделе «Структура проекта» должно совпадать с реальным содержимым папки.

## 1. Архитектура

Проект — **микросервисный монорепозиторий**, состоящий из двух сервисов:
- `core-api/` — FastAPI. Шлюз, хранилище состояния, фоновый воркер.
- `bot/` — aiogram 3.x. Тонкий интерфейсный слой, делегирует логику в Core API.

Сервисы общаются по двум каналам:
1. **HTTP REST** (`bot` → `core-api`) — управляющие команды и запросы данных.
2. **Redis Pub/Sub** (`core-api` → `bot`) — push-уведомления о новых событиях.

Схема взаимодействия и Data Flow подробно описаны в [`docs/architecture.md`](docs/architecture.md).

## 2. Принципы и архитектурные решения (ПОЧЕМУ)

### Бот не хранит учётные данные
Вся ответственность за хранение и использование паролей IntraService лежит **исключительно на Core API**. Бот получает только данные, отфильтрованные шлюзом. Это намеренное решение для изоляции секретов.

### Нет глобального кэша в worker
В `worker.py` намеренно отсутствует кэш истории заявок между пользователями. Причина: разные пользователи имеют разные права доступа в IntraService, поэтому общий кэш создаёт уязвимость утечки данных. Кэш с ключом по `auth_b64` был бы мёртвым кодом (каждая заявка в цикле встречается единожды).

### Воркер опрашивает IntraService через сервисный аккаунт
`check_updates` выполняет запросы к API IntraService глобально от имени выделенного сервисного аккаунта, а затем сопоставляет ID исполнителей задач со списком локальных пользователей из БД в памяти. Это кардинально снижает сетевую нагрузку и устраняет зависимость работоспособности воркера от наличия авторизованных сессий пользователей в базе данных.

### Часовые пояса
`last_check_time` хранится в **UTC**. Перед запросом к IntraService конвертируется в `settings.INTRASERVICE_TZ` (по умолчанию `Europe/Moscow`) через `zoneinfo`. Аналогично `event_date` из истории заявок. Не передавайте UTC-время напрямую в API IntraService.

### Динамическое включение WinRM (WMI Bootstrap)
Во избежание необходимости распространения GPO (Group Policy) в домене Active Directory, микросервис `printer-worker` осуществляет динамическое подключение и настройку WinRM на удаленных станциях через WMI (DCOM/RPC) «на лету» перед установкой принтера. После окончания работ (успешного или сбойного) оркестратор гарантированно деактивирует WinRM для минимизации поверхности сетевых атак на хосты пользователей.

### Веб-панель администратора (SSE и Redis-driven логирование)
Для ручного запуска установки принтеров и мониторинга воркера встроена легковесная веб-панель в `core-api`. Взаимодействие с `printer-worker` полностью событийно через Redis:
- Запуск ручной установки публикует команду в канал `printer_actions` с флагом `is_manual=True`.
- Воркер при этом обходит вызовы IntraService API, а лог-вывод транслирует в Redis Pub/Sub канал `printer_job_logs:{job_id}`.
- Панель считывает эти логи и отдает в браузер через Server-Sent Events (SSE). Это сохраняет воркер легким демоном без необходимости открывать дополнительные HTTP-порты.

### JWT-авторизация веб-панели (Session Cookie)
Доступ к API веб-панели администратора (`/admin/api/...`) защищен сессионной cookie `admin_session`, содержащей подписанный JWT-токен. Авторизация происходит посредством проверки введенных логина/пароля в API IntraService. Это исключает необходимость использования общего `BOT_API_KEY` в интерфейсе и повышает безопасность веб-панели.

### Избирательное оповещение при сбоях установки принтеров (Тихий режим)
При возникновении ошибок в ходе автоматической установки принтера воркер разделяет их на пользовательские (понятные пользователю: выключен ПК, нет пинга до МФУ, не хватает данных) и системные (инфраструктурные сбои, ошибки сети, сбои SMB копирования драйверов).
Для системных сбоев применен тихий режим: воркер не отправляет комментарии пользователю в IntraService и не переводит задачу в статус «Требует уточнения» (оставляя её в текущем статусе для ручного разбора администратором), поскольку пользователь никак не связан с проблемой и не может на неё повлиять.

### Сетевая проверка Fail-Fast перед подтверждением
Перед переводом задачи в статус ожидания подтверждения (`WAITING_APPROVAL`), микросервис `printer-worker` в обязательном порядке валидирует наличие необходимых данных (`connection_type`, `target_pc`, `driver_info`) и проверяет сетевую доступность целевого ПК (а также МФУ при типе подключения `tcpip`). В случае недоступности или нехватки данных задача сразу переходит в статус «Требует уточнения» с информативным комментарием для пользователя, не отвлекая администратора на этапе подтверждения.

## 3. Правила написания кода

### Асинхронность
Все I/O операции — **строго асинхронные** (`async`/`await`):
- База данных: `SQLAlchemy AsyncSession`
- HTTP: `aiohttp.ClientSession`
- Redis: `aioredis` async API

### Управление HTTP-сессиями aiohttp
Используйте **долгоживущие** `aiohttp.ClientSession`, привязанные к жизненному циклу приложения (FastAPI `lifespan`). Не создавайте новую сессию на каждый запрос — это утечка дескрипторов. Закрытие сессии (`await session.close()`) должно быть гарантировано в блоке `finally` или при завершении `lifespan`.

### Управление соединениями Redis Pub/Sub
Используйте контекстный менеджер:
```python
async with redis.pubsub() as pubsub:
    ...
```
И явный `await redis.close()` в `finally`. Без этого — утечка соединений.

### Формат дат
При передаче временных фильтров в API (`CreatedMoreThan`, `ChangedMoreThan`) используйте формат `YYYY-MM-DD HH:MM` в локальном TZ IntraService. Используйте `parse_api_date(date_str)` из `utils.py` для парсинга входящих дат.

## 4. Правила безопасности (запреты)

| Запрет | Причина |
|---|---|
| Не хардкодить `BOT_API_KEY` | Передавать только через переменные окружения |
| Не слушать на `0.0.0.0` вне Docker | При локальной разработке — только `127.0.0.1` |
| Не хранить пароли в боте | Только Core API работает с учётными данными |
| Не добавлять глобальный кэш в worker без учёта `auth_b64` | Уязвимость утечки данных между пользователями |
| Не удалять `secrets.compare_digest` в `deps.py` | Защита от Timing Attacks при проверке API-ключа |

## 5. Аутентификация между сервисами

**Бот → Core API:** Pre-shared ключ в заголовке `X-Bot-Api-Key: <key>`. Проверка в `core-api/app/routers/deps.py`.

**Core API → IntraService:** Basic Auth (`Authorization: Basic <base64(login:password)>`). Формируется из зашифрованного `is_password_b64`, хранящегося в PostgreSQL.
