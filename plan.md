
Есть какие-то архитектурные и концептуальные неясности в проекте, которые приводят к грязной архитектуре и потери фокуса
12:38 PM
Да, в проекте исторически накопилось 5 фундаментальных концептуальных неясностей, которые периодически размывают фокус и создают предпосылки для «грязной» архитектуры.

Разберём их честно, с первопричинами и чётким вектором решения:

1. 🧩 Размытая идентичность helpdesk-agent/ (3 роли в одной папке)
В чём неясность: В директории helpdesk-agent/ сейчас смешаны 3 принципиально разных сущности:
Execution Daemon (Domain Worker): Фоновый процесс (execution_worker.py), который должен жить на Windows-машине с доступом к Active Directory, слушать Redis Stream и крутить PowerShell.
CLI-инструмент инженера: Интерактивная консольная утилита (helpdesk_tool.py), через которую человек смотрит дашборд и принимает решения.
Тулкит для AI-агента Antigravity (AGY Skills): Скрипты, которые агент запускает из диалога (/triage, /diag, /sync).
К чему это приводит: Путаница в зависимостях (например, почему CLI импортирует execution_worker), дублирование логики и риск того, что код исполнения снова начнёт вызываться в процессе CLI вместо воркера.
Чёткое разделение фокуса:
agent-runner/ (или worker/) — только headless-демон исполнения (слушает очередь, крутит AD/WinRM).
helpdesk-cli/ — только тонкий клиент (отправляет команды в Core API и выводит красивый UI в терминал).
2. 🏛️ Монолитность core-api (Gateway + Worker + RAG + Хостинг SPA)
В чём неясность: Сервис core-api сейчас совмещает в одном процессе:
HTTP API Gateway & Command Bus.
Фоновый воркер опроса IntraService (worker.py на 1000 строк с AsyncIOScheduler).
Векторный RAG-поиск по базе знаний (Postgres + pgvector).
Хостинг статики React SPA (/admin).
К чему это приводит: При деплое или перезапуске API (например, обновлении маршрута или фронтенда) прерывается опрос очереди заявок и рвутся все активные SSE-сессии. В worker.py намешана бизнес-логика триажа, парсинг XML кастомных полей, отправка пушей и эвристики принтеров.
Чёткое разделение фокуса: Выделить intraservice-poller в отдельную фоновую задачу/процесс, а core-api оставить чистым шлюзом состояния, авторизации и шиной событий.
3. 🧠 Разорванный контур AI / LLM (Core API vs Local Ollama vs LiteLLM)
В чём неясность: В проекте нет единой точки входа для ИИ-логики:
Векторизация и семантический поиск тикетов (rag.py) живут в core-api и ходят в LiteLLM / Gemini.
Суммаризация истории тикетов (ollama_client.py) живёт в helpdesk-agent и напрямую дёргает Docker-контейнер intralink_ollama (Qwen2.5:1.5B).
Рекомендации по триажу формируются частью эвристиками, частью LLM.
К чему это приводит: Контейнер ollama запущен в Docker Compose с резервацией GPU, но бэкенд о нём не знает — его дёргает только CLI-скрипт напрямую по localhost.
Чёткое разделение фокуса: Все AI-сервисы (Embeddings, RAG, Summarization, Triage Suggestions) должны быть централизованы внутри Core API (например, в модуле app/services/llm.py), а клиенты (Web UI, CLI, Bot) получают готовые AI-ответы через единый API.
4. 📱 Двойственность интерфейсов (Telegram-бот vs Web SPA vs AGY CLI)
В чём неясность: Изначально проект начинался как intraservice-tg-bot (Telegram-бот для инженера). Затем появились:
Web SPA панель (intra-web) для пакетного разбора стопки заявок.
CLI-ассистент в среде Antigravity (helpdesk_tool.py + слэш-команды).
В результате Telegram-бот стал «третьим лишним» — в основном он просто пересылает пуши из Redis Streams, а его интерактивные сценарии отстали от Web UI.
К чему это приводит: Распыление внимания: непонятно, куда внедрять новые фичи управления (в бот или в веб).
Чёткое разделение фокуса: Зафиксировать за каждым интерфейсом одну главную роль:
Telegram-бот: Мобильный пейджер и экстренный пульт (уведомления об инцидентах + быстрые кнопки [✅ Одобрить] / [❌ Отклонить] для HITL).
Web SPA (/admin): Операторский центр (массовый триаж стопки тикетов, аналитика, журнал аудита).
AGY CLI / Скиллы: Инженерный автопилот (глубокий RAG, автоматизация AD/WLAN/принтеров, пакетная обработка).
5. 📑 Рассинхронизация шаблонов и правил триажа
В чём неясность: Правила принятия решений и тексты типовых комментариев размазаны по трём местам:
Константа TRIAGE_TEMPLATES в core-api/app/routers/triage.py.
Markdown-файлы навыков .agents/skills/intraservice-helpdesk/SKILL.md и duplicates/SKILL.md.
Эвристические регулярные выражения в intraservice_parser.py.
К чему это приводит: Если инженер хочет поменять текст шаблона (например, адрес кабинета для выдачи Wi-Fi или регламент создания почты), приходится редактировать Python-код и пересобирать контейнеры.
Чёткое разделение фокуса: Вынести шаблоны триажа и правила маршрутизации в конфигурируемый JSON/YAML или таблицу PostgreSQL, управляемую через Web UI / API без необходимости правок в коде.
